## 스펙 우선, 루프로 완결.

리포지토리가 하니스이며 계획은 스스로 완료까지 실행됩니다.

Deep Work Plan(DWP)은 AI 에이전트와 함께 복잡한 소프트웨어 작업을 계획하고 실행하기 위한 오픈, MIT 라이선스 방법론이자 키트입니다. 설치 방식을 고르거나 템플릿을 복사하지 않습니다 — init.md 프롬프트를 복사하여 에이전트에 붙여넣습니다:

> init.md 프롬프트를 복사하여 코딩 에이전트 — Claude Code, Cursor, Codex, 또는 다른 에이전트 — 에 붙여넣어 어떤 리포지토리든 AI-first로 만드세요.

## 방법론을 떠받치는 것.

1. **스펙 우선** — 계획은 지속되는 단일 진실 공급원입니다: 원자적 작업, 인수 기준, 그리고 에이전트가 통과해야 하는 검증 게이트.
2. **리포지토리가 곧 하니스** — 컨텍스트, 도구, 가드레일, 상태가 어떤 에이전트든 읽을 수 있는 일반 파일로 리포지토리에 있습니다.

3. **Loop engineering** — 계획은 끝까지 실행됩니다: 등록, 사람이 시작하는 데몬, 권한을 더하지 않는 넛지, 페일오버, 그리고 계획 이벤트.
4. **측정된 효율** — 플로우별 지시 바이트를 측정 방법과 함께 측정하고 공개합니다 — 지어낸 토큰 비율은 결코 없습니다.

## 문제와 해답

짧은 작업에서 코딩 에이전트는 놀라운 성능을 보입니다. 장기 미션 — 마이그레이션, 새 서브시스템, 수십 개 파일의 리팩터링 — 을 맡기면 표류합니다: 컨텍스트가 차고, 앞선 결정이 흐려지고, 수 시간의 작업이 한복간에서 멈춥니다.



컨텍스트는 에이전트에게 가장 귀한 자원입니다. 그래서 하네스는 자체 지시사항을 간결하고 감사할 수 있게 유지합니다. 지시사항은 단계적으로 로드되고, 검증은 변경된 부분에 집중하며, 각 작업에는 관련 컨텍스트가 제공됩니다. 플로우별 지시사항 용량을 바이트 단위로 공개해 그 부담을 확인할 수 있습니다. 계획도 작업에 맞춰 선택합니다. 범위가 정해진 수정에는 Lite, 몇 시간 걸리는 작업에는 Full을 사용합니다. 형식이 작업 범위를 따르므로 과정은 집중력을 유지하고 추적하기 쉽습니다.

## 인간은 방향을 잡습니다. 에이전트가 실행합니다.

완료가 무엇인지, 경계가 어디인지 정하는 것은 사람입니다. 계획이 의도를 담고, 에이전트가 시간을 소모합니다 — 늘 지켜볼 필요도, 이십 분마다 고칠 필요도 없습니다.

- 당신: 의도, 수용 기준, 리뷰
- 에이전트: 실행, 한 작업씩
- 계획: 둘 사이의 계약

## 에이전트가 이탈하지 못하는 계획.

긴 작업은 어떤 모델의 컨텍스트도 채웁니다. 세부 사항은 사라지고 에이전트는 표류합니다. 서면 계획 — 원자적 작업, 검증 게이트, 재개 가능한 상태 — 이야말로 매 바퀴 돌아오는 기준입니다.

1. 계획
2. 원자적 작업
3. 검증 게이트
4. 완료
5. 재개 가능한 상태

[핵심 루프 보기](/ko/methodology)

## 완료는 계약이지 감이 아닙니다.

각 작업은 수용 기준과 통과해야 할 검사를 명시합니다. 에이전트가 완료된 느낌으로 끝낼 수는 없습니다 — 통과하거나, 아니면 작업은 열린 채로 남습니다.

- 테스트가 통과한다
- 타입 검사가 통과한다
- 승인 기준이 충족된다
- 아니면 작업은 열려 있다

## 저장소가 곧 harness입니다.

컨텍스트, 도구, 가드레일, 상태는 어떤 에이전트나 읽을 수 있는 평범한 파일로 저장소 안에 살아 있습니다. 잠금도, 외부 두뇌도 없이 — 컨텍스트 초기화 이후에도 유지됩니다.

- 디스크에 남는 지속적인 명세
- 감이 아니라 검증 게이트
- 컨텍스트 초기화를 견딥니다

## 계획은 끝까지 실행됩니다. 권한은 사람에게 남습니다.

Loop engineering은 사람이 계속 확인하지 않아도 계획이 완료되도록 합니다. 아래 행은 루프의 릴리스된 계약을 설명합니다. 대부분은 herdr-peers 계약이며 계획 대기열은 팩 계약입니다. Herdr는 선택 사항이며, 방법론은 이를 사용하지 않아도 작동합니다.

> 스펙 우선은 무엇을, 하니스는 어디서를, Loop engineering은 어떻게 끝나는지를 말합니다.

**루프:** 등록 (`lead claim`, 리드와 승계) → 데몬 (`autopilot --loop`, 사람이 시작) → 넛지 (`idle ≥ 5 min`, 권한 추가 없음) → 페일오버 (`lead takeover`, 첫 연결 가능 승계자) → 알림 (`plan-event-v1`, 사람의 명령으로) → 완료 (`plan_completed`, 게이트 통과). 리드 기록이 있는 모든 열린 계획, 자체 상태가 완료를 말할 때까지.



| 계약 | 보장하는 것 | 출처 (herdr-peers v2.2.0) |
| --- | --- | --- |
| 계획 등록 (`herdr-peers lead claim`) | 루프가 지켜보는 계획에는 에포크와 승계 목록을 가진 리드 기록이 있습니다. 가장 높은 에포크의 보유자만 그 리드로 행동합니다. | `skills/herdr-peers/protocol.md` §12 |
| 사람만 시작 (`herdr-peers autopilot start --loop`) | 데몬은 사람이 자신의 말로만 시작합니다. 어떤 요청, 답장, 알림도 데몬을 시작하거나 멈추거나 그 동작을 바꿀 수 없습니다. | `skills/herdr-peers/autopilot.md` §1 |
| 넛지는 권한을 더하지 않음 (`plan_stalled`) | 열린 계획의 유휴 리드는 계속하라는 고정 프롬프트 하나를 받습니다. 게이트, 중지 조건, 에스컬레이션은 이전과 같이 구속력을 가지며, 진전 없는 프롬프트가 세 번이면 계획은 정체로 표시됩니다. | `skills/herdr-peers/autopilot.md` §5.2–5.3 |
| 승계자로 페일오버 (`herdr-peers lead takeover`) | 리드가 사라지면 처음으로 연결 가능한 승계자에게 인계가 요청되고, 헬퍼가 증거를 다시 확인합니다. 레인은 사람이 미리 기록한 허가가 있을 때만 리드를 맡습니다. | `skills/herdr-peers/autopilot.md` §5.2, §7 |
| 계획 이벤트 (`plan-event-v1`) | 계획이 정체되거나, 차단되거나, 리드를 잃거나, 큐에서 시작되거나, 완료되면 사람이 선택한 명령이 plan-event-v1 객체 하나를 받습니다. 팩에는 이를 위한 Dailybot 알림기가 포함되어 있습니다. | `docs/schema/plan-event-v1.json` |
| 플릿 맵 (`plans-v1` · `fleet-v1`) | 각 머신은 자신의 계획을 plans-v1으로 보고하고, 데몬은 모든 머신, 에이전트, 리포지토리, 계획의 fleet-v1 맵을 유지하며, fleet ui가 이를 읽기 전용으로 보여줍니다. | `docs/schema/fleet-v1.json` |
| 계획 대기열 (`dwp-queue-v1`) | 팩은 대기열을 검증하고 기록하며, 데몬은 이를 읽어 대기 중인 계획을 계속 진행합니다. | `skills/deepworkplan/shared/queue.py` |
| 리드 검증 (`herdr-peers lead verify`) | 병합, 태그, 릴리스 전에 리드는 모든 머신에서 여전히 계획을 보유하고 있는지 확인합니다. 더 새로운 리드가 있으면 거부되고, 연결할 수 없는 머신이 있으면 그 위험이 기록상 수용되지 않는 한 중단됩니다. | `skills/herdr-peers/protocol.md` §12 |

결정 브레인(`--brain`)과 리드 임명(`--appoint`)은 같은 데몬의 옵트인 플래그이며, 각각 사람이 켭니다. 데몬은 병합, 릴리스, 로그인, 권한 변경을 절대 하지 않습니다.

## 플로우별 지시 바이트, 측정됨.

하니스는 각 플로우가 시작 전에 읽어야 하는 것 — 라우터, 하위 스킬, 그리고 그것이 링크하는 공유 리소스 — 을 공개합니다. 이것이 릴리스된 팩의 필수 읽기 세트입니다.

| `resume` | 32,023|
| `refine` | 76,797|
| `onboard` | 82,051|
| `status` | 27,311|
| `verify` | 36,701|

단위: 파일 시스템 바이트. 릴리스된 팩에서 다음 명령으로 측정했습니다: `bash tests/efficiency/measure-instruction-load.sh` (deepworkplan-skill v8.0.2).

제공자 토큰, 비용, 루프 완결 통계는 표시하지 않습니다. 이를 측정하는 태그된 출처가 아직 없으므로 행이 없습니다. 스크립트의 바이트 ÷ 4 토큰 수치는 표시된 추정치이며, 측정값이 아닙니다.

## 무엇을 얻는가

- 실제 스택과 명령으로부터 추론된, 리포지토리 루트의 AGENTS.md.
- 분류된 `docs/`와 모듈별 문서.
- `.claude`에서 `.agents`로의 심링크가 있는 `.agents/` 디렉터리(스킬, 에이전트, 명령).
- 모든 에이전트를 위해 한 번 설치되는 Deep Work Plan 스킬 — author 하위 스킬을 포함하여 리포지토리가 자체 스킬, 에이전트, 명령을 키울 수 있고, dependency-upgrade 같은 선택형 애드온과 어떤 사용자 대면 인터페이스 표면에든 적용되는 design-system 애드온도 있습니다.
- gitignore된 `.dwp/` 폴더의 장시간, 재개 가능한 계획. 방법론 자체에는 데몬도 외부 상태도 필요 없으며, 선택형 루프 데몬은 연속성을 더할 뿐 의존성을 더하지 않습니다.
- 다중 에이전트 위임 및 에코시스템 1.0 — 격리된 워크트리, 게이트를 통한 검증된 증거, 선택형 고정 에코시스템 애드온을 통해 병렬 에이전트를 안전하게 조율합니다.

## 실행하면 무슨 일이 일어나는가

1. **에이전트가 [/init.md](/init.md)를 엽니다** — 온보딩 프롬프트와 그것이 링크하는 방법론, 스펙, 키트를 읽습니다.
2. **Deep Work Plan 스킬을 설치합니다** — 모든 리포지토리에서 동일한 엔진입니다: 라우터와 그 하위 스킬(create, execute, refine, resume, status, verify, onboard, author, upgrade)을, Claude Code, Cursor, Codex, Gemini, Copilot용으로.
3. **리포지토리를 적응시킵니다** — 실제 스택을 추론하여(복사·붙여넣기가 아니라) AGENTS.md, `docs/`, 모듈별 README, 추론된 `.agents/` 키트, gitignore된 `.dwp/`를 작성합니다. 리포지토리가 하니스가 됩니다.
4. **계획하고 실행합니다** — 장시간 Deep Work Plan을 명시적인 인수 기준과 검증 게이트에 대비해 단계별로, 수 시간 동안 자율적으로 실행합니다.
5. **사람이 루프를 시작합니다** — 선택 사항이며 Herdr 애드온과 함께 씁니다: 에이전트가 아닌 당신이 `herdr-peers autopilot start --loop`를 실행합니다. 리드 기록이 있는 모든 열린 계획이 끝까지 계속 실행되고, 계획이 정체되거나 차단되거나 완료되면 알림기가 이를 전달받습니다.

스킬은 어디서나 같은 방식으로 설치되는 재사용 가능한 엔진이고, 적응되는 것은 리포지토리입니다. 설치 방법(Skills CLI, OpenClaw, 또는 git clone)은 [/init.md](/init.md) 프롬프트와 [빠른 시작](/quickstart)에 있습니다.
