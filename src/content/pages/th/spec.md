## ข้อกำหนด Deep Work Plan

**มาตรฐานปัจจุบัน: DWP 8.0.0 (รุ่น `v8.0.0`)** ฐานที่คงไว้ประกอบด้วยชั้นบันทึก v6 และส่วนขยาย v7 แผนใหม่ใช้ `plan-contract/v8` เป็นค่าเริ่มต้น แผน v5, v6 และ v7 ที่มีอยู่ยังคงรุ่นที่บันทึกไว้ และจะย้ายรุ่นได้เฉพาะเมื่อสั่ง `refine migrate` อย่างชัดเจน v8 คง `plan-manifest/v7` ไว้และเพิ่ม `plan-contract/v8`, `journal-event/v8` และ `plan-snapshot/v8`; schema manifest และ journal-event v7 ยังรองรับแผนเดิม [Manifest v7](https://deepworkplan.com/schema/plan-manifest/v7.json), [contract v8](https://deepworkplan.com/schema/plan-contract/v8.json), [journal event v8](https://deepworkplan.com/schema/journal-event/v8.json) และ [snapshot v8](https://deepworkplan.com/schema/plan-snapshot/v8.json)

ข้อกำหนดคือนิยามที่แม่นยำและอ่านได้ของระเบียบวิธี — โครงสร้างและโปรโตคอลที่มนุษย์และเอเจนต์ใช้ร่วมกัน มันระบุในเชิงบรรทัดฐานตามถ้อยคำแบบ RFC-2119 ว่าแผนที่ขับเคลื่อนด้วยข้อกำหนดมีโครงสร้างอย่างไรและเอเจนต์ต้องดำเนินการเทียบกับมันอย่างไร แผนคือแหล่งความจริง validation gate เป็นแบบสองค่า และ repository เองพก harness ที่เอเจนต์ต้องการ มันถูกจัดเป็นเอกสารที่เรียงลำดับ

- **มาตรฐานเอกสาร** — โครงสร้าง repository แบบ AI-first
- **เลเยอร์การบันทึก** — เลเยอร์บันทึกที่สนับสนุนด้วยหลักฐาน: สัญญา, วารสาร, คลาสของหลักฐาน, การอนุมัติ และใบเสร็จ
- **ทรัพยากรและความสามารถ** — การรันงานแบบมีขอบเขต: มานิเฟสต์บริบท, ขอบเขตทรัพยากร, ความสามารถของโฮสต์ และรีจิสทรีส่วนเสริม
- **การมอบหมายงาน** — การทำงานหลายเอเจนต์และแบบฝูง: worktree คู่ขนานที่ปลอดภัย, เหตุการณ์การมอบหมายงาน และการสืบทอดตำแหน่งผู้นำ
- **สถานะแผนงาน** — เลเยอร์สถานะที่เครื่องอ่านได้: สแนปช็อตที่ดึงมาจากวารสารใน v6/v7 (`ledger.py project`), เลเยอร์สถานะดั้งเดิม v5 และการปรับปรุงข้อมูล
- **โปรโตคอลของเอเจนต์** — พฤติกรรมข้ามเอเจนต์ที่จำเป็น การจับคู่คำสั่ง เอเจนต์ที่รองรับ (รวมถึง OpenClaw และ Hermes) และโปรไฟล์การดำเนินงาน (แบบโต้ตอบเทียบกับแบบไม่มีผู้ดูแล) พร้อมเงื่อนไขหยุดและ scheduled continuation
- **Archetype** — repo เดี่ยว orchestrator hub และ agent workspace (บ้านที่มีอายุยาวนานของเอเจนต์อัตโนมัติ: OpenClaw workspace ไดเรกทอรีบริการ Hermes persistent volume ของ cloud agent); หลักการจำแนกประเภทและความแตกต่างของการออนบอร์ด
- **ส่วนเสริม** — กลไกแบบเลือกเข้าร่วมสำหรับวางซ้อนความสามารถที่เป็นทางเลือก รวมถึง sub-skill ชื่อ author (เพื่อให้ repository ปลูก kit ของตัวเอง) ส่วนเสริมการบำรุงรักษาอย่าง dependency-upgrade และส่วนเสริม design-system (`docs/DESIGN.md` ที่ให้เหตุผลจากแหล่งดีไซน์จริงของ repo พร้อมโปรไฟล์สำหรับ UI เชิงภาพ เอาต์พุต CLI และพื้นผิวเชิงสนทนา)
- **ความสอดคล้อง** — นิยามเชิงบรรทัดฐานของ repository แบบ AI-first: สิ่งประดิษฐ์ที่ repository MUST และ SHOULD มี สิ่งที่ทำให้แผนมีรูปแบบที่ถูกต้อง และวิธีตรวจสอบมันอย่างเป็นวัตถุวิสัยด้วย `/dwp-verify`
- **สถานะแผน** — ชั้นสถานะที่เครื่องอ่านได้: `manifest.json` และ `state.json` บันทึก gate บันทึกผลลัพธ์ในฐานะหน่วยความจำเชิงลำดับเหตุการณ์ การปรับประสานงาน (markdown ชนะ) และเมื่อใดที่ชั้นนี้จำเป็น
