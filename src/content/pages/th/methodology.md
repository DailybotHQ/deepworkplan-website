## ระเบียบวิธี Deep Work Plan

แพ็ก v8 สร้างแผนใหม่ด้วย `plan-contract/v8` เป็นค่าเริ่มต้น แผนเดิมคงรุ่นที่บันทึกไว้ การย้ายต้องใช้ `refine migrate` อย่างชัดเจน
Deep Work Plan (DWP) คือระเบียบวิธีแบบเปิดที่เป็นกลางต่อเฟรมเวิร์กสำหรับการดำเนินงานวิศวกรรมอย่างมีโครงสร้างและอิสระด้วยเอเจนต์เขียนโค้ด AI มันเปลี่ยนเป้าหมายที่คลุมเครือให้กลายเป็นแผนที่ทบทวนได้ ซึ่งเอเจนต์สามารถดำเนินการ หยุดพัก ดำเนินการต่อ และรายงานผลได้ — โดยไม่สูญเสียบริบท

DWP ตั้งอยู่บนเสาหลักสี่ต้น — สเปกมาก่อน, repository คือ harness, Loop engineering และประสิทธิภาพที่วัดได้ สรุปในประโยคเดียว: *สเปกมาก่อน ปิดลูปในตัว: repository คือ harness และแผนจะเดินหน้าเองจนเสร็จ*

**สเปกมาก่อน** แทนที่จะถือว่าบทสนทนาแชตเป็นแหล่งความจริง คุณเขียนลงไปก่อนว่า *อะไร* ควรเป็นจริง — เป้าหมาย ขอบเขต เกณฑ์การยอมรับ และการตรวจสอบที่พิสูจน์ว่าเสร็จ — และเอเจนต์ดำเนินการเทียบกับข้อกำหนดนั้น ใน DWP แผน *คือ* ข้อกำหนด แผน → atomic task → validation gate → การเสร็จสิ้น การเขียนข้อกำหนดก่อนลดการเบี่ยงเบน (เอเจนต์ถูกวัดเทียบกับเกณฑ์ที่ระบุไว้) ทำให้งานตรวจสอบได้ (ทุก gate ผ่านหรือไม่ผ่าน) และทำให้ดำเนินต่อได้ (ข้อกำหนดอยู่ได้นานกว่าเซสชันหรือเอเจนต์ใด) ด้วยความที่เป็นกลางต่อเครื่องมือและฝังอยู่ใน repository โดยกำเนิด มันจึงต่างจากระบบขับเคลื่อนด้วยข้อกำหนดที่ผูกติดกับเครื่องมืออย่าง GitHub Spec Kit, Amazon Kiro และ Tessl

**repository คือ harness** ตัวแบบจำลองภาษาโดยลำพังเป็นเพียงตัวทำนายข้อความ สิ่งที่ทำให้มันเป็นวิศวกรที่เชื่อถือได้คือ *harness* รอบตัวมัน — บริบท เครื่องมือ control loop guardrail และสถานะถาวร harness engineering คือการออกแบบโครงนั่งร้านนั้นอย่างจงใจ จุดยืนของ DWP คือมันควรอยู่ใน repository ไม่ใช่ในเครื่องมือ ได้แก่ บริบทในรูป `AGENTS.md` + `docs/` เครื่องมือในรูป kit `.agents/` control loop ในรูปแผน guardrail ในรูป validation gate และสถานะในรูป `.dwp/` ที่ถูก gitignore เพราะทุกส่วนเป็นไฟล์ใน repo harness จึงพกพาได้ — เอเจนต์ใดก็ขับเคลื่อน repo ใดก็ได้

**Loop engineering** สเปกและ harness ทำให้งานถูกต้องและพกพาได้ ส่วน Loop engineering ทำให้งานเสร็จจริง เมื่อใช้ส่วนเสริม Herdr ซึ่งเป็นตัวเลือก แผนจะลงทะเบียน lead ของตน และลงทะเบียนผู้สืบทอดเมื่อแผนระบุไว้ daemon ที่มีเพียงมนุษย์เท่านั้นเป็นผู้เริ่มจะเตือน lead ที่ว่างอยู่ให้ทำต่อ ขอให้ผู้สืบทอดคนแรกที่ติดต่อได้รับช่วงต่อจาก lead ที่หายไป และรายงานเมื่อแผนหยุดชะงัก ถูกบล็อก หรือเสร็จสิ้น การเตือนไม่ได้เพิ่มอำนาจ — gates และการส่งต่อเรื่องของแผนยังคงมีผลบังคับเช่นเดิม ระเบียบวิธีทำงานได้โดยไม่มีลูป ลูปเพียงขยายพลังของมันเท่านั้น

**ประสิทธิภาพที่วัดได้** บริบทคือทรัพยากรที่หายากที่สุดของเอเจนต์เขียนโค้ด และระเบียบวิธีที่เปลืองบริบทจะล้มเหลวในจังหวะที่งานยืดยาวขึ้นพอดี DWP โหลดคำสั่งแบบค่อยเป็นค่อยไป — คู่มือแต่ละเล่มถูกโหลดเมื่อทริกเกอร์ของมันเริ่มทำงาน — คัดเลือกการตรวจสอบจากสิ่งที่แต่ละงานแตะต้องจริง และตัดสินใจเรื่อง skill ภายในงาน instruction bytes ที่แต่ละขั้นตอนต้องใช้ถูกวัดและเผยแพร่ ไม่มีเปอร์เซ็นต์ token ที่แต่งขึ้น

ระเบียบวิธีอธิบายไว้ในแปดบท

1. **แถลงการณ์** — Deep Work Plan คืออะไรและทำไมการดำเนินงานแบบมีโครงสร้างจึงสำคัญ
2. **ลูปหลัก** — วงจรวางแผน-ดำเนินการ-ตรวจสอบที่ขับเคลื่อนทุกงาน
3. **เทมเพลต** — โครงสร้างแผนและงานที่เอเจนต์และมนุษย์ใช้ร่วมกัน
4. **Skills และ agents** — วิธีที่คำสั่งและบทบาทของ agent ทำงานร่วมกัน kit ที่มีชีวิต (วิธีที่ repository ปลูก skill ของตัวเองผ่าน sub-skill ชื่อ author) และส่วนเสริมแบบเลือกเข้าร่วมอย่าง dependency-upgrade และส่วนเสริม design-system สำหรับพื้นผิวอินเทอร์เฟซที่ผู้ใช้มองเห็นทุกแบบ (UI เชิงภาพ เอาต์พุต CLI หรือเชิงสนทนา)
5. **Archetype** — การปรับระเบียบวิธีให้เข้ากับ repo เดี่ยวและ orchestrator hub
6. **การรันเอเจนต์หลายตัว** — lead และ lane ของมันข้าม pane คอนเทนเนอร์ เครื่อง และบัญชี โดยมีหนึ่ง branch และหนึ่งรีลีสต่อ repository
7. **ความเป็นอิสระของ swarm** — การตรวจความจุที่ขอบเขตของงาน handoff packet การสืบทอดตำแหน่ง lead ด้วย epoch และการส่งต่อเฉพาะเรื่องวิกฤต เพื่อให้ swarm อยู่รอดได้เกินขีดจำกัดของบัญชีเดียวหรือการสูญเสียเอเจนต์ตัวเดียว
8. **Loop engineering** — การลงทะเบียนแผน daemon ที่มนุษย์เป็นผู้เริ่ม การเตือนที่ไม่เพิ่มอำนาจ การสลับไปยังผู้สืบทอด เหตุการณ์ของแผน คิวของแผน และแผนที่ fleet
