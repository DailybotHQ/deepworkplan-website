## เปลี่ยน repository ของคุณให้เอเจนต์ AI ตัวไหนก็ทำงานให้เสร็จได้

repository ของคุณเก็บแผน บริบท และการตรวจสอบไว้ งานจึงอยู่รอดข้ามการรีสตาร์ต ส่งต่อระหว่างเอเจนต์ได้ และวนต่อไปจนผ่านทุกเกต — ภายในขอบเขตอำนาจที่คุณมอบให้

Deep Work Plan (DWP) คือระเบียบวิธีและ kit แบบเปิดที่ใช้ใบอนุญาต MIT สำหรับการวางแผนและดำเนินงานซอฟต์แวร์ที่ซับซ้อนด้วยเอเจนต์ AI คุณไม่ต้องเลือกวิธีติดตั้งหรือคัดลอกเทมเพลต — คุณคัดลอก prompt ของ init.md และวางลงใน agent ของคุณ:

> คัดลอก prompt ของ init.md และวางลงใน coding agent ของคุณ — Claude Code, Cursor, Codex หรืออื่น ๆ — เพื่อทำให้ repository ใดก็ได้เป็น AI-first

## รากฐานของระเบียบวิธีนี้

1. **สเปกมาก่อน** — แผนคือแหล่งความจริงที่คงทน: งานอะตอมมิก เกณฑ์การยอมรับ และ validation gate ที่เอเจนต์ต้องผ่าน
2. **repository คือ harness** — บริบท เครื่องมือ ราวกันตก และสถานะอยู่ใน repository เป็นไฟล์ธรรมดาที่เอเจนต์ใดก็อ่านได้

3. **Loop engineering** — แผนรันจนจบ: การลงทะเบียน daemon ที่มนุษย์เป็นผู้เริ่ม การกระตุ้นที่ไม่เพิ่มอำนาจใด ๆ การสลับไปยังผู้สืบทอด และเหตุการณ์ของแผน
4. **ประสิทธิภาพที่วัดได้** — จำนวนไบต์ของคำแนะนำต่อโฟลว์ วัดและเผยแพร่พร้อมวิธีการวัด — ไม่เคยแต่งตัวเลขเปอร์เซ็นต์ token ขึ้นมาเอง

## ปัญหาและคำตอบ

ในงานสั้น ๆ เอเจนต์เขียนโค้ดทำได้ดีมาก แต่เมื่อรับงานระยะยาว — การย้ายระบบ ซับซิสเต็มใหม่ การรีแฟกเตอร์หลายสิบไฟล์ — มันจะเบี่ยงเบน: คอนเท็กซ์เต็ม การตัดสินใจก่อนหน้าจางหาย และงานหลายชั่วโมงติดค้างกลางทาง



บริบทเป็นทรัพยากรที่มีจำกัดที่สุดของเอเจนต์ harness จึงรักษาคำแนะนำของตัวเองให้กระชับและตรวจสอบได้ คำแนะนำจะโหลดเป็นลำดับ การตรวจสอบมุ่งไปที่ส่วนที่เปลี่ยน และแต่ละงานได้รับบริบทที่เกี่ยวข้อง เราเผยแพร่ขนาดคำแนะนำของแต่ละโฟลว์เป็นไบต์ เพื่อให้เห็นภาระส่วนนี้อย่างชัดเจน แผนก็ปรับตามงานเช่นกัน: Lite สำหรับการแก้ไขที่มีขอบเขตชัดเจน และ Full สำหรับงานที่ใช้เวลาหลายชั่วโมง รูปแบบสอดคล้องกับขอบเขตงาน ช่วยให้กระบวนการมีจุดมุ่งหมายและติดตามได้

## มนุษย์นำทิศ agent ลงมือทำ

คุณคือผู้กำหนดว่า “เสร็จ” หมายความว่าอย่างไรและเส้นแบ่งอยู่ตรงไหน แผนงานจะส่งต่อเจตนาของคุณ ส่วนเอเจนต์ทำหน้าที่ลงมือชั่วโมงต่อชั่วโมง — ไม่ต้องคอยกำกับ ไม่ต้องคอยแก้ทุกยี่สิบนาที

- คุณ: เจตนา เกณฑ์การยอมรับ การรีวิว
- agent: ลงมือทำ ทีละงาน
- แผน: สัญญาระหว่างกัน

## แผนซึ่งเอเจนต์เบี่ยงเบนไปจากไม่ได้

งานยาว ๆ เติมคอนเท็กซ์ของโมเดลใดก็ได้จนเต็ม รายละเอียดหายไปและเอเจนต์เริ่มหลงทาง แผนงานที่เขียนไว้ — งานอะตอมมิก ประตูตรวจสอบ สถานะที่กลับมาทำต่อได้ — คือจุดที่มันวนกลับมาในทุกรอบ

1. แผน
2. งานอะตอมมิก
3. ด่านตรวจสอบ
4. การเสร็จสิ้น
5. สถานะที่กลับมาทำต่อได้

## เสร็จคือสัญญา ไม่ใช่ความรู้สึก

ทุกงานระบุเกณฑ์การยอมรับและการตรวจสอบที่ต้องผ่าน เอเจนต์ “รู้สึกว่าเสร็จ” ไม่ได้ — ต้องผ่านเท่านั้น ไม่เช่นนั้นงานยังคงเปิดอยู่

- เทสผ่าน
- ตรวจสอบไทป์ผ่าน
- บรรลุเกณฑ์การยอมรับ
- มิฉะนั้นงานยังเปิดอยู่

## แผนรันจนจบ อำนาจยังอยู่กับมนุษย์

Loop engineering ทำให้แผนดำเนินจนเสร็จได้โดยไม่ต้องมีมนุษย์คอยตรวจสอบ แถวด้านล่างอธิบายสัญญาที่ออกรุ่นแล้วของลูป: ส่วนใหญ่มาจาก herdr-peers ส่วนคิวแผนเป็นสัญญาของแพ็ก Herdr เป็นตัวเลือก ระเบียบวิธีทำงานได้โดยไม่มีมัน

> สเปกมาก่อนบอกว่าทำอะไร harness บอกว่าทำที่ไหน Loop engineering บอกว่าจะจบอย่างไร

**ลูป:** ลงทะเบียน (`lead claim`, lead และผู้สืบทอด) → Daemon (`autopilot --loop`, มนุษย์เป็นผู้เริ่ม) → กระตุ้น (`idle ≥ 5 min`, ไม่เพิ่มอำนาจ) → สลับ (`lead takeover`, ผู้สืบทอดแรกที่ติดต่อได้) → แจ้ง (`plan-event-v1`, ถึงคำสั่งของมนุษย์) → เสร็จ (`plan_completed`, ผ่าน gate แล้ว) ทุกแผนที่เปิดอยู่และมีบันทึก lead จนกว่าสถานะของมันเองจะบอกว่าเสร็จ



| สัญญา | สิ่งที่รับประกัน | แหล่งที่มา (herdr-peers v2.2.1) |
| --- | --- | --- |
| การลงทะเบียนแผน (`herdr-peers lead claim`) | แผนที่ลูปเฝ้าดูมีบันทึก lead พร้อม epoch และลำดับผู้สืบทอด เฉพาะผู้ถือ epoch สูงสุดเท่านั้นที่ทำหน้าที่เป็น lead | `skills/herdr-peers/protocol.md` §12 |
| มนุษย์เท่านั้นที่เริ่มได้ (`herdr-peers autopilot start --loop`) | มีเพียงมนุษย์ที่เริ่ม daemon ด้วยคำพูดของตนเอง ไม่มีคำถาม คำตอบ หรือการแจ้งเตือนใดที่เริ่ม หยุด หรือเปลี่ยนสิ่งที่มันทำได้ | `skills/herdr-peers/autopilot.md` §1 |
| การกระตุ้นไม่เพิ่มอำนาจ (`plan_stalled`) | lead ที่ว่างอยู่ของแผนที่เปิดอยู่จะได้รับพรอมต์คงที่หนึ่งข้อให้ทำต่อ gate เงื่อนไขการหยุด และการยกระดับยังผูกพันเหมือนเดิม พรอมต์สามครั้งโดยไม่มีความคืบหน้าจะทำเครื่องหมายว่าแผนหยุดชะงัก | `skills/herdr-peers/autopilot.md` §5.2–5.3 |
| สลับไปยังผู้สืบทอด (`herdr-peers lead takeover`) | เมื่อ lead หายไป ผู้สืบทอดคนแรกที่ติดต่อได้จะถูกขอให้รับช่วง และตัวช่วยจะตรวจหลักฐานอีกครั้ง lane จะรับตำแหน่ง lead ได้ก็ต่อเมื่อมีการอนุญาตที่มนุษย์บันทึกไว้ล่วงหน้าเท่านั้น | `skills/herdr-peers/autopilot.md` §5.2, §7 |
| เหตุการณ์ของแผน (`plan-event-v1`) | เมื่อแผนหยุดชะงัก ถูกบล็อก สูญเสีย lead เริ่มจากคิว หรือเสร็จสิ้น คำสั่งที่มนุษย์เลือกจะได้รับออบเจกต์ plan-event-v1 หนึ่งรายการ แพ็กมาพร้อมตัวแจ้งเตือน Dailybot สำหรับสิ่งนี้ | `docs/schema/plan-event-v1.json` |
| แผนที่ฟลีต (`plans-v1` · `fleet-v1`) | แต่ละเครื่องรายงานแผนของตนเป็น plans-v1 daemon เก็บแผนที่ fleet-v1 ของทุกเครื่อง เอเจนต์ repository และแผน และ fleet ui แสดงผลแบบอ่านอย่างเดียว | `docs/schema/fleet-v1.json` |
| คิวแผน (`dwp-queue-v1`) | แพ็กตรวจสอบและเขียนคิว ส่วน daemon อ่านคิวเพื่อดำเนินแผนที่รอต่อไป | `skills/deepworkplan/shared/queue.py` |
| การยืนยัน lead (`herdr-peers lead verify`) | ก่อนการ merge, tag หรือ release ใด ๆ lead จะยืนยันว่ายังถือแผนอยู่บนทุกเครื่อง lead ที่ใหม่กว่าจะปฏิเสธ และเครื่องที่ติดต่อไม่ได้จะหยุดมัน เว้นแต่ความเสี่ยงนั้นได้รับการยอมรับและบันทึกไว้ | `skills/herdr-peers/protocol.md` §12 |

สมองการตัดสินใจ (`--brain`) และการแต่งตั้ง lead (`--appoint`) เป็นแฟล็กแบบเลือกเปิดของ daemon ตัวเดียวกัน ซึ่งมนุษย์เป็นผู้เปิดแต่ละตัว daemon ไม่เคย merge, release, ลงชื่อเข้าใช้ หรือเปลี่ยนสิทธิ์ใด ๆ

## สิ่งที่คุณได้รับ

- AGENTS.md ที่รากของ repository ผ่านการให้เหตุผลจากเทคสแตกและคำสั่งจริงของคุณ
- `docs/` ที่จัดหมวดหมู่และเอกสารต่อโมดูล
- ไดเรกทอรี `.agents/` (skill, agent, คำสั่ง) พร้อม symlink จาก `.claude` ไปยัง `.agents`
- skill ของ Deep Work Plan ติดตั้งครั้งเดียวสำหรับทุกเอเจนต์ — รวมถึง sub-skill ชื่อ author เพื่อให้ repository ปลูก skill, agent และคำสั่งของตัวเองได้ พร้อมส่วนเสริมแบบเลือกเข้าร่วมอย่าง dependency-upgrade และส่วนเสริม design-system สำหรับพื้นผิวอินเทอร์เฟซที่ผู้ใช้มองเห็นทุกแบบ
- แผนระยะยาวที่ดำเนินต่อได้ในโฟลเดอร์ `.dwp/` ที่ถูก gitignore ตัวระเบียบวิธีเองไม่ต้องใช้ daemon และไม่มีสถานะภายนอก daemon ของลูปแบบเลือกใช้เพิ่มความต่อเนื่อง ไม่ใช่การพึ่งพา
- การมอบหมายงานหลายเอเจนต์และ Ecosystem 1.0 — ประสานงานเอเจนต์คู่ขนานอย่างปลอดภัยด้วย git worktree ที่แยกเฉพาะ, หลักฐานที่สังเกตได้ และส่วนเสริมระบบนิเวศ

## เกิดอะไรขึ้นเมื่อคุณรันมัน

1. **เอเจนต์ของคุณเปิด [/init.md](/init.md)** — มันอ่านพรอมต์การออนบอร์ดและระเบียบวิธี ข้อกำหนด และ kit ที่ลิงก์ไปถึง
2. **มันติดตั้ง skill ของ Deep Work Plan** — เครื่องยนต์ที่เหมือนกันในทุก repository ได้แก่ ตัวกำหนดเส้นทางพร้อม sub-skill (create, execute, refine, resume, status, verify, onboard, author, upgrade) สำหรับ Claude Code, Cursor, Codex, Gemini และ Copilot
3. **มันปรับ repository ของคุณ** — โดยให้เหตุผลเกี่ยวกับเทคสแตกจริงของคุณ (ไม่เคยคัดลอกวาง) มันเขียน AGENTS.md, `docs/`, README ต่อโมดูล, kit `.agents/` ที่ผ่านการให้เหตุผล และ `.dwp/` ที่ถูก gitignore repository ของคุณกลายเป็น harness
4. **คุณวางแผนและดำเนินการ** — Deep Work Plan ระยะยาว รันทีละขั้นเทียบกับเกณฑ์การยอมรับและ validation gate ที่ชัดเจน อย่างอิสระเป็นเวลาหลายชั่วโมง
5. **มนุษย์เป็นผู้เริ่มลูป** — เลือกใช้ได้ พร้อมส่วนเสริม Herdr: คุณ — ไม่ใช่ agent — เป็นผู้รัน `herdr-peers autopilot start --loop` ทุกแผนที่เปิดอยู่และมีบันทึก lead จะเดินต่อไปจนจบ และตัวแจ้งเตือนของคุณจะได้รับข่าวเมื่อแผนหยุดชะงัก ถูกบล็อก หรือเสร็จสิ้น

skill คือเครื่องยนต์ที่ใช้ซ้ำได้ ติดตั้งในแบบเดียวกันทุกที่ สิ่งที่ถูกปรับคือ repository ของคุณ กลไกการติดตั้ง (Skills CLI, OpenClaw หรือ git clone) อยู่ในพรอมต์ [/init.md](/init.md) และบน[quickstart](/quickstart)
