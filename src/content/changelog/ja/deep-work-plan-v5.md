本日、Deep Work Plan v5 をリリースします。これは書き直しではありません。実プラン 108 件を直接監査したことを含む、数か月にわたる実運用が、方法論の約束とエージェントの実際の挙動がどこでずれうるかを一つひとつ明らかにしてきた結果です。このリリースの正直な要約はこうです。方法論は以前からこれらすべてを約束していた——今はそれを保証する。v5 より前は、文書に文字どおり従うエージェントでも現実の失敗シナリオに到達する可能性がありました。その一つひとつは、この実運用とフィードバックを通じて特定され、今は閉じられ、実行可能なテストで固定されています。散文を重ねてごまかしたわけではありません。このサイクルでスキルの契約スイートは 132 から 258 テストへ成長し、以下の保証はすべてリリース済みタグに対して実地検証されました。クリーンなリポジトリにインストールし、本来のフローを一通り実行してから、このエントリを書いています。

**検証していない成功を決して主張しない検証器。** 適合性チェックは以前、黙って劣化していました。有能なインタプリタがない場合はすべての検証を飛ばしても「適合」という判定を印字し、フィールド内の太字テキストを欠落フィールドと取り違えることもありました。現在、検証器は実際に検証できないとき、明示的な `UNVERIFIED` 判定で終了します。検証器は自分が確認していない成功を報告しません。ゲートへの信頼こそが提案のすべてであり、自分のチェックを飛ばせるゲートはその信頼の連鎖を断ち切ります。

**Lite プランに対するただ一つの承認契約。**「このプランを開始することが現在のスコープを承認することを意味するのか」という問いに、3 つの面が 3 通りの答えを返していました。エージェントは最も危険な境界でデッドロックしたり、承認なしに実行したりしうる状態でした。v5 はすべての場面でただ一つの契約を定めます。明示的な execute または resume が現在の ready スコープを承認し、作業の前にその承認を記録します。保留中の提案だけでは何も承認されません。中断されたプロモーションは、製品作業の前に回復されます。

**状態を壊さないマルチリポジトリオーケストレーション。** オーケストレーターハブの環境オーバーライドは以前、子リポジトリへ漏れていました。子がハブ自身のフォルダにプラン状態を書き込むこともありました。オーケストレーターのテンプレートは `FAIL` を印字しながら成功で終了し、ステータス文字列を grep するだけの完了チェックは、完了タスク 1 つを完了プランと誤読しえました。現在、ハブのルートはサブリポジトリへ移動する前に保存され、各子は隔離されて自分の `.dwp/` を解決し、すべての失敗分岐はエラーで終了し、完了状態はプランの最上位ステータスから解析され、devcontainer のエントリポイントは何かを削除する前にコピーエラーを伝播します。

**ただ一つのアドオン同意マトリクス。** どのアドオンがデフォルトでインストールされ、どれが提示のみで、どのレビューが必須なのか——以前の面ごとに答えが違いました。v5 は一つのマトリクスを宣言します。AI Diff Reviewer はローカルレビューに必須で、検証済みリリースに固定され、CI レビューは決して自己ブートストラップしない明示的オプトインです。design-system アドオンは UI 作業を検出したとき必ず提示されますが、明示的な受諾でのみインストールされます。dependency-upgrade アドオンはほぼデフォルトの不活性なデリゲータとして届き、正確なスナップショットによるロールバックを備えます。dailybot は承認された場所でのみ報告します。空の diff は完了したレビューとして数えられなくなりました。

**長期プランのための本物の機構。** 108 の実プランの監査は、並列化可能な作業が一般的ながら逐次実行の決定がほとんど宣言されず、ステージゲートが場当たり的な実践に留まっていたことを示しました。v5 は実行決定を常に宣言させます。並列化が妥当でない場合は理由を記録した上で逐次と宣言します。20 タスク以上のプランにはオプションの Stage Gates を加え、Plan Variables はリグアー段階・エビデンス水準・禁止操作で拡張されます。これらはすべて段階的にロードされ、Lite プランを圧迫しません。

**強制される Context、タスクごとの単一目標。** プランは文脈のないタスクリストに崩れ、1 つのタスクが 1 つの緑のゲートの裏に 3 つの目標を束ねることもありました。v5 はプランレベルで Goal と Context のペアを要求し、新規タスク記録ごとにタスクレベルの Context——新しいセッションがそのタスク単独を開始するために必要なもの——を要求します（完了済みの記録は書かれたまま保持）。そして「1 タスク 1 目標」を、崩壊を防ぐガード付きの規範的ルールにします。

**安全なアップグレード経路。** `/dwp-upgrade` は新しいものです。チェックフェーズは読み取り専用で何もインストールしません。アップグレードは明示的な受諾でのみ開始され、上書きの前にローカルでの適応内容が差分表示されます。インストールは正確なタグを対象とし、自分自身を検証します。オンボーディングは新しい init として再実行されます。アップグレードは決して `.dwp/` に触れません。プラン、状態ファイル、ゲート記録、エビデンスは何も移行も書き換えも無効化もされません。

**正直で測定可能なエビデンス。** 効率性の主張は現在、3 つのベースライン——v3.0.0、v4.0.3、最終ツリー——で再測定されます。測定スクリプトはリポジトリにコミット済みです。結果はファイルシステムのバイト数で報告され、私たちが裏付けできないトークン数やコスト数値には決して換算されません。検証できない主張はすべて、評価記録の中でそのように隔離されます。

**バージョン管理され、公開された契約。** 上記の約束はすべて、文章だけでなく他のツールが読めるデータによって裏付けられています。plan-manifest と plan-state のフォーマットは、今や v5 スキーマ系列としてバージョン管理されています——[`plan-manifest/v5.json`](https://deepworkplan.com/schema/plan-manifest/v5.json) と [`plan-state/v5.json`](https://deepworkplan.com/schema/plan-state/v5.json)。これにより、プラン、検証器、またはサードパーティツールは、文書の一段落ではなく、公開された機械可読な契約に対して適合性を確認できます。v5 系列は v2 と比べて形を変えていません。v1 または v2 のスキーマを参照する既存のプランは有効なままであり、決して書き換えられません。

Deep Work Plan v5 は DWP 標準 5.0.0 に従います。[規範仕様](https://deepworkplan.com/spec)を読み、[スキルリポジトリ](https://github.com/DailybotHQ/deepworkplan-skill)を確認するか、[`/init`](https://deepworkplan.com/init) から導入を始めてください。

## 更新 — 2026-09-17 · スキル v5.4.0

v5 系列で最初のポイントリリースです。計画が「実際には確認されていない作業」の上で完了しうる最後の経路をふさぎ、計画自身の証拠がどこに置かれるかを定めました。DWP 標準 5.0.0 は変わりません。これはアドオン契約とドキュメントのリリースであり、スキーマの変更ではありません。

**一度も実行されなかったレビューは、もはやクリーンなレビューと区別がつかないものではありません。** Final Review のセキュリティパスは、レビュアーの不在（指摘として記録）と、呼び出しのエラー（一度警告して続行）をすでに区別していました。上流のレビュアーは三つ目の結末を加えました。開始したのち、指摘を一件も書かずに終了する実行です。名前がないままでは「パスは完了し、何も見つからなかった」に吸収され、行われなかったレビューを根拠に計画を完了させてしまいます。いまやそれ自体が一つの状態です。不完全なレビューとして記録され、変更内容がクリーンである証拠として数えられることはなく、Final Review を終える理由にもなりません。三つの異なる結末があり、そのいずれも「差分が読まれ、問題がなかった」を意味しません。

**計画の証拠は計画のものです。** 標準はすでに、分析記録・skills の台帳・セキュリティレビュー・ゲートのログを計画自身の `analysis_results/` に置いていましたが、その排他性を規則として述べてはいませんでした。そのため、レポートの出力先が既定で作業ディレクトリになっているリポジトリ側の監査ツールが、どのフローにも気づかれないまま計画の証拠をリポジトリのルートに書き出しかねませんでした。仕様はこれを要求するようになりました。フローがその計画について生み出したものはすべてその計画のフォルダへ入り、既定の出力先が作業ディレクトリであるツールには、明示的な出力オプションを与えなければなりません。計画が示す場所にない証拠は、失われた証拠です。これが規則の実務上の理由であり、整理の好みではありません。

**AI Diff Reviewer のピンが v2.3.0 に上がりました。** 必須のローカルレビューが導入するレビュアーは、runner と backend を分離します。そのため同じレビューを互換性のある任意のエンドポイントに対して実行でき、DWP が依存する対象は変わりません。中立性の保証は緩むのではなく、強まります。さらに、チェックサム検証付きインストーラ、推測ではなく実測に基づくコストの既定値、そして未解決の指摘を引き継ぎながら実際の新しい差分をレビューする追加ラウンドを備えます。最後の点には、はっきり述べておくべき契約上の帰結があります。ある指摘が解決済みだとモデル自身が主張しても、それで取り下げられることはありません。取り下げるのはメンテナーです。

**働き方の原則がハーネスとともに届くようになりました。** 同日のうちに公開された `v5.5.0` により、オンボーディングはリポジトリに何があるかだけでなく、そのリポジトリの agent が*どう働くか*も教えるようになります。十の簡潔な行動——成果を引き受ける、尋ねる前に調べる、日常的な判断は自分で下す、判断材料や権限が本当に欠けているときにエスカレーションする、完了を主張する前に検証する、など——を `AGENTS.md` にインラインで記し、入口のファイルしか読まない agent でも見つけられるようにします。これらは依頼の範囲内における既定であって、新たな権限ではありません。ホストの権限、より狭いスコープ、計画のゲート、リポジトリ自身の承認ルールを上書きすることはできません。アップグレードはキーワードではなく意味で調停するため、すでにある同等のルールは書き換えられず残ります。

**AI Diff Reviewer のピンが v2.3.1 に上がりました。** スキル `v5.5.1` が導入するレビュアーは、check、レビュー本文、追跡コメントが一致するものです。本文が `Recommendation: approve` と書いてあっても、check が通った証拠にはなりません——追跡マーカーの Check status ブロックを読んでください。advisory のもとでは、スレッドがすでに折りたたまれた指摘でも、裏付けのある修正で取り下げられるため、止まっていた PR は本物の修正のあとでグリーンになります。
