本日、Deep Work Plan v5 をリリースします。このリリースの正直な要約はこうです。方法論は以前からこれらすべてを約束していた——今はそれを保証する。v5 より前は、文書に文字どおり従うエージェントでも現実の失敗シナリオに到達する可能性がありました。その一つひとつが今は閉じられ、実行可能なテストで固定されています。このサイクルでスキルの契約スイートは 132 から 258 テストへ成長し、以下の保証はすべてリリース済みタグに対して実地検証されました。クリーンなリポジトリにインストールし、本来のフローを一通り実行してから、このエントリを書いています。

**検証していない成功を決して主張しない検証器。** 適合性チェックは以前、黙って劣化していました。有能なインタプリタがない場合はすべての検証を飛ばしても「適合」という判定を印字し、フィールド内の太字テキストを欠落フィールドと取り違えることもありました。現在、検証器は実際に検証できないとき、明示的な `UNVERIFIED` 判定で終了します。検証器は自分が確認していない成功を報告しません。ゲートへの信頼こそが提案のすべてであり、自分のチェックを飛ばせるゲートはその信頼の連鎖を断ち切ります。

**Lite プランに対するただ一つの承認契約。**「このプランを開始することが現在のスコープを承認することを意味するのか」という問いに、3 つの面が 3 通りの答えを返していました。エージェントは最も危険な境界でデッドロックしたり、承認なしに実行したりしうる状態でした。v5 はすべての場面でただ一つの契約を定めます。明示的な execute または resume が現在の ready スコープを承認し、作業の前にその承認を記録します。保留中の提案だけでは何も承認されません。中断されたプロモーションは、製品作業の前に回復されます。

**状態を壊さないマルチリポジトリオーケストレーション。** オーケストレーターハブの環境オーバーライドは以前、子リポジトリへ漏れていました。子がハブ自身のフォルダにプラン状態を書き込むこともありました。オーケストレーターのテンプレートは `FAIL` を印字しながら成功で終了し、ステータス文字列を grep するだけの完了チェックは、完了タスク 1 つを完了プランと誤読しえました。現在、ハブのルートはサブリポジトリへ移動する前に保存され、各子は隔離されて自分の `.dwp/` を解決し、すべての失敗分岐はエラーで終了し、完了状態はプランの最上位ステータスから解析され、devcontainer のエントリポイントは何かを削除する前にコピーエラーを伝播します。

**ただ一つのアドオン同意マトリクス。** どのアドオンがデフォルトでインストールされ、どれが提示のみで、どのレビューが必須なのか——以前の面ごとに答えが違いました。v5 は一つのマトリクスを宣言します。AI Diff Reviewer はローカルレビューに必須で、検証済みリリースに固定され、CI レビューは決して自己ブートストラップしない明示的オプトインです。design-system アドオンは UI 作業を検出したとき必ず提示されますが、明示的な受諾でのみインストールされます。dependency-upgrade アドオンはほぼデフォルトの不活性なデリゲータとして届き、正確なスナップショットによるロールバックを備えます。dailybot は承認された場所でのみ報告します。空の diff は完了したレビューとして数えられなくなりました。

**長期プランのための本物の機構。** 108 の実プランの監査は、並列化可能な作業が一般的ながら逐次実行の決定がほとんど宣言されず、ステージゲートが場当たり的な実践に留まっていたことを示しました。v5 は実行決定を常に宣言させます。並列化が妥当でない場合は理由を記録した上で逐次と宣言します。20 タスク以上のプランにはオプションの Stage Gates を加え、Plan Variables はリグアー段階・エビデンス水準・禁止操作で拡張されます。これらはすべて段階的にロードされ、Lite プランを圧迫しません。

**強制される Context、タスクごとの単一目標。** プランは文脈のないタスクリストに崩れ、1 つのタスクが 1 つの緑のゲートの裏に 3 つの目標を束ねることもありました。v5 はプランレベルで Goal と Context のペアを要求し、新規タスク記録ごとにタスクレベルの Context——新しいセッションがそのタスク単独を開始するために必要なもの——を要求します（完了済みの記録は書かれたまま保持）。そして「1 タスク 1 目標」を、崩壊を防ぐガード付きの規範的ルールにします。

**安全なアップグレード経路。** `/dwp-upgrade` は新しいものです。チェックフェーズは読み取り専用で何もインストールしません。アップグレードは明示的な受諾でのみ開始され、上書きの前にローカルでの適応内容が差分表示されます。インストールは正確なタグを対象とし、自分自身を検証します。オンボーディングは新しい init として再実行されます。アップグレードは決して `.dwp/` に触れません。プラン、状態ファイル、ゲート記録、エビデンスは何も移行も書き換えも無効化もされません。

**正直で測定可能なエビデンス。** 効率性の主張は現在、3 つのベースライン——v3.0.0、v4.0.3、最終ツリー——で再測定されます。測定スクリプトはリポジトリにコミット済みです。結果はファイルシステムのバイト数で報告され、私たちが裏付けできないトークン数やコスト数値には決して換算されません。検証できない主張はすべて、評価記録の中でそのように隔離されます。

Deep Work Plan v5 は DWP 標準 4.0.0 に従います。[規範仕様](https://deepworkplan.com/spec)を読み、[スキルリポジトリ](https://github.com/DailybotHQ/deepworkplan-skill)を確認するか、[`/init`](https://deepworkplan.com/init) から導入を始めてください。
