今天我们发布 Deep Work Plan v5。对这个版本最诚实的概括：这些能力方法论早已承诺——现在它做出了保证。在 v5 之前，一个逐字照着文档执行的智能体仍可能落入真实的失败场景；如今每一个这样的场景都已关闭，并由可执行的测试锁定。本周期内技能的契约测试套件从 132 个增长到 258 个，且下文的每一项保证都是针对已发布的 tag 在实测中验证的——先安装进一个干净的仓库，再跑完它自己的全部流程，然后才写下这篇条目。

**绝不谎报未验证成功的验证器。** 一致性检查过去会静默降级：在没有可用解释器的情况下，它会跳过所有验证，却仍然打印出「符合」的判定；字段内的粗体文本也可能被误判为字段缺失。现在，只要验证器无法真正完成验证，它就会以显式的 `UNVERIFIED` 判定退出。验证器绝不报告自己没有检查过的成功——对验证闸门的信任就是全部主张，而一个能跳过自身检查的闸门会毁掉整条信任链。

**Lite 计划的唯一审批契约。** 对于「启动这个计划是否就批准了它的当前范围」这个问题，三个界面曾给出三种不同答案，智能体恰恰在最危险的边界上可能死锁，或者在未获授权的情况下运行。v5 在所有界面上确立唯一契约：显式的 execute 或 resume 批准当前 ready 的范围，并在做任何工作之前记录该批准；仅一个待审提案本身不授权任何事；被中断的晋升会在任何产品工作运行之前先完成恢复。

**不会破坏状态的多仓库编排。** 编排中心的环境覆盖过去会泄漏到子仓库——子仓库可能把计划状态写进中心自己的目录。编排模板还会打印 `FAIL` 却以成功码退出；一个只对状态字符串做 grep 的完整性检查，会把单个已完成的任务误读为已完成的计划。现在，中心根路径在进入子仓库之前先被保存，每个子仓库隔离地解析自己的 `.dwp/`，每个失败分支都以错误码退出，完整性从计划的顶层状态解析，devcontainer 入口点在任何删除之前先传播复制错误。

**唯一的插件同意矩阵。** 哪个插件默认安装、哪个只是提议、哪种评审是必需的——此前的界面答案不一。v5 给出唯一矩阵：AI Diff Reviewer 为本地评审所必需，固定到经过验证的版本，CI 评审则是显式选择、绝不自行启动；design-system 插件在检测到 UI 工作时必须提议，但只在明确接受时安装；dependency-upgrade 插件以近乎默认、惰性的委托器形式提供，并带有精确快照回滚；dailybot 只在被授权的地方汇报。空 diff 不再计为已完成的评审。

**面向长周期计划的真正机制。** 对 108 个真实计划的审计显示：可并行的工作很常见，但顺序执行的决定几乎从不被声明，阶段闸门也只是零散的个人实践。v5 要求执行决定总是被声明——当并行不成立时，声明为顺序执行并记录原因——为二十个及以上任务的计划增加可选的 Stage Gates，并以严格度层级、证据标准和禁止操作丰富 Plan Variables。所有这些都按需渐进加载，绝不拖累 Lite 计划。

**强制 Context，每任务单一目标。** 计划可能退化为没有上下文的任务清单，一个任务也可能把三个目标打包在一个绿灯之后。v5 要求计划层面的 Goal 与 Context 成对出现，每条新任务记录都有任务级 Context——一个新会话独立启动该任务所需的一切（已完成的记录保持原样），并让「一任务一目标」成为规范规则，附带防止退化的守卫。

**一条安全的升级路径。** `/dwp-upgrade` 是全新的。它的检查阶段只读、不安装任何东西；升级只在明确接受后开始，本地适配在覆盖任何内容之前先做比对并呈现；安装指向精确的 tag 并自我验证；onboarding 以全新 init 重新执行。升级绝不触碰 `.dwp/`——任何计划、状态文件、闸门记录或证据都不会被迁移、改写或失效。

**诚实、可度量的证据。** 效率主张现在在三个基线上重新度量——v3.0.0、v4.0.3 与最终代码树——度量脚本已提交到仓库。结果以文件系统字节数报告，绝不换算成我们无法背书的 token 数或成本数字；每一个无法验证的主张都在评估记录中被明确隔离标注。

Deep Work Plan v5 遵循 DWP 标准 4.0.0。阅读[规范文本](https://deepworkplan.com/spec)，查看[技能仓库](https://github.com/DailybotHQ/deepworkplan-skill)，或从 [`/init`](https://deepworkplan.com/init) 开始采纳。
