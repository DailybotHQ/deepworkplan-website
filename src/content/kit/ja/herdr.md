# Herdr アドオン

[Herdr](https://herdr.dev) は、コーディングエージェントをペインに配置します。あなたのマシン上でも、SSH 経由で到達できるマシン上でも可能です。このアドオンにより、Deep Work Plan はそれらのエージェントを**ピア**として使えるようになります。計画は範囲の限定されたタスクを別のペインのエージェントに渡し、認可されたちょうど一つの返信を受け取り、そのやり取りの記録を残せます。

これは **DWP v7**（`v7.0.0`）の任意のアドオンです。方法論はこれがなくても同じように機能します。アドオンが存在しない、または無効化されている場合、すべてのタスクはこれまでとまったく同じく現在のセッションで実行されます。

## 何を統合するか

このアドオンは薄い統合レイヤーです。実際の作業は **[herdr-peers](https://github.com/DailybotHQ/herdr-peers)** が担います。これは **`v1.0.0`** に固定された独立した MIT のスキル で、Deep Work Plan がなくても役立ちます。Herdr 自体が未定義のまま残している部分を定めています。誰が回答してよいか、回答がマシンをまたいでどう戻ってくるか、二つのエージェントが互いに延々と回答し合うのをどう防ぐか、そして「質問し、回答があった」という記録をどこに保持するか、です。

| 項目 | 値 |
|---|---|
| プロダクト | `DailybotHQ/herdr-peers`、タグ `v1.0.0`、プロトコル 1 |
| レジストリキー | `.dwp/config.json` 内の `herdr` |
| トランスポート | 対話型：Herdr ペイン内のピア |
| 提供するもの | `subagents`、`cancel_children` |
| 必要なもの | 計画コントラクトの `agent_delegation` 付与 |

**`v1.0.0` 以降は安定版です。** 公開インターフェースはセマンティックバージョニングに従います。対象は、CLI の動詞とドキュメント化されたフラグ、終了コード `0`–`7`、ドキュメント化された `HERDR_PEERS_*`、`DWP_PLAN`、`DWP_TASK` 変数、プロトコル 1、そして JSON コントラクト `herdr-peers/lanes-v1`、`herdr-peers/lead-v1` と委任レコードです。これらのいずれかに対する破壊的変更はメジャーバージョンを上げ、ワイヤーフォーマットの変更はさらにプロトコル番号も上げます。`v1.0.0` は `v0.3.3` から動作を一切変えておらず、0.x 系のリリースはサポート対象外になりました。

## インストール

herdr-peers と、それが依存する Herdr 公式のスキル をインストールします。エージェントに回答させたいすべてのマシンにも、このスキル が必要です。

```bash
npx --yes skills add https://github.com/DailybotHQ/herdr-peers/tree/v1.0.0 --skill herdr-peers -g -y
npx --yes skills add https://github.com/herdrdev/herdr/tree/v0.9.3 --skill herdr -g -y
```

要件：Herdr 0.9.1 以降、`bash`、および `python3` 3.9 以降（標準ライブラリのみ）。オンボーディングがこのアドオンを提案し、あなたの回答をアドオンレジストリに記録します。同意なしに有効化されることはありません。

## 計画に追加されるもの

- **ピアへの委任。** コントラクトが `agent_delegation` を付与している v7 の計画では、`execute` が `parallel_safe` なタスク、または読み取り専用の質問を、別のペインのエージェントに渡せます。そのエージェントはこのマシン上でも別のマシン上でも構いません。
- **認可された一つの返信。** リクエストには、ちょうど一つの回答を認可するスタンプが付きます。ピアはヘルパーを通じて一度だけ返信し、その返信にも独自のスタンプが付きます。
- **依拠する前に記録。** すべての委任は、返信が使われる前に計画の `analysis_results/delegations.ndjson` に書き込まれ、v7 の `delegation` ジャーナルイベントに対応します。
- **結果は確認されるまで主張のまま。** ピアの回答は、計画自身のゲートランナーが観測するまで `asserted` な証拠です。それだけでタスクを完了させることはありません。

## 安全モデル

| ルール | 意味 |
|---|---|
| 付与が先 | 委任は、計画コントラクトが `agent_delegation` を付与している場合にのみ実行されます。 |
| 深さの上限 1 | `depth=1` または `reply-to=` のスタンプが付いたメッセージには決して回答せず、委任先がさらに委任することもありません。 |
| ファンアウト上限 | デフォルトでは、呼び出し元ごとに最大四つのピアまで。 |
| 指示ではなくデータ | 返信が、受信側にもともとなかった権限を与えることはありません。 |
| パスごとに書き手は一人 | 書き込みを行うピアは、自身の git worktree の中で作業します。 |

herdr-peers は送信者を認証しません。スタンプ内の `from=` フィールドは主張にすぎません。その緩和策が `HERDR_PEERS_SCOPE` 許可リストで、ピアが受け入れるワークスペースとマシンを制限します。

## コンテナとホスト

devcontainer-kit `v1.0.0` 上の [devcontainer](/kit/devcontainer) アドオンを使うと、すべての dck コンテナが herdr-peers を同梱し、`dck up` の時点でメッシュに参加します。そのエージェントは、ホスト上、他のコンテナ内、ホストの他のループバックコンテナ内のエージェントに問い合わせ、返信を受け取れます。`dck setup` はホストに検証済みの herdr-peers をインストールするため、ホストのエージェントも返信できます。ホストリスナーと、他のコンテナを受け入れる追加の鍵は、キットのホストプロファイルであなたが決めるものであり、このアドオンがそれらを設定することはありません。herdr-peers (`v0.2.3`) 以降、各マシンは自身の状態（`$XDG_STATE_HOME/herdr-peers/<server>/`）を持つため、ホストとコンテナが共有するチェックアウトでも互いの記録が混ざらなくなりました。また devcontainer-kit (`v0.3.3`) 以降はコンテナ自身が `HERDR_PEERS_SELF` をエクスポートするため、コンテナ内の Codex エージェントは手作業なしで他のマシンに到達できます。

## Herdr か agentkit か

どちらのアドオンも同じ委任インターフェース（`launch`、`observe`、`collect`、`cancel`）を、異なるトランスポートで実装しています。

| 状況 | 使うもの |
|---|---|
| 出力が宣言された、範囲の限定された `parallel_safe` なタスク | [agentkit](/kit/agentkit)（worktree 内でヘッドレスに `ak run`） |
| タスクに対話が必要、長時間実行される、または別のマシン上にある | Herdr（ペイン内のピア） |

多数のレーン（ホスト、コンテナ、別マシン上のペインで、それぞれが自分のアカウントを使う）を同時に動かすリードには、`herdr-peers lanes` がすべてのレーンを状態とともに一覧表示し、`herdr-peers status <pane>` がブロック中のレーンのいる画面を分類します。また、すべての委任記録には、その作業を担ったアカウントとベンダーが記されます。[多数のエージェントを動かす](/methodology/06-orchestration)を参照してください。

**Codex のレーンは自分のペインを指定します。** Codex は、そのアカウントの全セッションが共有するバックグラウンドサーバーからレーンのコマンドを実行するため、引き継いだペイン ID が別のレーンのものである場合があります。Codex のレーンは、リードの指示にある自分のペインを、すべての herdr-peers コマンド（`ask`, `reply`, `notify`, `check`, `wait`, `lanes`, `cancel`）で `--pane <pane>` として渡します。

## 通知とリーダーシップ

herdr-peers (`v0.3.2`) は、スウォームがリードを失っても続けられるようにする機能を加えます（[スウォームの自律性](/ja/methodology/07-swarm-autonomy)）。

- **通知。** `herdr-peers notify <addr|lead> "<text>" --pane <pane>` は、`reply=no` のスタンプが付いた一方向のメッセージを送ります。受け手の `check` はそれを通知として分類し、データとして記録し、決して返信しません。通知はファンアウトの枠を消費せず、ask が開いている間でも送れます。ハンドオフの告知、リードの交代、リリースの一斉通知に使います。
- **計画ごとのリードレコード。** `herdr-peers lead claim --plan <P> --succession <A,B> --lanes <A,B>` は、あるエージェントを一つの計画のリードにします。`lead show` はそのレコードを表示します（スキーマ `herdr-peers/lead-v1`：計画、リード、エポック、継承順、レーン、更新時刻）。`lead handover <addr> --plan <P>` はリーダーシップを引き渡し、`lead takeover --plan <P>` はリードがいなくなったときに最初に到達できる代理がそれを引き継ぐようにし、`lead release --plan <P>` はそれを終えます。変更のたびにエポックが上がり、すべてのレーンに通知されます。レーンを起動する前に計画を claim します。`lead` はレコードが存在して初めて解決されます。`v0.3.2` からレコードは claim したリポジトリをローカルに保持し、別のリポジトリからの同じ計画 id の claim を拒否します。その計画は `--plan <repo>/<id>` と指定します。
- **フェンシング。** レーンがリードの通知を受け入れるのは、自分に指示を出したエージェント（最初の claim）、次のエポックの現リード（handover）、または次のエポックで最初に到達できる継承順のエントリ（takeover）からだけです。それ以外は記録されて無視され、戻ってきたリードはより高いエポックを見ると身を引きます。
- **`lead` アドレス。** `ask lead …` と `notify lead …` は `--plan`（なければ `$DWP_PLAN`）の現リードに解決されるため、レーンへの指示にリードのペインを固定で書く必要はありません。
- **`usage_limit` 画面。** `status` と `lanes` は、CLI の使用量上限のメッセージを画面クラス `usage_limit` として認識し、その次の手順はハンドオフです。この画面にキーを送ることは決してありません。`lanes --json` は、計画、そのリード、エポック、各レーンが最後に報告したキャパシティを加えます。

レーン同士も、情報や調整（インターフェース、フラグ名、ブランチの状態）について互いに尋ねられますが、作業を割り当てるのはリードだけです。深さは一、ファンアウトの上限も引き続き適用されます。`v0.2.x` には通知もリードレコードもありません。レーンは指示に書かれたリードのアドレスに尋ね、リードの交代は開発者が中継します。

## 補足

任意であり、必須となることはありません。リポジトリはオプションアドオンがゼロでも完全に適合し、このアドオンに依存するフローはありません。二つのペインによるマシンをまたいだ往復は、模擬した Herdr に対するテストでカバーされています。初回の実行は人が監督する形で計画してください。
