# dwp-verify

リポジトリと計画の適合性を客観的に確認します。読み取り専用です。

<CmdVerify lang="ja" class="not-prose my-8" />

## 何をするか

`dwp-verify` は、リポジトリが AI-first（DeepWorkPlan に適合）か、そしてその計画がよく形成されているかを機械的に確認し、合否を報告します。何も変更しません。

## 使い方

```
/dwp-verify            # verify the repository
/dwp-verify plan auth  # also verify a specific plan
/dwp-verify all        # repository + every plan
```

## 振る舞い

1. リポジトリを確認する。実際に実行可能なコマンドを備えた `AGENTS.md`、`CLAUDE.md` の解決、`docs/` のカテゴリ、ディスクと一致する `.agents/` のカタログ、薄い `dwp-*` 委譲、gitignore された `.dwp/` と `tmp/`、解決可能なスキル。
2. 計画を確認する（求められたとき)。すべてのタスクが受け入れ基準と検証ゲートを備え、進捗が永続化され、記録された Final Review が（そのセキュリティパスを含めて）存在し、タスクが目標へと改めて立ち返っているか。
3. **CONFORMANT** または **NOT CONFORMANT** を、各失敗を列挙して報告する。
4. 不足を Deep Work Plan として捕捉することを提案する。決して黙って修正しない。

**世代ごとの計画検証。** リポジトリの来歴チェッカーは現在の DWP 標準 7.0.0 を受け入れますが、計画の検証は世代ごとに行います。v6 または v7 の計画は manifest の contract ポインター、`contract.json`、または `contracts/` のリビジョンチェーンで識別され、`conformance.sh --plan` によって自身の記録に照らして読み取り専用で判定されます。判定内容は、すべての contract リビジョンが有効であること、manifest が contract の世代と対応していること、journal が途切れておらず有効であること、承認が現行の contract を引用していること、`state.json` が journal の投影と一致していることです（古い snapshot は助言扱いで再生成され、手作業で編集されることはありません）。v5 のライフサイクル検査は v5 以前の計画にのみ適用され、v5 の最終処理は v6 または v7 の計画を拒否します。各世代は共存し、検証時にいずれも移行されません。
