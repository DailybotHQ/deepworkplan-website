# AI Diff Reviewer アドオン

すべての Deep Work Plan は同じ形で幕を閉じます。作業を完了と呼べるようになる前に、計画の蓄積された変更全体を読み通す、必須の **Final Review** です。その中のセキュリティパスは、何かを捕まえられる最後の地点にあたります。助けがなければ、その時点での唯一の読み手は、そのコードを書いたのと同じ agent です。

このアドオンは、その diff に二人目の読み手を置きます。**[AI Diff Reviewer](https://github.com/DailybotHQ/ai-diff-reviewer)**（マーケットプレイスでの掲載名は "AI Diff Reviewer"、現在は **v2.3.0**）をセキュリティパスに組み込み、散文ではなく構造化された結果を返させます。判定、指摘の一覧表、そして各指摘の深刻度です。`critical` の指摘は、修正されるか明示的に受け入れられるまで完了をブロックします。このレビューはコメントではなく、ゲートです。

標準 2.3.0 以降、このローカルレビューは**ベースラインの一部であり、追加オプションではありません**。オンボーディングがそれを導入し、すべての Final Review がそれを実行します。任意のままなのは CI サーフェスです。つまり Flow B であり、そこでは同じレビューが GitHub Action を通じてプルリクエストをゲートします。

これを安心して採用できるようにしている境界は、意図的に狭く引かれています。レビュアーは MIT ライセンスでタグ固定された skill であり、あなたがすでに動かしている coding agent が実行します。そのため、Deep Work Plan のどのフローも、商用サービス・CI プロバイダー・シークレットに依存しません。**Flow A**（ローカルのみ）は、オンボーディングを終えたすべてのリポジトリが受け取るものです。**Flow B** は明示的に提案されるものであり、求められないまま導入されることはありません。開発者はレビュアーそのものを断ることもできます。その拒否は宣言された例外として記録され、`verify` は導入されるまでその点についてリポジトリを非適合として報告します。

## 使用するタイミング

| シグナル | アクション |
|--------|--------|
| オンボーディングされたすべてのリポジトリ | オンボーディングの**フェーズ 7a** で **Flow A をインストール**（vendored スキル + `.review/extension.md`）。対象を絞ったハーネスアップグレードが、より前にオンボーディングされたリポジトリにそれを追加 |
| チームが構造化された検出結果を持つ CI PR マージゲートを望んでいる | **Flow B を提案** — 明示的なオプトインであり、決してデフォルトではない |
| 個人または実験的なリポジトリ；ローカルレビューで十分 | **Flow A にとどまる** — ベースラインは完全 |

## 2 つの採用フロー

| フロー | 得られるもの |
|------|----------------|
| **A — ローカルのみ（ベースライン）** | vendored スキル + 必須の `.review/extension.md`（`generate-extension` 経由）。すべての Final Review のセキュリティパスの中でローカルレビューを実行。GitHub Actions ワークフローなし。 |
| **B — デュアルサーフェス** | Flow A に加え、`setup` が `.github/workflows/pr-review.yml`（Action `@v2`）を作成。ローカルと CI で同じ拡張ファイルを使用。CI が検出結果を投稿した後、オプションで `apply-review` コンパニオンを使用可能。 |

ローカルレビューの検出には、次のいずれかの場所に**スキル + 拡張ファイル**が必要です：`.review/extension.md`、`.github/ai-diff-reviewer/extension.md`、または `.github/ai-pr-reviewer/extension.md`。スキルだけでは不十分です。

## このアドオンが接続する内容（意図的に限定）

DWP アドオンはレビュアーを**再発明しません**。インストール、方法論、CI ウィザード、拡張オーサリング、PR 草案作成、CI 後のウォークスルーを、上流スキルの 5 つのサブスキル（親デフォルトフロー、`generate-extension`、`setup`、`open-pr`、`apply-review`）に委任します。

### 必須のローカルレビュー

`create` はすべての Final Review のセキュリティパスにローカルレビューステップを追加し、`execute` がそれを実行します。出力はプランローカルの `analysis_results/SECURITY_REVIEW.md`（プラン自身のフォルダー内であり、リポジトリルートではない）の `## AI Diff Reviewer local review` の下に追記されます。

- **レビュアーの欠落 — 記録され、黙ってスキップされない：** スキルまたは拡張の欠落は `local reviewer not installed` の検出結果になります。Final Review はスキルが存在する場合にローカルパスを実行し、存在しない場合は検出結果を完了レポートに持ち越します — インストールはオンボーディングの同意または明示的なアドオン呼び出しに属し、決してサプライズブートストラップではありません。
- **ソフト失敗（呼び出しのみ）：** 開始できたにもかかわらずエラーになったレビュー → 一度警告し、記録し、続行；このミスでタスクを失敗させません。
- **完了したパスの後のゲート：** `critical` の検出結果は修正または明示的に承認されるまで Final Review の完了をブロックし続けます。`warning` / `info` は記録されますがブロックしません。
- **Flow A に CI シークレットは不要。** 未設定の `CURSOR_API_KEY` はローカルパスを抑制してはなりません。

### Flow B CI ゲート（オプション）

Action `DailybotHQ/ai-diff-reviewer@v2`、通常ラベルゲート（`ready`）、ブランチ保護用の安定した名前の **AI review gate** ジョブ、オプションのスキップラベル `skip-review-label: skip-ai-review`。共有の `prompt.md` + 拡張で方法論と深刻度を整合；反復認識レビューでは、CI の 2 回目以降のラウンドが短くなる場合がありますが、ローカルパスは完全に保たれます。

### オプションの `apply-review` コンパニオン

CI がレビューを投稿した後、開発者は `execute` 中に `apply-review` を呼び出して、検出結果を 1 つずつ（適用 / 延期 / スキップ）同意のもとで確認できます。デフォルトで読み取り専用；プランタスクファイルとしては使用しない（必須の最終タスク順序を壊す）。

## v2.0.1 からの変更点

v2.0.1 から v2.3.0 までの間に、アップストリームで 3 つのリリースがありました。いずれも本アドオンがレビュアーを接続する方法は変えていません（Flow A、三つの検出パス、ブロッキング契約はそのままです）が、導入者が得られるものは変わります。

| 変更 | DWP リポジトリにとっての意味 |
|------|------------------------------|
| **runner と backend が別々の入力になった**（v2.1.0） | `provider` は *runner*（レビューループを実行する主体）を指定し、新しい `api-base` は *backend*（モデルの所在）を指定します。`api-base` が空の場合は v2.0.x とバイト単位で同一であり、既存のインストールの挙動は従来とまったく変わりません。 |
| **runner が 2 つ追加**（v2.1.0） | `openai`（インプロセス、インストール不要）と `grok`（CLI）が既存の選択肢に加わりました。 |
| **コストは一語のティアで決まり、その既定値は実測に基づく**（v2.1.0、v2.3.0） | コストはティアのキーワードと絞り込まれた diff によって制御され、レビューごとに報告されます。xAI では `balanced` と `economy` がいずれも `grok-4.5` に、`deep` が `grok-4.6` に解決されます。 |
| **追加ラウンドは実際の新しい diff をレビューする**（v2.1.0、v2.2.0） | 未解決の指摘は次のラウンドへ引き継がれます。`prior-findings-resolution` の既定は `advisory` です。モデルによる「解決済み」の判定は報告されますが、メンテナーがスレッドを解決するまで、その指摘はブロックし続けます。 |
| **不完全なレビューが「緑」になることはない**（v2.2.0） | 指摘を書き出さずに終了した実行は、明示的な不完全レビューとして投稿されます。ブロッキングを伴う厳格度ではすべて失敗となり、レビュー済みラベルは付与されず、空のラウンドによって未解決の指摘が取り下げられることもありません。 |
| **チェックサム検証付きインストーラ**（v2.2.0） | `cursor-installer-sha256` と `grok-installer-sha256` は、ベンダー成果物のハッシュが設定された固定値と異なる場合、その実行を拒否します。 |

このうち二点は、方法論にとって特に重要です。

**不完全レビューのゲートは、セキュリティパスの実在の穴をふさぎます。** Final Review が、実施されなかったレビューを根拠に完了できてはなりません。v2.2.0 より前は、指摘を出さずに終了した runner はクリーンな合格と区別がつきませんでした。現在は名前の付いた非グリーンの状態であるため、「指摘なし」はレビュアーが確認したうえで何も見つからなかったことを意味し、まったく確認していないことではありません。

**`economy` は意図的に安価ではありません。** アップストリームの 2026-09-16 のベンチマークでは、`grok-4.3` は既知の欠陥 5 件のうち 0 件しか検出せず（レビューせずに承認します）、一方 `grok-4.5` は 3 件を検出して `grok-4.6` と並び、誤検出はゼロ、コストは同等で所要時間は 4 分の 1 でした。レビューを実際に行う、より安価な xAI モデルが存在しないため、`economy` は何も見つけないティアになるのではなく、`balanced` と同じモデルに解決されます。そのため CLI 経由の xAI 経路のコストは、1 回のレビューあたり約 \$0.07 から約 \$0.40〜0.75 に上がります。従来の挙動を保つには `model: grok-4.3` を明示的に固定できます。これらの数値はアップストリームが公開した測定値であり、Deep Work Plan 自身のものではありません。

## 動作

- **Flow A がベースライン；Flow B は確認して決めるもので、決して推測しない。** 未要求のワークフローをインストールすることは、Flow A にとどまるよりも大きなフットプリントになります。
- **調整する、上書きしない。** 既存のスキル、拡張、または `pr-review.yml` は保持；ギャップのみ埋める。
- **認証は延期。** CI のプロバイダーシークレットはメンテナーが設定；このアドオンは認証情報を保存しません。
- **ベンダー中立。** 商用サービス、CI プロバイダー、シークレットが要求されることは決してありません。プロバイダーに触れるのは CI サーフェスだけです。

## 注意事項

標準 2.3.0 以降、ローカルレビューは必須。CI サーフェスはオプション。上流スキル：[DailybotHQ/ai-diff-reviewer](https://github.com/DailybotHQ/ai-diff-reviewer)。スペックページ：[Add-ons](/spec/addons)。
