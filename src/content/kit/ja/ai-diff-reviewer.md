# AI Diff Reviewer アドオン

すべての Deep Work Plan は同じ形で幕を閉じます。作業を完了と呼べるようになる前に、計画の蓄積された変更全体を読み通す、必須の **Final Review** です。その中のセキュリティパスは、何かを捕まえられる最後の地点にあたります。助けがなければ、その時点での唯一の読み手は、そのコードを書いたのと同じ agent です。

このアドオンは、その diff に二人目の読み手を置きます。**[AI Diff Reviewer](https://github.com/DailybotHQ/ai-diff-reviewer)**（マーケットプレイスでの掲載名は "AI Diff Reviewer"、現在のリリースは **v3.1.1**）をセキュリティパスに組み込み、散文ではなく構造化された結果を返させます。判定、指摘の一覧表、そして各指摘の深刻度です。v3 以降、`critical` の指摘とは、アドオンのベリファイアが第二の コード根拠型モデル呼び出しでそれを確認したことを意味します。完了をブロックするのは、検証済みクリティカルだけです。修正されるか明示的に受け入れられるまで。このレビューはコメントではなく、ゲートです。

標準 2.3.0 以降、このローカルレビューは**ベースラインの一部であり、追加オプションではありません**。オンボーディングがそれを導入し、すべての Final Review がそれを実行します。任意のままなのは CI サーフェスです。つまり Flow B であり、そこでは同じレビューが GitHub Action を通じてプルリクエストをゲートします。

これを安心して採用できるようにしている境界は、意図的に狭く引かれています。レビュアーは MIT ライセンスでタグ固定された skill であり、あなたがすでに動かしている coding agent が実行します。そのため、Deep Work Plan のどのフローも、商用サービス・CI プロバイダー・シークレットに依存しません。**Flow A**（ローカルのみ）は、オンボーディングを終えたすべてのリポジトリが受け取るものです。**Flow B** は明示的に提案されるものであり、求められないまま導入されることはありません。開発者はレビュアーそのものを断ることもできます。その拒否は宣言された例外として記録され、`verify` は導入されるまでその点についてリポジトリを非適合として報告します。

## 使用するタイミング

| シグナル | アクション |
|--------|--------|
| オンボーディングされたすべてのリポジトリ | オンボーディングの**フェーズ 7a** で **Flow A をインストール**（vendored スキル + `.review/extension.md`）。対象を絞ったハーネスアップグレードが、より前にオンボーディングされたリポジトリにそれを追加 |
| チームが構造化された指摘を持つ CI PR マージゲートを望んでいる | **Flow B を提案** — 明示的なオプトインであり、決してデフォルトではない |
| 個人または実験的なリポジトリ；ローカルレビューで十分 | **Flow A にとどまる** — ベースラインは完全 |

## 2 つの採用フロー

| フロー | 得られるもの |
|------|----------------|
| **A — ローカルのみ（ベースライン）** | vendored スキル + 必須の `.review/extension.md`（`generate-extension` 経由）。すべての Final Review のセキュリティパスの中でローカルレビューを実行。GitHub Actions ワークフローなし。 |
| **B — デュアルサーフェス** | Flow A に加え、`setup` がレビューワークフロー（Action `@v3`）を作成。ローカルと CI で同じ拡張ファイルを使用。CI が指摘を投稿した後、オプションで `apply-review` と `address-review` コンパニオンを使用可能。 |

ローカルレビューの検出には、次のいずれかの場所に**スキル + 拡張ファイル**が必要です：`.review/extension.md`、`.github/ai-diff-reviewer/extension.md`、または `.github/ai-pr-reviewer/extension.md`。スキルだけでは不十分です。

## このアドオンが接続する内容（意図的に限定）

DWP アドオンはレビュアーを**再発明しません**。インストール、方法論、CI ウィザード、拡張オーサリング、PR 草案作成、CI 後のレビューループを、上流スキルの 6 つのサブスキル（親デフォルトフロー、`generate-extension`、`setup`、`open-pr`、`apply-review`、`address-review`）に委任します。

### 必須のローカルレビュー

`create` はすべての Final Review のセキュリティパスにローカルレビューステップを追加し、`execute` がそれを実行します。出力はプランローカルの `analysis_results/SECURITY_REVIEW.md`（プラン自身のフォルダー内であり、リポジトリルートではない）の `## AI Diff Reviewer local review` の下に追記されます。

- **レビュアーの欠落 — 記録され、黙ってスキップされない：** スキルまたは拡張の欠落は `local reviewer not installed` の検出結果になります。Final Review はスキルが存在する場合にローカルパスを実行し、存在しない場合は検出結果を完了レポートに持ち越します — インストールはオンボーディングの同意または明示的なアドオン呼び出しに属し、決してサプライズブートストラップではありません。
- **ソフト失敗（呼び出しのみ）：** 開始できたにもかかわらずエラーになったレビュー → 一度警告し、記録し、続行；このミスでタスクを失敗させません。
- **完了したパスの後のゲート：** **検証済みクリティカル**は、修正または明示的に承認されるまで Final Review の完了をブロックします（BC-07）。未検証のクリティカル主張は注釈付き警告として現れます — 目に見え、ブロックはしない。`strict-unverified-criticals: true` が主張ベースのゲートを復旧させる場合を除きます。ターン上限（`incomplete`）や壁時計（`timeout`）を使い切ったレビューは、ブロッキングを伴う厳格度の下でクリーンなパスではありません（BC-04）。`warning` / `info` は記録されますがブロックしません。
- **Flow A に CI シークレットは不要。** 未設定のプロバイダーキーがローカルパスを抑制してはなりません。

### Flow B CI ゲート（オプション）

Action `DailybotHQ/ai-diff-reviewer@v3`、通常ラベルゲート（`ready`）、ブランチ保護用の安定した名前の **AI review gate** ジョブ、オプションのスキップラベル `skip-review-label: skip-ai-review`。v3 以降、レビュー予算は変更の決定論的リスク階層に従います — `budget-profile: auto` の下で `low` から `critical` まで 8/20/30/40 ターン（`fixed` は移行期に v3 以前の定数を復旧）— そしてコードを一切変更しないプッシュは、ベリファイアのみのラウンドを実行します。共有の `prompt.md` + 拡張で方法論と深刻度を整合；ローカルと CI は方法論として同一であり、反復認識レビューでは CI の 2 回目以降のラウンドが短くなる場合がありますが、ローカルパスは完全に保たれます。

### オプションのレビューコンパニオン

CI がレビューを投稿した後、開発者が呼び出せる 2 つのサブスキルがループを閉じます。どちらも決してプランタスクファイルにはなりません（必須の最終タスク順序を壊すため）。

- `apply-review` は、同意のもとで指摘を 1 つずつ（適用 / 延期 / スキップ）確認できます。デフォルトで読み取り専用；コミットもプッシュもしません。
- `address-review`（v3.1.1 で新登場）は 1 回呼び出しのループです。ブランチのオープンな PR を見つけ、レビューが現在の head をカバーしているか確認し、適用/延期/スキップの計画とともに指摘を提示し、ひとつの「はい」ののちに — 適用し、小さな Conventional Commits バッチでコミットし、プッシュし、そのリポジトリがレビュアーをトリガーする方法に応じて再武装します（ラベルゲート → ラベルを切り替え；プッシュトリガー → 新しい実行を確認）。`apply-review` とは異なり、コミットとプッシュを行います。それがこのループの存在意義です。集約型 ensemble レビューでは、集約ドキュメントと `ai-pr-reviewer-aggregate` マーカーを読みます。
- 機械向けの経路は構造化出力であり、レビュー本文ではありません。`review-output/3.0` ドキュメント（`.aiprr/review-output.json`、`structured-output-path` と `structured-output-sha256` 出力で特定）は、実行レコード、証拠と検証付きの指摘、却下された指摘、そしてゲートを運びます。レビュー本文に `Recommendation: approve` と書いてあっても、チェックが通った証拠にはなりません。先にトラッキングマーカーの Highest severity / Strictness gate / Check status ブロックを読んでください。

## v3 での変更点

2026-09-24 に 3 つのリリースがあり（v3.0.0、v3.0.1、v3.1.0）、v3.1.1 が `address-review` サブスキルとともに続きました。いずれも本アドオンがレビュアーを接続する方法は変えていません（Flow A、三つの検出パス、「ブロックしない」の階段はそのままです）が、導入者が得られるものは変わります。

| 変更 | DWP リポジトリにとっての意味 |
|------|------------------------------|
| **`critical` は検証されたときだけ公開される**（v3.0.0） | 主張された各クリティカル — 警告の 30 % サンプルも追加 — が、別のモデル呼び出しによる第二の短いコード根拠型チェックを受けます（検証済み指摘あたり約 3 k トークン、10 秒、\$0.009）。検証済みクリティカルがセキュリティパスにゲートをかけます。却下された主張は注釈付き警告として可視性を保ち、構造化出力に列挙され、インラインで投稿されることはありません。 |
| **予算はリスク階層に従う**（v3.0.0） | `budget-profile: auto` の下、変更インベントリから導かれた `low` から `critical` までの 8/20/30/40 ターン。コードを変更しないプッシュは −93 % のコストでベリファイアのみのラウンドを実行します。`budget-profile: fixed` は v3 以前の 30 ターンの定数を復旧します。 |
| **未完了のレビューは赤**（v3.0.0） | `incomplete`（ターン上限）と `timeout`（壁時計）は部分的な指摘を投稿し、ブロッキングを伴う厳格度で失敗します — 「指摘なし」は今や、常にレビュアーが確認したうえで何も見つからなかったことを意味します。 |
| **構造化出力が機械向けの経路**（v3.0.0） | `review-output/3.0` ドキュメントは、実行レコード、変更インベントリ、型付き証拠と検証付きの指摘、却下された指摘、そしてゲートを運びます。レビュー本文をこそ抜き取るのではなく、このドキュメントを読んでください。 |
| **6 つのサブスキル**（v3.1.1） | `address-review` がルーターに加わります。1 回の呼び出しで適用、コミット、プッシュ、レビュアーの再武装を行います。 |
| **オプションの ensemble**（v3.0.0） | 読み取り専用の `mode: emit` レグと 1 つの `aggregate` ジョブが、統合された指摘を一度だけ検証し、単一のレビューを投稿します。 |
| **`@v2` は動き続ける** | v2 ラインは `release/v2` で凍結され、6 か月間のセキュリティとカタログのメンテナンスを受けます。v3 は推奨であって、強制移行では決してありません。 |

このうち二点は、方法論にとって特に重要です。

**検証済みクリティカルのゲートは、セキュリティパスを強化します。** v3 より前は、モデルが `critical` を自由に主張でき、ゲートはその主張に従っていました。現在、Final Review でのクリティカルな指摘は、第二のモデル呼び出しがコードに対してそれを確認したことを意味し、リリースキャンペーンがその差を測定しました。10 のキャンペーンにわたる 771 回の有料評価実行、総額約 \$83、クリティカル階層は 63/63 のリコールと裁定付き適合率 1.0 に到達し、増分ラウンドは入力トークンを 62〜76 % 削減しました。これらの数値はアップストリームが公開した測定値であり、Deep Work Plan 自身のものではありません。

**`economy` は意図的に安価ではありません。** アップストリームの 2026-09-16 のベンチマークでは、`grok-4.3` は既知の欠陥 5 件のうち 0 件しか検出せず（レビューせずに承認します）、一方 `grok-4.5` は 3 件を検出して `grok-4.6` と並び、誤検出はゼロ、コストは同等で所要時間は 4 分の 1 でした。レビューを実際に行う、より安価な xAI モデルが存在しないため、`economy` は何も見つけないティアになるのではなく、`balanced` と同じモデルに解決されます。grok ランナーでは、コストをスケールさせるのはモデルの選択ではなく、リスク階層のターン予算です。そのため CLI 経由の xAI 経路のコストは、1 回のレビューあたり約 \$0.07 から約 \$0.40〜0.75 に上がります。v3.0 プロンプト以降、63 回実行の再測定により `grok-4.3` は 5 件中 0 件から 83 % の再現率、誤検出ゼロ、コスト約 31 % 減まで改善しました — ただし指摘ファイルの書き出しに失敗する頻度は依然 `grok-4.5` の約 3 倍であるため、`grok-4.5` がデフォルトのままであり、`model: grok-4.3` は明示的な、受け入れ済みのトレードオフの選択のままです。これらの数値はアップストリームが公開した測定値であり、Deep Work Plan 自身のものではありません。

## 動作

- **Flow A がベースライン；Flow B は確認して決めるもので、決して推測しない。** 未要求のワークフローをインストールすることは、Flow A にとどまるよりも大きなフットプリントになります。
- **調整する、上書きしない。** 既存のスキル、拡張、またはレビューワークフローは保持；ギャップのみ埋める。
- **認証は延期。** CI のプロバイダーシークレットはメンテナーが設定；このアドオンは認証情報を保存しません。
- **ベンダー中立。** 商用サービス、CI プロバイダー、シークレットが要求されることは決してありません。プロバイダーに触れるのは CI サーフェスだけです。
