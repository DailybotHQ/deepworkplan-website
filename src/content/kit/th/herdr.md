# แอดออน Herdr

[Herdr](https://herdr.dev) วาง coding agent ไว้ใน pane ทั้งบนเครื่องของคุณและบนเครื่องที่มันเข้าถึงได้ผ่าน SSH แอดออนนี้ทำให้ Deep Work Plan ใช้เอเจนต์เหล่านั้นเป็น **peer** ได้ แผนสามารถส่งงานที่มีขอบเขตชัดเจนให้เอเจนต์ใน pane อื่น รับคำตอบที่ได้รับอนุญาตเพียงหนึ่งเดียว และเก็บบันทึกของการแลกเปลี่ยนนั้นไว้

นี่คือแอดออนแบบเลือกใช้ของ **DWP v7** (`v7.0.0`) ระเบียบวิธีทำงานเหมือนเดิมทุกประการเมื่อไม่มีแอดออนนี้ หากไม่มีแอดออนหรือปิดใช้งานไว้ ทุกงานจะรันในเซสชันปัจจุบันเหมือนที่เคยเป็นมาทุกประการ

## สิ่งที่ผสานรวมเข้ามา

แอดออนนี้เป็นเพียงตัวเชื่อมบาง ๆ งานจริงทำโดย **[herdr-peers](https://github.com/DailybotHQ/herdr-peers)** ซึ่งเป็น skill แบบ MIT ที่แยกเป็นอิสระ ตรึงไว้ที่ **`v0.1.0`** และใช้งานได้แม้ไม่มี Deep Work Plan มันกำหนดสิ่งที่ Herdr เองเปิดทิ้งไว้ ได้แก่ ใครมีสิทธิ์ตอบ คำตอบเดินทางกลับข้ามเครื่องได้อย่างไร เอเจนต์สองตัวจะหลีกเลี่ยงการตอบกันไปมาไม่รู้จบได้อย่างไร และบันทึกว่า "ฉันถามแล้ว มันตอบแล้ว" เก็บไว้ที่ใด

| รายการ | ค่า |
|---|---|
| ผลิตภัณฑ์ | `DailybotHQ/herdr-peers` แท็ก `v0.1.0` โปรโตคอล 1 |
| คีย์ใน registry | `herdr` ใน `.dwp/config.json` |
| ช่องทางการส่ง | แบบโต้ตอบ: peer ใน pane ของ Herdr |
| สิ่งที่มอบให้ | `subagents`, `cancel_children` |
| สิ่งที่ต้องมี | การอนุญาต `agent_delegation` ในสัญญาของแผน |

## การติดตั้ง

ติดตั้ง herdr-peers และ skill ทางการของ Herdr ที่มันต้องพึ่งพา ทุกเครื่องที่ต้องการให้เอเจนต์ของตนตอบได้ก็ต้องมี skill นี้ด้วย

```bash
npx --yes skills add DailybotHQ/herdr-peers@v0.1.0 --skill herdr-peers -g -y
npx --yes skills add herdrdev/herdr@v0.9.3 --skill herdr -g -y
```

ข้อกำหนด: Herdr 0.9.1 ขึ้นไป `bash` และ `python3` 3.9 ขึ้นไป (ใช้เฉพาะไลบรารีมาตรฐาน) ขั้นตอน onboarding จะเสนอแอดออนนี้และบันทึกคำตอบของคุณไว้ใน registry ของแอดออน โดยจะไม่มีการเปิดใช้งานเลยหากไม่ได้รับความยินยอม

## สิ่งที่เพิ่มให้กับแผน

- **การมอบหมายงานให้ peer** ในแผน v7 ที่สัญญาให้สิทธิ์ `agent_delegation` คำสั่ง `execute` สามารถส่งงาน `parallel_safe` หรือคำถามแบบอ่านอย่างเดียว ให้เอเจนต์ใน pane อื่นได้ ไม่ว่าจะอยู่บนเครื่องนี้หรือเครื่องอื่น
- **คำตอบเดียวที่ได้รับอนุญาต** คำขอจะมีตราประทับ (stamp) ที่อนุญาตให้ตอบได้เพียงครั้งเดียวเท่านั้น peer ตอบกลับหนึ่งครั้งผ่าน helper และคำตอบนั้นก็มีตราประทับของตัวเองเช่นกัน
- **บันทึกก่อนนำไปใช้** การมอบหมายทุกครั้งจะถูกเขียนลงใน `analysis_results/delegations.ndjson` ของแผนก่อนที่คำตอบจะถูกนำไปใช้ และสอดคล้องกับเหตุการณ์ journal `delegation` ของ v7
- **ผลลัพธ์ยังเป็นเพียงคำกล่าวอ้างจนกว่าจะตรวจสอบ** คำตอบของ peer เป็นหลักฐานแบบ `asserted` จนกว่า gate runner ของแผนเองจะสังเกตเห็นมัน และไม่มีวันปิดงานได้ด้วยตัวมันเอง

## โมเดลความปลอดภัย

| กฎ | ความหมาย |
|---|---|
| ต้องได้รับสิทธิ์ก่อน | การมอบหมายงานจะทำงานก็ต่อเมื่อสัญญาของแผนให้สิทธิ์ `agent_delegation` เท่านั้น |
| จำกัดความลึกที่ 1 | ข้อความที่มีตราประทับ `depth=1` หรือ `reply-to=` จะไม่ได้รับคำตอบเลย และผู้รับมอบหมายจะไม่มอบหมายต่ออีก |
| เพดาน fan-out | ค่าเริ่มต้นคือไม่เกินสี่ peer ต่อผู้เรียกหนึ่งราย |
| เป็นข้อมูล ไม่ใช่คำสั่ง | คำตอบไม่มีวันมอบอำนาจที่ผู้รับไม่ได้มีอยู่แล้ว |
| หนึ่ง path หนึ่งผู้เขียน | peer ที่เขียนไฟล์จะทำงานใน git worktree ของตัวเอง |

herdr-peers ไม่ได้ยืนยันตัวตนของผู้ส่ง ฟิลด์ `from=` ในตราประทับเป็นเพียงคำกล่าวอ้าง มาตรการบรรเทาคือ allow-list `HERDR_PEERS_SCOPE` ซึ่งจำกัด workspace และเครื่องที่ peer จะยอมรับ

## Herdr หรือ agentkit

แอดออนทั้งสองใช้อินเทอร์เฟซการมอบหมายงานเดียวกัน ได้แก่ `launch`, `observe`, `collect`, `cancel` แต่ใช้ช่องทางการส่งต่างกัน

| สถานการณ์ | ใช้ |
|---|---|
| งาน `parallel_safe` ที่มีขอบเขตชัดเจนและประกาศผลลัพธ์ไว้ | [agentkit](/kit/agentkit) (`ak run` แบบ headless ใน worktree) |
| งานที่ต้องโต้ตอบ รันนาน หรืออยู่บนเครื่องอื่น | Herdr (peer ใน pane) |

## หมายเหตุ

เป็นแบบเลือกใช้และไม่บังคับเสมอ repo หนึ่งสอดคล้องกับมาตรฐานได้อย่างสมบูรณ์แม้ไม่มีแอดออนแบบเลือกใช้ใดเลย และไม่มีขั้นตอนใดที่ต้องพึ่งพาแอดออนนี้ การรับส่งไปกลับข้ามเครื่องแบบสอง pane ได้รับการทดสอบกับ Herdr จำลอง ควรวางแผนให้การรันครั้งแรกมีผู้กำกับดูแล
