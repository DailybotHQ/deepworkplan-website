# แอดออน Herdr

[Herdr](https://herdr.dev) วาง coding agent ไว้ใน pane ทั้งบนเครื่องของคุณและบนเครื่องที่มันเข้าถึงได้ผ่าน SSH แอดออนนี้ทำให้ Deep Work Plan ใช้เอเจนต์เหล่านั้นเป็น **peer** ได้ แผนสามารถส่งงานที่มีขอบเขตชัดเจนให้เอเจนต์ใน pane อื่น รับคำตอบที่ได้รับอนุญาตเพียงหนึ่งเดียว และเก็บบันทึกของการแลกเปลี่ยนนั้นไว้

นี่คือแอดออนแบบเลือกใช้ของ **DWP v7** (pack `v7.9.0`) ระเบียบวิธีทำงานเหมือนเดิมทุกประการเมื่อไม่มีแอดออนนี้ หากไม่มีแอดออนหรือปิดใช้งานไว้ ทุกงานจะรันในเซสชันปัจจุบันเหมือนที่เคยเป็นมาทุกประการ

## สิ่งที่ผสานรวมเข้ามา

แอดออนนี้เป็นเพียงตัวเชื่อมบาง ๆ งานจริงทำโดย **[herdr-peers](https://github.com/DailybotHQ/herdr-peers)** ซึ่งเป็น skill แบบ MIT ที่แยกเป็นอิสระ ตรึงไว้ที่ **`v1.1.0`** และใช้งานได้แม้ไม่มี Deep Work Plan มันกำหนดสิ่งที่ Herdr เองเปิดทิ้งไว้ ได้แก่ ใครมีสิทธิ์ตอบ คำตอบเดินทางกลับข้ามเครื่องได้อย่างไร เอเจนต์สองตัวจะหลีกเลี่ยงการตอบกันไปมาไม่รู้จบได้อย่างไร และบันทึกว่า "ฉันถามแล้ว มันตอบแล้ว" เก็บไว้ที่ใด

| รายการ | ค่า |
|---|---|
| ผลิตภัณฑ์ | `DailybotHQ/herdr-peers` แท็ก `v1.1.0` โปรโตคอล 1 |
| คีย์ใน registry | `herdr` ใน `.dwp/config.json` |
| ช่องทางการส่ง | แบบโต้ตอบ: peer ใน pane ของ Herdr |
| สิ่งที่มอบให้ | `subagents`, `cancel_children` |
| สิ่งที่ต้องมี | การอนุญาต `agent_delegation` ในสัญญาของแผน |

**เสถียรตั้งแต่ `v1.0.0`** อินเทอร์เฟซสาธารณะเป็นไปตาม semantic versioning ได้แก่ คำสั่งย่อยของ CLI และแฟล็กที่มีเอกสารกำกับ รหัสออก `0`–`7` ตัวแปร `HERDR_PEERS_*`, `DWP_PLAN` และ `DWP_TASK` ที่มีเอกสารกำกับ โปรโตคอล 1 และสัญญา JSON `herdr-peers/lanes-v1`, `herdr-peers/lead-v1` รวมถึงบันทึกการมอบหมายงาน การเปลี่ยนแปลงที่ไม่เข้ากันกับของเดิมในส่วนใดส่วนหนึ่งจะเพิ่มเวอร์ชันหลัก และการเปลี่ยนแปลงรูปแบบข้อมูลที่ส่งผ่านสายจะเพิ่มหมายเลขโปรโตคอลด้วย `v1.0.0` ไม่เปลี่ยนพฤติกรรมใดจาก `v0.3.3` และรุ่น 0.x ไม่ได้รับการสนับสนุนอีกต่อไป

## การติดตั้ง

ติดตั้ง herdr-peers และ skill ทางการของ Herdr ที่มันต้องพึ่งพา ทุกเครื่องที่ต้องการให้เอเจนต์ของตนตอบได้ก็ต้องมี skill นี้ด้วย

```bash
npx --yes skills add https://github.com/DailybotHQ/herdr-peers/tree/v1.1.0 --skill herdr-peers -g -y
npx --yes skills add https://github.com/herdrdev/herdr/tree/v0.9.3 --skill herdr -g -y
```

ข้อกำหนด: Herdr 0.9.1 ขึ้นไป `bash` และ `python3` 3.9 ขึ้นไป (ใช้เฉพาะไลบรารีมาตรฐาน) ขั้นตอน onboarding จะเสนอแอดออนนี้และบันทึกคำตอบของคุณไว้ใน registry ของแอดออน โดยจะไม่มีการเปิดใช้งานเลยหากไม่ได้รับความยินยอม

## สิ่งที่เพิ่มให้กับแผน

- **การมอบหมายงานให้ peer** ในแผน v7 ที่สัญญาให้สิทธิ์ `agent_delegation` คำสั่ง `execute` สามารถส่งงาน `parallel_safe` หรือคำถามแบบอ่านอย่างเดียว ให้เอเจนต์ใน pane อื่นได้ ไม่ว่าจะอยู่บนเครื่องนี้หรือเครื่องอื่น
- **คำตอบเดียวที่ได้รับอนุญาต** คำขอจะมีตราประทับ (stamp) ที่อนุญาตให้ตอบได้เพียงครั้งเดียวเท่านั้น peer ตอบกลับหนึ่งครั้งผ่าน helper และคำตอบนั้นก็มีตราประทับของตัวเองเช่นกัน
- **บันทึกก่อนนำไปใช้** การมอบหมายทุกครั้งจะถูกเขียนลงใน `analysis_results/delegations.ndjson` ของแผนก่อนที่คำตอบจะถูกนำไปใช้ และสอดคล้องกับเหตุการณ์ journal `delegation` ของ v7
- **ผลลัพธ์ยังเป็นเพียงคำกล่าวอ้างจนกว่าจะตรวจสอบ** คำตอบของ peer เป็นหลักฐานแบบ `asserted` จนกว่า gate runner ของแผนเองจะสังเกตเห็นมัน และไม่มีวันปิดงานได้ด้วยตัวมันเอง

## โมเดลความปลอดภัย

| กฎ | ความหมาย |
|---|---|
| ต้องได้รับสิทธิ์ก่อน | การมอบหมายงานจะทำงานก็ต่อเมื่อสัญญาของแผนให้สิทธิ์ `agent_delegation` เท่านั้น |
| จำกัดความลึกที่ 1 | ข้อความที่มีตราประทับ `depth=1` หรือ `reply-to=` จะไม่ได้รับคำตอบเลย และผู้รับมอบหมายจะไม่มอบหมายต่ออีก |
| เพดาน fan-out | ค่าเริ่มต้นคือไม่เกินสี่ peer ต่อผู้เรียกหนึ่งราย |
| เป็นข้อมูล ไม่ใช่คำสั่ง | คำตอบไม่มีวันมอบอำนาจที่ผู้รับไม่ได้มีอยู่แล้ว |
| หนึ่ง path หนึ่งผู้เขียน | peer ที่เขียนไฟล์จะทำงานใน git worktree ของตัวเอง |

herdr-peers ไม่ได้ยืนยันตัวตนของผู้ส่ง ฟิลด์ `from=` ในตราประทับเป็นเพียงคำกล่าวอ้าง มาตรการบรรเทาคือ allow-list `HERDR_PEERS_SCOPE` ซึ่งจำกัด workspace และเครื่องที่ peer จะยอมรับ

## คอนเทนเนอร์และโฮสต์

เมื่อใช้แอดออน [devcontainer](/kit/devcontainer) บน devcontainer-kit `v1.0.1` คอนเทนเนอร์ dck ทุกตัวจะมาพร้อม herdr-peers และเข้าร่วม mesh เมื่อรัน `dck up` เอเจนต์ในคอนเทนเนอร์จึงถามเอเจนต์บนโฮสต์ ในคอนเทนเนอร์อื่น และในคอนเทนเนอร์ loopback อื่นของโฮสต์ แล้วรับคำตอบกลับมาได้ `dck setup` ติดตั้ง herdr-peers ที่ผ่านการตรวจสอบแล้วบนโฮสต์ เอเจนต์บนโฮสต์จึงตอบกลับได้ด้วย listener บนโฮสต์และ key เพิ่มเติมที่อนุญาตให้คอนเทนเนอร์อื่นเข้ามาได้เป็นการตัดสินใจของคุณในโปรไฟล์โฮสต์ของชุดเครื่องมือ แอดออนนี้ไม่เคยตั้งค่าสิ่งเหล่านี้ ตั้งแต่ herdr-peers (`v0.2.3`) แต่ละเครื่องเก็บสถานะของตัวเอง (`$XDG_STATE_HOME/herdr-peers/<server>/`) ดังนั้น checkout ที่โฮสต์และคอนเทนเนอร์ใช้ร่วมกันจะไม่ปะปนบันทึกของทั้งสองฝั่งอีกต่อไป และตั้งแต่ devcontainer-kit (`v0.3.3`) คอนเทนเนอร์จะ export `HERDR_PEERS_SELF` เอง เอเจนต์ Codex ภายในจึงเข้าถึงเครื่องอื่นได้โดยไม่ต้องทำขั้นตอนใดด้วยมือ

## Herdr หรือ agentkit

แอดออนทั้งสองใช้อินเทอร์เฟซการมอบหมายงานเดียวกัน ได้แก่ `launch`, `observe`, `collect`, `cancel` แต่ใช้ช่องทางการส่งต่างกัน

| สถานการณ์ | ใช้ |
|---|---|
| งาน `parallel_safe` ที่มีขอบเขตชัดเจนและประกาศผลลัพธ์ไว้ | [agentkit](/kit/agentkit) (`ak run` แบบ headless ใน worktree) |
| งานที่ต้องโต้ตอบ รันนาน หรืออยู่บนเครื่องอื่น | Herdr (peer ใน pane) |

สำหรับ lead ที่รันหลาย lane พร้อมกัน ทั้ง pane บนโฮสต์ ในคอนเทนเนอร์ และบนเครื่องอื่น โดยแต่ละ lane ใช้บัญชีของตัวเอง `herdr-peers lanes` แสดงทุก lane พร้อมสถานะ `herdr-peers status <pane>` จำแนกหน้าจอที่ lane ที่ถูกบล็อกค้างอยู่ และบันทึกการมอบหมายทุกรายการระบุบัญชีและผู้ให้บริการที่รับงานนั้น ดู [การรันเอเจนต์หลายตัว](/methodology/06-orchestration)

**ทุกเลนระบุเพนของตัวเอง** ภายใต้กฎความเป็นอิสระของสวอร์ม (Guide §17.2) ทุกเลนจะส่งเพนของตัวเองด้วย  ในทุกคำกริยาของ herdr-peers (, , , , , , ) เพื่อป้องกันการระบุผู้รับข้อความผิดพลาดและการอิ่มตัวของสล็อตกระจายงาน โดยเฉพาะเลน Codex ที่กำหนดให้ใช้อย่างเข้มงวดเนื่องจากมีการใช้เซิร์ฟเวอร์พื้นหลังร่วมกันระหว่างเซสชัน

## notice และความเป็นผู้นำ

herdr-peers (`v0.3.2`) เพิ่มสิ่งที่ทำให้ swarm อยู่ได้นานกว่า lead ของมัน ([ความเป็นอิสระของ swarm](/th/methodology/07-swarm-autonomy)):

- **notice** `herdr-peers notify <addr|lead> "<text>" --pane <pane>` ส่งข้อความทางเดียวที่มีตราประทับ `reply=no` คำสั่ง `check` ของผู้รับจำแนกมันเป็น notice บันทึกไว้เป็นข้อมูล และไม่ตอบกลับเลย notice ไม่ใช้ช่อง fan-out และส่งได้แม้ขณะที่ ask ยังเปิดอยู่ ใช้สำหรับประกาศ handoff การเปลี่ยน lead และการประกาศรีลีส
- **บันทึก lead หนึ่งรายการต่อแผน** `herdr-peers lead claim --plan <P> --succession <A,B> --lanes <A,B>` ทำให้เอเจนต์หนึ่งตัวเป็น lead ของแผนหนึ่งแผน `lead show` พิมพ์บันทึกนั้น (schema `herdr-peers/lead-v1`: แผน lead epoch ลำดับการสืบทอด lane และเวลาที่อัปเดต) `lead handover <addr> --plan <P>` ส่งต่อความเป็นผู้นำ `lead takeover --plan <P>` ให้ผู้แทนรายแรกที่ติดต่อได้รับตำแหน่งไปเมื่อ lead หายไป และ `lead release --plan <P>` ยุติตำแหน่งนั้น ทุกการเปลี่ยนแปลงเพิ่มค่า epoch และแจ้งทุก lane ให้ claim แผนก่อนเปิด lane ของแผน: `lead` จะ resolve ได้ก็ต่อเมื่อมีบันทึกอยู่แล้ว ตั้งแต่ `v0.3.2` บันทึกจะเก็บ repository ที่ claim ไว้ในเครื่อง และปฏิเสธการ claim แผน id เดียวกันจาก repository อื่น ให้ระบุแผนนั้นเป็น `--plan <repo>/<id>`
- **fencing** lane ยอมรับ notice จาก lead เฉพาะจากเอเจนต์ที่มอบงานให้มัน (claim ครั้งแรก) จาก lead ปัจจุบันที่ epoch ถัดไป (handover) หรือจากรายการแรกที่ติดต่อได้ในลำดับการสืบทอดที่ epoch ถัดไป (takeover) นอกเหนือจากนี้จะถูกบันทึกและเพิกเฉย และ lead ที่กลับมาแล้วเห็น epoch ที่สูงกว่าจะลงจากตำแหน่ง
- **ที่อยู่ `lead`** `ask lead …` และ `notify lead …` ชี้ไปยัง lead ปัจจุบันของ `--plan` (หรือ `$DWP_PLAN` หากไม่ระบุ) จึงไม่มีคำสั่งงานของ lane ใดฝังที่อยู่ pane ของ lead ไว้ตายตัว
- **หน้าจอ `usage_limit`** `status` และ `lanes` รู้จักข้อความแจ้งขีดจำกัดการใช้งานของ CLI ว่าเป็นหน้าจอคลาส `usage_limit` ซึ่งขั้นตอนถัดไปคือ handoff และไม่กดแป้นตอบเด็ดขาด `lanes --json` เพิ่มแผน lead ของแผน epoch และความจุล่าสุดที่แต่ละ lane รายงาน

lane ยังถามกันเองเพื่อขอข้อมูลและประสานงานได้ — อินเทอร์เฟซ ชื่อแฟล็ก หรือสถานะของ branch — แต่มีเพียง lead ที่มอบหมายงาน ความลึกหนึ่งชั้นและเพดาน fan-out ยังคงใช้อยู่ ใน `v0.2.x` ไม่มี notice หรือบันทึก lead: lane ถามไปยังที่อยู่ของ lead ตามคำสั่งงาน และการเปลี่ยน lead ต้องให้นักพัฒนาเป็นผู้ส่งต่อ

## การดีเบต

herdr-peers 1.1.0 เพิ่มซับสกิล **debate** แบบเนทีฟ (`debate.md`): เอเจนต์ lead จัดคณะ peer ในเพน Herdr ให้ดำเนินไปหลายรอบ แล้วปิดท้ายด้วยผลลัพธ์เดียวที่มนุษย์ไว้วางใจได้ พร้อมหลักฐานและความเห็นแย้ง ใช้เฉพาะเมื่อมนุษย์ขอการดีเบต คณะผู้อภิปราย ทีมแดง การค้นคว้าจากหลายเอเจนต์หรือหลายมุมมอง หรือคณะที่สองเพื่อทบทวนผลลัพธ์เท่านั้น ความเห็นของเอเจนต์ตัวเดียวใช้ ask เพียงครั้งเดียว

- **กำหนดเป้าหมายก่อน** lead เลือกเป้าหมาย ได้แก่ **ตัดสินใจ** **ค้นคว้า**สถานะล่าสุดของสาขา **ทดสอบภายใต้แรงกดดัน** **ตรวจสอบยืนยัน** หรือ **สร้างทางเลือก** แต่ละเป้าหมายมีรูปแบบ วิธีนับ และผลงานส่งมอบของตนเอง เป้าหมายต่อกันเป็นลำดับได้ (ค้นคว้า → ตัดสินใจ, ตัดสินใจ → ตรวจสอบยืนยัน) และขนาดของการดีเบตมีแบบเร็ว มาตรฐาน หรือเชิงลึก
- **ข้อผูกพันของ lead** lead ไม่ลงคะแนนเสียงเลย ถ้อยคำของมนุษย์ถูกคัดลอกตามตัวอักษร บรีฟส่งถึงคณะผ่านช่องทางเดียว แต่ละเพนเขียนความเห็นลงดิสก์และตอบกลับด้วยหนึ่งบรรทัด และไม่มีเพนใดดำเนินการภายนอก
- **รูปแบบ** การค้นคว้าตามมุมมอง รอบแบบคลาสสิก ชุดร่าง การซักค้านทีละข้ออ้าง ทีมแดงก่อนแล้วจึงผู้แก้ต่าง steelman ก่อนแล้วจึงตัดสิน การท้าทายแบบปิดตาด้วยบริบทใหม่ คณะทำซ้ำผล และข้อเสนอที่แตกแขนง การตัดสินใจจะจบด้วยชุดคำตัดสินที่กำหนดไว้เสมอ
- **คำสั่ง `herdr-peers debate`** `tally` นับบัตรลงคะแนนแบบจัดอันดับและคำตัดสินรายข้อ (Borda, Copeland การดวลเป็นคู่ ผู้ชนะและผู้แพ้แบบ Condorcet) `claims` รวมบัญชีข้ออ้างของแต่ละเลนเป็นสถานะ เช่น ยืนยันแล้ว ยังโต้แย้งกันอยู่ หรือถูกหักล้าง ซึ่งเป็นองค์ประชุม ไม่ใช่การตรวจสอบยืนยัน `anon` คัดลอกความเห็นด้วยชื่อนิรนาม โดยเก็บการจับคู่ไว้ในคีย์ส่วนตัว `filings` แสดงรายการความเห็นที่ส่งแล้ว ที่ขาด และที่สั้นเกินไป เพื่อถามซ้ำเฉพาะเพนที่ขาด
- **การจัดองค์คณะ** `panel` เสนอองค์คณะโดยไม่รันสิ่งใด ที่นั่งถูกแบ่งวนไปตามผู้ให้บริการโมเดล และภายในผู้ให้บริการเดียวกัน ที่นั่งที่มีโควตามากที่สุดจะได้ก่อน โดยเลือกจากเพนที่ว่างอยู่ และเมื่อติดตั้ง agentkit (`ak`) ไว้ ก็เลือกจากบัญชีที่ `ak pick` เสนอ หากไม่มี `ak` จะแนะนำ coding-agents-kit (ไม่บังคับ `v1.0.1` ขึ้นไป)
- **เทมเพลต** มีสิบหกเทมเพลตใน `templates/debate/` ตั้งแต่บันทึกของมนุษย์และบรีฟสำหรับการค้นคว้า การทดสอบภายใต้แรงกดดัน และแต่ละรอบ ไปจนถึงไฟล์บัตรลงคะแนนและไฟล์ข้ออ้าง ชุดส่งมอบงานของ lead และบันทึกการตัดสินใจ สถานะล่าสุด การทดสอบภายใต้แรงกดดัน และการทำซ้ำผล
- **การส่งถึง peer ที่ติดค้าง** `reply` และ `notify` จะลองส่งซ้ำถึง peer ที่ค้างอยู่ที่คำถามได้นานสุด `--wait-blocked` วินาที และยังคงเป็นคำตอบเพียงครั้งเดียว

รุ่นนี้เป็นการเพิ่มเท่านั้น: โปรโตคอล 1 และคำสั่ง แฟล็ก รหัสออก และสัญญา JSON ทั้งหมดยังคงเดิม
