# ส่วนเสริม AI Diff Reviewer

ทุก Deep Work Plan ปิดฉากลงในแบบเดียวกัน นั่นคือด้วย **Final Review** ที่บังคับ ซึ่งจะอ่านชุดการเปลี่ยนแปลงทั้งหมดที่แผนนั้นสะสมไว้ ก่อนที่งานจะถูกเรียกว่าเสร็จได้ ขั้นตรวจความปลอดภัยภายในนั้นคือจุดสุดท้ายที่ยังพอจะจับอะไรได้ หากไม่มีตัวช่วย ผู้อ่านเพียงรายเดียว ณ จุดนั้นก็คือ agent ตัวเดียวกับที่เขียนโค้ดนั้นเอง

ส่วนเสริมนี้วางผู้อ่านคนที่สองลงบน diff ดังกล่าว มันเชื่อม **[AI Diff Reviewer](https://github.com/DailybotHQ/ai-diff-reviewer)** ซึ่งอยู่ใน marketplace ในชื่อ "AI Diff Reviewer" และปัจจุบันคือ **v2.3.0** เข้ากับขั้นตรวจความปลอดภัย โดยให้มันคืนสิ่งที่มีโครงสร้างแทนที่จะเป็นร้อยแก้ว ได้แก่ คำตัดสิน ตารางข้อค้นพบ และระดับความรุนแรงของแต่ละข้อ ข้อค้นพบระดับ `critical` จะปิดกั้นการปิดงานจนกว่าจะได้รับการแก้ไขหรือได้รับการยอมรับอย่างชัดแจ้ง การตรวจสอบนี้คือประตูกั้น ไม่ใช่ความคิดเห็น

ตั้งแต่มาตรฐาน 2.3.0 เป็นต้นมา การตรวจสอบในเครื่องนั้น**เป็นส่วนหนึ่งของพื้นฐาน ไม่ใช่ของแถม** onboarding เป็นผู้ติดตั้ง และทุก Final Review เป็นผู้เรียกใช้ สิ่งที่ยังคงเป็นทางเลือกคือพื้นผิว CI นั่นคือ Flow B ซึ่งการตรวจสอบเดียวกันนี้จะควบคุมคำขอดึงผ่าน GitHub Action

เส้นแบ่งที่ทำให้สิ่งนี้ปลอดภัยพอจะนำไปใช้นั้นถูกขีดให้แคบอย่างจงใจ ตัวตรวจทานเป็น skill ที่ใช้สัญญาอนุญาต MIT ตรึงไว้กับแท็ก และทำงานโดย coding agent ที่คุณใช้อยู่แล้ว ดังนั้นจึงไม่มีขั้นตอนใดของ Deep Work Plan ที่ต้องพึ่งพาบริการเชิงพาณิชย์ ผู้ให้บริการ CI หรือค่าลับใด ๆ **Flow A** (เฉพาะในเครื่อง) คือสิ่งที่ทุกที่เก็บโค้ดซึ่งผ่าน onboarding จะได้รับ ส่วน **Flow B** จะถูกเสนออย่างชัดแจ้งและจะไม่ถูกติดตั้งโดยไม่มีการร้องขอ ผู้พัฒนายังสามารถปฏิเสธตัวตรวจทานไปเลยก็ได้ การปฏิเสธนั้นจะถูกบันทึกเป็นข้อยกเว้นที่ประกาศไว้ และ `verify` จะรายงานว่าที่เก็บโค้ดไม่สอดคล้องในประเด็นนั้นจนกว่าจะมีการติดตั้ง

## เมื่อใดควรใช้

| สัญญาณ | การดำเนินการ |
|--------|--------|
| ทุก repository ที่ผ่าน onboarding | **Flow A ถูกติดตั้ง** ใน onboarding Phase 7a (skill ที่ฝังมาพร้อม + `.review/extension.md`) การอัปเกรด harness แบบเจาะจงจะเพิ่มมันให้กับ repository ที่ผ่าน onboarding มาก่อนหน้า |
| ทีมต้องการเกทการรวม PR ใน CI พร้อมผลการค้นพบแบบมีโครงสร้าง | **เสนอ Flow B** — เลือกใช้อย่างชัดเจน ไม่ใช่ค่าเริ่มต้น |
| ที่เก็บโค้ดส่วนตัวหรือทดลอง การตรวจสอบในเครื่องเพียงพอ | **อยู่ที่ Flow A ต่อไป** — พื้นฐานครบถ้วนแล้ว |

## สองขั้นตอนการนำไปใช้

| ขั้นตอน | สิ่งที่คุณได้รับ |
|------|----------------|
| **A — เฉพาะในเครื่อง (พื้นฐาน)** | Skill ที่ฝังมาพร้อม + `.review/extension.md` ที่จำเป็น (ผ่าน `generate-extension`) รันการตรวจสอบในเครื่องภายในการตรวจความปลอดภัยของทุก Final Review ไม่มีเวิร์กโฟลว์ GitHub Actions |
| **B — สองพื้นผิว** | Flow A บวกกับ `setup` ที่เขียน `.github/workflows/pr-review.yml` (Action `@v2`) ไฟล์ส่วนขยายเดียวกันสำหรับในเครื่องและ CI ผู้ช่วย `apply-review` แบบเลือกใช้หลังจาก CI โพสต์ผลการค้นพบ |

การตรวจจับสำหรับการตรวจสอบในเครื่องต้องการ **skill + ไฟล์ส่วนขยาย** ที่หนึ่งในนี้: `.review/extension.md`, `.github/ai-diff-reviewer/extension.md` หรือ `.github/ai-pr-reviewer/extension.md` Skill เพียงอย่างเดียวไม่เพียงพอ

## ส่วนเสริมนี้เชื่อมต่ออะไร (จำกัดตามการออกแบบ)

ส่วนเสริม DWP **ไม่** สร้างผู้ตรวจสอบขึ้นใหม่ แต่มอบหมายการติดตั้ง ระเบียบวิธี ตัวช่วย CI การสร้างส่วนขยาย การร่าง PR และการทบทวนหลัง CI ให้กับ sub-skill ห้ารายการของ skill ต้นทาง (โฟลว์หลักเริ่มต้น `generate-extension` `setup` `open-pr` `apply-review`)

### การตรวจสอบในเครื่องที่จำเป็น

`create` เพิ่มขั้นตอนการตรวจสอบในเครื่องให้กับการตรวจความปลอดภัยของทุก Final Review และ `execute` รันมัน ผลลัพธ์จะถูกเพิ่มภายใต้ `## AI Diff Reviewer local review` ใน `analysis_results/SECURITY_REVIEW.md` ท้องถิ่นของแผน (ภายในโฟลเดอร์ของแผนเอง ไม่ใช่ที่รูทของ repo)

- **ผู้ตรวจสอบหายไป — ถูกบันทึก ไม่เคยข้ามอย่างเงียบ ๆ:** skill หรือส่วนขยายที่หายไปกลายเป็นข้อค้นพบ `local reviewer not installed` Final Review รันการตรวจสอบในเครื่องเมื่อมี skill อยู่ มิฉะนั้นจะนำข้อค้นพบนั้นติดไปในรายงานการเสร็จสิ้น — การติดตั้งเป็นของความยินยอมของ onboarding หรือการเรียกใช้ addon อย่างชัดเจน ไม่เคยเป็นการบูตสแตรปโดยไม่แจ้งล่วงหน้า
- **ความล้มเหลวแบบนุ่มนวล (เฉพาะการเรียก):** การตรวจสอบที่เริ่มได้แต่เกิดข้อผิดพลาด → เตือนหนึ่งครั้ง บันทึกไว้ และดำเนินต่อ อย่าทำให้งานล้มเหลวเพราะเหตุนี้
- **เกทหลังจากผ่านการตรวจสอบแล้ว:** ผลการค้นพบ `critical` ยังคงบล็อกการเสร็จสิ้นของ Final Review จนกว่าจะแก้ไขหรือยอมรับอย่างชัดเจน `warning` / `info` ถูกบันทึกแต่ไม่บล็อก
- **Flow A ไม่ต้องการ CI secret** `CURSOR_API_KEY` ที่ไม่ได้ตั้งค่าต้องไม่ระงับการรันในเครื่อง

### เกท CI Flow B (แบบเลือกใช้)

Action `DailybotHQ/ai-diff-reviewer@v2` โดยทั่วไปถูกควบคุมด้วยป้ายกำกับ (`ready`) พร้อมงาน **AI review gate** ที่ตั้งชื่ออย่างมั่นคงสำหรับการปกป้อง branch และป้ายกำกับข้ามแบบเลือกใช้ `skip-review-label: skip-ai-review` `prompt.md` ที่ใช้ร่วมกัน + ส่วนขยายจัดแนวระเบียบวิธีและระดับความรุนแรง ภายใต้การตรวจสอบแบบรับรู้การวนซ้ำ รอบ CI ที่ 2 ขึ้นไปอาจสั้นลงในขณะที่การรันในเครื่องยังคงสมบูรณ์

### ผู้ช่วย `apply-review` แบบเลือกใช้

หลังจาก CI โพสต์การตรวจสอบ นักพัฒนาสามารถเรียก `apply-review` ระหว่าง `execute` เพื่อทบทวนผลการค้นพบทีละรายการ (นำไปใช้ / เลื่อน / ข้าม) ด้วยความยินยอม อ่านอย่างเดียวตามค่าเริ่มต้น ไม่เคยเป็นไฟล์งานของแผน (จะทำให้ลำดับงานสุดท้ายที่บังคับเสียหาย)

## สิ่งที่เปลี่ยนไปนับตั้งแต่ v2.0.1

มีการปล่อยเวอร์ชันจากต้นทางสามครั้งระหว่าง v2.0.1 กับ v2.3.0 ไม่มีครั้งใดเปลี่ยนวิธีที่ส่วนเสริมนี้ต่อเข้ากับตัวตรวจทาน — Flow A เส้นทางการตรวจพบทั้งสาม และสัญญาการบล็อก ยังคงเหมือนเดิม — แต่ทั้งหมดเปลี่ยนสิ่งที่ผู้นำไปใช้จะได้รับ

| การเปลี่ยนแปลง | ความหมายต่อที่เก็บโค้ดแบบ DWP |
|----------------|--------------------------------|
| **runner กับ backend เป็นค่าอินพุตที่แยกจากกัน** (v2.1.0) | `provider` ระบุ *runner* คือใครเป็นผู้รันลูปการตรวจทาน ส่วน `api-base` ที่เพิ่มเข้ามาระบุ *backend* คือที่อยู่ของโมเดล หาก `api-base` ว่างไว้ ผลลัพธ์จะเหมือน v2.0.x ทุกไบต์ การติดตั้งเดิมจึงทำงานเหมือนเดิมทุกประการ |
| **เพิ่ม runner อีกสองตัว** (v2.1.0) | `openai` (ทำงานในกระบวนการเดียวกัน ไม่ต้องติดตั้ง) และ `grok` (CLI) เข้าร่วมกับชุดเดิม |
| **ต้นทุนกำหนดด้วยระดับชั้นคำเดียว และค่าตั้งต้นมาจากการวัดจริง** (v2.1.0, v2.3.0) | ต้นทุนควบคุมด้วยคำสำคัญของระดับชั้นและ diff ที่ถูกจำกัดขอบเขต และรายงานเป็นรายครั้งของการตรวจทาน บน xAI ทั้ง `balanced` และ `economy` ต่างแปลงเป็น `grok-4.5` ส่วน `deep` แปลงเป็น `grok-4.6` |
| **รอบถัดไปตรวจทาน diff ใหม่ของจริง** (v2.1.0, v2.2.0) | ข้อค้นพบที่ยังค้างอยู่จะถูกส่งต่อไป ค่าตั้งต้นของ `prior-findings-resolution` คือ `advisory` กล่าวคือ คำตัดสินว่า "แก้ไขแล้ว" จากโมเดลจะถูกรายงาน แต่ข้อค้นพบนั้นยังคงบล็อกต่อไปจนกว่าผู้ดูแลจะปิดกระทู้ |
| **การตรวจทานที่ไม่สมบูรณ์ไม่นับว่าผ่าน** (v2.2.0) | การรันที่จบลงโดยไม่ได้เขียนข้อค้นพบใด ๆ จะถูกเผยแพร่ในฐานะการตรวจทานที่ไม่สมบูรณ์อย่างชัดแจ้ง ความเข้มงวดที่มีผลบล็อกทุกระดับจะตัดสินว่าไม่ผ่าน ป้ายกำกับว่าตรวจทานแล้วจะไม่ถูกประทับ และรอบที่ว่างเปล่าจะไม่ถอนข้อค้นพบที่ยังเปิดอยู่ |
| **ตัวติดตั้งที่ตรวจสอบด้วยเช็กซัม** (v2.2.0) | `cursor-installer-sha256` และ `grok-installer-sha256` จะปฏิเสธการรันสิ่งประดิษฐ์ของผู้ให้บริการที่มีค่าแฮชต่างไปจากค่าที่ตรึงไว้ |

ในบรรดาสิ่งเหล่านี้ มีสองข้อที่สำคัญต่อระเบียบวิธีมากกว่าข้ออื่น

**เกทของการตรวจทานที่ไม่สมบูรณ์ปิดช่องโหว่ที่มีอยู่จริงในขั้นตรวจความปลอดภัย** Final Review ต้องไม่สามารถปิดงานโดยอาศัยการตรวจทานที่ไม่เคยเกิดขึ้นจริง ก่อน v2.2.0 runner ที่จบลงโดยไม่ให้ข้อค้นพบใด ๆ นั้นแยกไม่ออกจากการตรวจที่สะอาดหมดจด ตอนนี้มันเป็นสถานะที่มีชื่อเรียกและไม่ใช่สีเขียว ดังนั้น "ไม่มีข้อค้นพบ" จึงหมายความว่าตัวตรวจทานได้ดูแล้วและไม่พบอะไร ไม่ใช่ว่ามันไม่เคยดูเลย

**`economy` จงใจไม่ถูกกว่า** การวัดเปรียบเทียบของต้นทางเมื่อ 2026-09-16 วัด `grok-4.3` ได้ 0 จาก 5 ข้อบกพร่องที่ทราบอยู่แล้ว — มันอนุมัติโดยไม่ตรวจทาน — ขณะที่ `grok-4.5` เสมอกับ `grok-4.6` ที่ 3 จาก 5 โดยไม่มีผลบวกลวง ด้วยต้นทุนเท่ากันและใช้เวลาเพียงหนึ่งในสี่ เนื่องจากไม่มีโมเดล xAI ที่ถูกกว่านี้ซึ่งยังตรวจทานอยู่จริง `economy` จึงแปลงเป็นโมเดลเดียวกับ `balanced` แทนที่จะเป็นระดับชั้นที่หาอะไรไม่พบเลย ด้วยเหตุนี้เส้นทาง xAI ผ่าน CLI จึงขยับจากราว \$0.07 เป็นราว \$0.40–0.75 ต่อการตรวจทานหนึ่งครั้ง และยังคงตรึง `model: grok-4.3` อย่างชัดแจ้งได้เพื่อคงพฤติกรรมเดิมไว้ ตัวเลขเหล่านี้เป็นผลการวัดที่ต้นทางเผยแพร่ ไม่ใช่ของ Deep Work Plan เอง

## พฤติกรรม

- **Flow A คือพื้นฐาน ส่วน Flow B ต้องถาม อย่าเดาเอาเอง** การติดตั้งเวิร์กโฟลว์โดยไม่ได้ขอมีผลกระทบมากกว่าการอยู่ที่ Flow A
- **ประนีประนอม อย่าเขียนทับ** Skill ส่วนขยาย หรือ `pr-review.yml` ที่มีอยู่จะถูกเก็บรักษาไว้ เติมเต็มเฉพาะช่องว่าง
- **การตรวจสอบสิทธิ์ถูกเลื่อนออกไป** ผู้รักษาจะกำหนดค่า secret ของผู้ให้บริการสำหรับ CI ส่วนเสริมนี้ไม่เก็บข้อมูลประจำตัว
- **เป็นกลางต่อผู้ให้บริการ** ไม่มีบริการเชิงพาณิชย์ ผู้ให้บริการ CI หรือ secret ใดที่จำเป็นเลย พื้นผิว CI เป็นชิ้นส่วนเดียวที่แตะต้องผู้ให้บริการ
