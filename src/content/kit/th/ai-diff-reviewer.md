# ส่วนเสริม AI Diff Reviewer

ทุก Deep Work Plan ปิดฉากลงในแบบเดียวกัน นั่นคือด้วย **Final Review** ที่บังคับ ซึ่งจะอ่านชุดการเปลี่ยนแปลงทั้งหมดที่แผนนั้นสะสมไว้ ก่อนที่งานจะถูกเรียกว่าเสร็จได้ ขั้นตรวจความปลอดภัยภายในนั้นคือจุดสุดท้ายที่ยังพอจะจับอะไรได้ หากไม่มีตัวช่วย ผู้อ่านเพียงรายเดียว ณ จุดนั้นก็คือ agent ตัวเดียวกับที่เขียนโค้ดนั้นเอง

ส่วนเสริมนี้วางผู้อ่านคนที่สองลงบน diff ดังกล่าว มันเชื่อม **[AI Diff Reviewer](https://github.com/DailybotHQ/ai-diff-reviewer)** ซึ่งอยู่ใน marketplace ในชื่อ "AI Diff Reviewer" และรีลีสปัจจุบันคือ **v3.1.1** เข้ากับขั้นตรวจความปลอดภัย โดยให้มันคืนสิ่งที่มีโครงสร้างแทนที่จะเป็นร้อยแก้ว ได้แก่ คำตัดสิน ตารางข้อค้นพบ และระดับความรุนแรงของแต่ละข้อ ตั้งแต่ v3 ข้อค้นพบระดับ `critical` หมายความว่าตัวตรวจสอบของส่วนเสริมได้ยืนยันมันด้วยการเรียกโมเดลครั้งที่สองที่อิงโค้ด มีเพียง critical ที่ผ่านการตรวจสอบแล้วเท่านั้นที่จะปิดกั้นการปิดงานจนกว่าจะได้รับการแก้ไขหรือได้รับการยอมรับอย่างชัดแจ้ง การตรวจสอบนี้คือประตูกั้น ไม่ใช่ความคิดเห็น

ตั้งแต่มาตรฐาน 2.3.0 เป็นต้นมา การตรวจสอบในเครื่องนั้น**เป็นส่วนหนึ่งของพื้นฐาน ไม่ใช่ของแถม** onboarding เป็นผู้ติดตั้ง และทุก Final Review เป็นผู้เรียกใช้ สิ่งที่ยังคงเป็นทางเลือกคือพื้นผิว CI นั่นคือ Flow B ซึ่งการตรวจสอบเดียวกันนี้จะควบคุมคำขอดึงผ่าน GitHub Action

เส้นแบ่งที่ทำให้สิ่งนี้ปลอดภัยพอจะนำไปใช้นั้นถูกขีดให้แคบอย่างจงใจ ตัวตรวจทานเป็น skill ที่ใช้สัญญาอนุญาต MIT ตรึงไว้กับแท็ก และทำงานโดย coding agent ที่คุณใช้อยู่แล้ว ดังนั้นจึงไม่มีขั้นตอนใดของ Deep Work Plan ที่ต้องพึ่งพาบริการเชิงพาณิชย์ ผู้ให้บริการ CI หรือค่าลับใด ๆ **Flow A** (เฉพาะในเครื่อง) คือสิ่งที่ทุกที่เก็บโค้ดซึ่งผ่าน onboarding จะได้รับ ส่วน **Flow B** จะถูกเสนออย่างชัดแจ้งและจะไม่ถูกติดตั้งโดยไม่มีการร้องขอ ผู้พัฒนายังสามารถปฏิเสธตัวตรวจทานไปเลยก็ได้ การปฏิเสธนั้นจะถูกบันทึกเป็นข้อยกเว้นที่ประกาศไว้ และ `verify` จะรายงานว่าที่เก็บโค้ดไม่สอดคล้องในประเด็นนั้นจนกว่าจะมีการติดตั้ง

## เมื่อใดควรใช้

| สัญญาณ | การดำเนินการ |
|--------|--------|
| ทุก repository ที่ผ่าน onboarding | **Flow A ถูกติดตั้ง** ใน onboarding Phase 7a (skill ที่ฝังมาพร้อม + `.review/extension.md`) การอัปเกรด harness แบบเจาะจงจะเพิ่มมันให้กับ repository ที่ผ่าน onboarding มาก่อนหน้า |
| ทีมต้องการเกทการรวม PR ใน CI พร้อมผลการค้นพบแบบมีโครงสร้าง | **เสนอ Flow B** — เลือกใช้อย่างชัดเจน ไม่ใช่ค่าเริ่มต้น |
| ที่เก็บโค้ดส่วนตัวหรือทดลอง การตรวจสอบในเครื่องเพียงพอ | **อยู่ที่ Flow A ต่อไป** — พื้นฐานครบถ้วนแล้ว |

## สองขั้นตอนการนำไปใช้

| ขั้นตอน | สิ่งที่คุณได้รับ |
|------|----------------|
| **A — เฉพาะในเครื่อง (พื้นฐาน)** | Skill ที่ฝังมาพร้อม + `.review/extension.md` ที่จำเป็น (ผ่าน `generate-extension`) รันการตรวจสอบในเครื่องภายในการตรวจความปลอดภัยของทุก Final Review ไม่มีเวิร์กโฟลว์ GitHub Actions |
| **B — สองพื้นผิว** | Flow A บวกกับ `setup` ที่เขียนเวิร์กโฟลว์การตรวจทาน (Action `@v3`) ไฟล์ส่วนขยายเดียวกันสำหรับในเครื่องและ CI ผู้ช่วย `apply-review` และ `address-review` แบบเลือกใช้หลังจาก CI โพสต์ผลการค้นพบ |

การตรวจจับสำหรับการตรวจสอบในเครื่องต้องการ **skill + ไฟล์ส่วนขยาย** ที่หนึ่งในนี้: `.review/extension.md`, `.github/ai-diff-reviewer/extension.md` หรือ `.github/ai-pr-reviewer/extension.md` Skill เพียงอย่างเดียวไม่เพียงพอ

## ส่วนเสริมนี้เชื่อมต่ออะไร (จำกัดตามการออกแบบ)

ส่วนเสริม DWP **ไม่** สร้างผู้ตรวจสอบขึ้นใหม่ แต่มอบหมายการติดตั้ง ระเบียบวิธี ตัวช่วย CI การสร้างส่วนขยาย การร่าง PR และลูปการตรวจทานหลัง CI ให้กับ sub-skill หกรายการของ skill ต้นทาง (โฟลว์หลักเริ่มต้น `generate-extension` `setup` `open-pr` `apply-review` `address-review`)

### การตรวจสอบในเครื่องที่จำเป็น

`create` เพิ่มขั้นตอนการตรวจสอบในเครื่องให้กับการตรวจความปลอดภัยของทุก Final Review และ `execute` รันมัน ผลลัพธ์จะถูกเพิ่มภายใต้ `## AI Diff Reviewer local review` ใน `analysis_results/SECURITY_REVIEW.md` ท้องถิ่นของแผน (ภายในโฟลเดอร์ของแผนเอง ไม่ใช่ที่รูทของ repo)

- **ผู้ตรวจสอบหายไป — ถูกบันทึก ไม่เคยข้ามอย่างเงียบ ๆ:** skill หรือส่วนขยายที่หายไปกลายเป็นข้อค้นพบ `local reviewer not installed` Final Review รันการตรวจสอบในเครื่องเมื่อมี skill อยู่ มิฉะนั้นจะนำข้อค้นพบนั้นติดไปในรายงานการเสร็จสิ้น — การติดตั้งเป็นของความยินยอมของ onboarding หรือการเรียกใช้ addon อย่างชัดเจน ไม่เคยเป็นการบูตสแตรปโดยไม่แจ้งล่วงหน้า
- **ความล้มเหลวแบบนุ่มนวล (เฉพาะการเรียก):** การตรวจสอบที่เริ่มได้แต่เกิดข้อผิดพลาด → เตือนหนึ่งครั้ง บันทึกไว้ และดำเนินต่อ อย่าทำให้งานล้มเหลวเพราะเหตุนี้
- **เกทหลังจากผ่านการตรวจสอบแล้ว:** **critical ที่ผ่านการตรวจสอบแล้ว** จะบล็อกการเสร็จสิ้นของ Final Review จนกว่าจะแก้ไขหรือยอมรับอย่างชัดเจน (BC-07) การอ้างสิทธิ์ระดับ critical ที่ยังไม่ผ่านการตรวจสอบจะปรากฏเป็นคำเตือนพร้อมหมายเหตุ — มองเห็นได้ ไม่บล็อก เว้นแต่ `strict-unverified-criticals: true` จะฟื้นการกั้นตามการอ้างสิทธิ์ การตรวจสอบที่ใช้หมดเพดานรอบ (`incomplete`) หรือนาฬิกาจับเวลา (`timeout`) ไม่ถือเป็นการรันที่สะอาดภายใต้ความเข้มงวดแบบบล็อก (BC-04) `warning` / `info` ถูกบันทึกแต่ไม่บล็อก
- **Flow A ไม่ต้องการ CI secret** คีย์ของผู้ให้บริการที่ไม่ได้ตั้งค่าต้องไม่ระงับการรันในเครื่อง

### เกท CI Flow B (แบบเลือกใช้)

Action `DailybotHQ/ai-diff-reviewer@v3` โดยทั่วไปถูกควบคุมด้วยป้ายกำกับ (`ready`) พร้อมงาน **AI review gate** ที่ตั้งชื่ออย่างมั่นคงสำหรับการปกป้อง branch และป้ายกำกับข้ามแบบเลือกใช้ `skip-review-label: skip-ai-review` ตั้งแต่ v3 งบประมาณการตรวจทานจะเป็นไปตามระดับความเสี่ยงเชิงกำหนดของการเปลี่ยนแปลง — 8/20/30/40 รอบจาก `low` ถึง `critical` ภายใต้ `budget-profile: auto` (`fixed` คืนค่าคงที่ก่อน v3 ระหว่างการเปลี่ยนผ่าน) — และ push ที่ไม่เปลี่ยนโค้ดจะรันหนึ่งรอบเฉพาะตัวตรวจสอบ `prompt.md` ที่ใช้ร่วมกัน + ส่วนขยายจัดแนวระเบียบวิธีและระดับความรุนแรง ในเครื่องและ CI ยังคงเหมือนกันในเชิงระเบียบวิธี ขณะที่รอบ CI ที่ 2 ขึ้นไปอาจสั้นลงภายใต้การตรวจสอบแบบรับรู้การวนซ้ำ และการรันในเครื่องยังคงสมบูรณ์

### ผู้ช่วยการตรวจทานแบบเลือกใช้

sub-skill สองรายการที่นักพัฒนาเรียกใช้ได้จะปิดลูปหลังจาก CI โพสต์การตรวจทาน ไม่มีรายการใดเป็นไฟล์งานของแผนเลย (นั่นจะทำลายลำดับงานสุดท้ายที่บังคับ)

- `apply-review` ทบทวนผลการค้นพบทีละรายการ (นำไปใช้ / เลื่อน / ข้าม) ด้วยความยินยอม อ่านอย่างเดียวตามค่าเริ่มต้น ไม่เคย commit หรือ push
- `address-review` (ใหม่ใน v3.1.1) คือลูปคำสั่งเดียว ค้นหา PR ที่เปิดอยู่ของ branch ตรวจว่าการตรวจทานยังครอบคลุม head ปัจจุบันอยู่หรือไม่ นำเสนอข้อค้นพบพร้อมแผนนำไปใช้/เลื่อน/ข้าม แล้ว — เมื่อได้รับคำว่าใช่เพียงครั้งเดียว — นำไปใช้ commit เป็นชุด Conventional Commits ขนาดเล็ก push และติดอาวุธตัวตรวจทานใหม่ตามวิธีที่ repo ทริกเกอร์มัน (กั้นด้วยป้าย → สลับป้ายกำกับ ทริกเกอร์ด้วย push → ยืนยันรอบใหม่) ต่างจาก `apply-review` ตรงที่มัน commit และ push นั่นแหละคือจุดประสงค์ของลูปนี้ บนการตรวจทาน ensemble แบบรวมศูนย์ มันจะอ่านเอกสารรวมศูนย์และเครื่องหมาย `ai-pr-reviewer-aggregate`
- เส้นทางสำหรับเครื่องจักรคือผลลัพธ์ที่มีโครงสร้าง ไม่ใช่เนื้อหาการตรวจทาน เอกสาร `review-output/3.0` (`.aiprr/review-output.json` ระบุตำแหน่งผ่าน output `structured-output-path` และ `structured-output-sha256`) บรรจุบันทึกการรัน ข้อค้นพบพร้อมหลักฐานและการตรวจสอบ ข้อค้นพบที่ถูกหักล้าง และเกท เนื้อหาการตรวจทานที่ระบุ `Recommendation: approve` ไม่ใช่หลักฐานว่าการตรวจสอบผ่านแล้ว — ให้อ่านบล็อก Highest severity / Strictness gate / Check status ของเครื่องหมายติดตามก่อน

## สิ่งที่เปลี่ยนไปใน v3

สามรีลีสมาถึงในวันที่ 2026-09-24 (v3.0.0, v3.0.1, v3.1.0) และ v3.1.1 ตามมาพร้อม sub-skill `address-review` ไม่มีรีลีสใดเปลี่ยนวิธีที่ส่วนเสริมนี้ต่อเข้ากับตัวตรวจทาน — Flow A เส้นทางการตรวจพบทั้งสาม และบันไดไม่บล็อก ยังคงเหมือนเดิม — แต่ทั้งหมดเปลี่ยนสิ่งที่ผู้นำไปใช้จะได้รับ

| การเปลี่ยนแปลง | ความหมายต่อที่เก็บโค้ดแบบ DWP |
|----------------|--------------------------------|
| **`critical` จะเผยแพร่เมื่อผ่านการตรวจสอบเท่านั้น** (v3.0.0) | การอ้างสิทธิ์ระดับ critical แต่ละรายการ — บวกตัวอย่าง 30 % ของคำเตือน — จะได้รับการตรวจสอบครั้งที่สองสั้น ๆ ที่อิงโค้ดโดยการเรียกโมเดลแยกต่างหาก (≈ 3 k โทเค็น 10 วินาที และ $0.009 ต่อข้อค้นพบที่ผ่านการตรวจสอบ) critical ที่ผ่านการตรวจสอบเป็นผู้กั้นขั้นตรวจความปลอดภัย ส่วนการอ้างสิทธิ์ที่ถูกหักล้างยังคงมองเห็นได้เป็นคำเตือนพร้อมหมายเหตุและถูกระบุไว้ในผลลัพธ์ที่มีโครงสร้าง ไม่เคยโพสต์แบบอินไลน์ |
| **งบประมาณตามระดับความเสี่ยง** (v3.0.0) | 8/20/30/40 รอบจาก `low` ถึง `critical` อนุมานจากสินค้าคงคลังการเปลี่ยนแปลง (`budget-profile: auto`) push ที่ไม่เปลี่ยนโค้ดรันหนึ่งรอบเฉพาะตัวตรวจสอบด้วยต้นทุน −93 % `budget-profile: fixed` คืนค่าคงที่ก่อน v3 ของ 30 รอบ |
| **การตรวจทานที่ยังไม่เสร็จเป็นสีแดง** (v3.0.0) | `incomplete` (เพดานรอบ) และ `timeout` (นาฬิกาจับเวลา) โพสต์ข้อค้นพบบางส่วนและล้มเหลวภายใต้ความเข้มงวดแบบบล็อก — "ไม่มีข้อค้นพบ" ตอนนี้หมายความเสมอว่าตัวตรวจทานได้ดูแล้วและไม่พบอะไร |
| **ผลลัพธ์ที่มีโครงสร้างคือเส้นทางสำหรับเครื่องจักร** (v3.0.0) | เอกสาร `review-output/3.0` บรรจุบันทึกการรัน สินค้าคงคลังการเปลี่ยนแปลง ข้อค้นพบพร้อมหลักฐานแบบมีประเภทและการตรวจสอบ ข้อค้นพบที่ถูกหักล้าง และเกท อ่านเอกสารนี้แทนการขูดเนื้อหาการตรวจทาน |
| **หก sub-skill** (v3.1.1) | `address-review` เข้าร่วมเราเตอร์ คำสั่งเดียวนำไปใช้ commit push และติดอาวุธตัวตรวจทานใหม่ |
| **Ensemble แบบเลือกใช้** (v3.0.0) | ขา `mode: emit` อ่านอย่างเดียวบวกงาน `aggregate` หนึ่งงาน ตรวจสอบข้อค้นพบที่รวมกันเพียงครั้งเดียวและโพสต์การตรวจทานเดียว |
| **`@v2` ยังใช้งานได้** | ไลน์ v2 ถูกแช่แข็งที่ `release/v2` พร้อมการบำรุงรักษาด้านความปลอดภัยและแคตตาล็อกหกเดือน v3 เป็นคำแนะนำ ไม่ใช่การย้ายถิ่นแบบบังคับ |

ในบรรดาสิ่งเหล่านี้ มีสองข้อที่สำคัญต่อระเบียบวิธีมากกว่าข้ออื่น

**เกทของ critical ที่ผ่านการตรวจสอบแล้วทำให้ขั้นตรวจความปลอดภัยแข็งแกร่งขึ้น** ก่อน v3 โมเดลสามารถอ้างสิทธิ์ `critical` ได้อย่างอิสระ และเกทจะเดินตามการอ้างสิทธิ์นั้น ตอนนี้ข้อค้นพบระดับ critical ใน Final Review หมายความว่าการเรียกโมเดลครั้งที่สองได้ยืนยันมันกับโค้ดแล้ว และแคมเปญรีลีสวัดความต่างนี้ไว้ 771 รันการประเมินแบบมีค่าใช้จ่ายในสิบแคมเปญ รวมประมาณ $83 ระดับ critical ไปถึง 63/63 recall ด้วยความแม่นยำที่ตัดสินแล้ว 1.0 และรอบแบบเพิ่มเติมตัดโทเค็นอินพุตลง 62–76 % ตัวเลขเหล่านี้เป็นผลการวัดที่ต้นทางเผยแพร่ ไม่ใช่ของ Deep Work Plan เอง

**`economy` จงใจไม่ถูกกว่า** การวัดเปรียบเทียบของต้นทางเมื่อ 2026-09-16 วัด `grok-4.3` ได้ 0 จาก 5 ข้อบกพร่องที่ทราบอยู่แล้ว — มันอนุมัติโดยไม่ตรวจทาน — ขณะที่ `grok-4.5` เสมอกับ `grok-4.6` ที่ 3 จาก 5 โดยไม่มีผลบวกลวง ด้วยต้นทุนเท่ากันและใช้เวลาเพียงหนึ่งในสี่ เนื่องจากไม่มีโมเดล xAI ที่ถูกกว่านี้ซึ่งยังตรวจทานอยู่จริง `economy` จึงแปลงเป็นโมเดลเดียวกับ `balanced` แทนที่จะเป็นระดับชั้นที่หาอะไรไม่พบเลย บน runner grok สิ่งที่ทำให้ต้นทุนขยายตัวคืองบรอบของระดับความเสี่ยง ไม่ใช่การเลือกโมเดล ด้วยเหตุนี้เส้นทาง xAI ผ่าน CLI จึงขยับจากราว $0.07 เป็นราว $0.40–0.75 ต่อการตรวจทานหนึ่งครั้ง นับตั้งแต่พรอมต์ v3.0 การวัดใหม่ 63 รันพา `grok-4.3` จาก 0 ใน 5 ไปที่ 83 % recall ไม่มีผลบวกลวง ต้นทุนต่ำลง ~31 % — แต่มันยังล้มเหลวในการเขียนไฟล์ข้อค้นพบบ่อยกว่า `grok-4.5` ราวสามเท่า ดังนั้น `grok-4.5` จึงยังเป็นค่าเริ่มต้น และ `model: grok-4.3` ยังคงเป็นทางเลือกแลกเปลี่ยนที่ยอมรับอย่างชัดแจ้ง ตัวเลขเหล่านี้เป็นผลการวัดที่ต้นทางเผยแพร่ ไม่ใช่ของ Deep Work Plan เอง

## พฤติกรรม

- **Flow A คือพื้นฐาน ส่วน Flow B ต้องถาม อย่าเดาเอาเอง** การติดตั้งเวิร์กโฟลว์โดยไม่ได้ขอมีผลกระทบมากกว่าการอยู่ที่ Flow A
- **ประนีประนอม อย่าเขียนทับ** Skill ส่วนขยาย หรือเวิร์กโฟลว์การตรวจทานที่มีอยู่จะถูกเก็บรักษาไว้ เติมเต็มเฉพาะช่องว่าง
- **การตรวจสอบสิทธิ์ถูกเลื่อนออกไป** ผู้รักษาจะกำหนดค่า secret ของผู้ให้บริการสำหรับ CI ส่วนเสริมนี้ไม่เก็บข้อมูลประจำตัว
- **เป็นกลางต่อผู้ให้บริการ** ไม่มีบริการเชิงพาณิชย์ ผู้ให้บริการ CI หรือ secret ใดที่จำเป็นเลย พื้นผิว CI เป็นชิ้นส่วนเดียวที่แตะต้องผู้ให้บริการ
