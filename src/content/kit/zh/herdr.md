# Herdr 附加组件

[Herdr](https://herdr.dev) 把编码代理放进窗格中，既可在你的机器上，也可在它通过 SSH 连接到的机器上。这个附加组件让 Deep Work Plan 把这些代理当作**对等方**来使用：计划可以把一项有边界的任务交给另一个窗格中的代理，接收恰好一条获授权的回复，并保留这次交互的记录。

它是 **DWP v7**（pack `v7.9.0`）的一个可选附加组件。没有它，方法论的运作方式完全相同：附加组件缺失或被禁用时，每项任务都在当前会话中运行，与以往完全一样。

## 它集成了什么

该附加组件是一个轻量的集成层。实际工作由 **[herdr-peers](https://github.com/DailybotHQ/herdr-peers)** 完成，它是一个独立的 MIT 技能，固定在 **`v1.1.0`**，脱离 Deep Work Plan 也能使用。它定义了 Herdr 本身留白的部分：谁可以回答，答复如何跨机器返回，两个代理如何避免无休止地互相回答，以及“我提问、它回答”的记录存放在哪里。

| 项目 | 值 |
|---|---|
| 产品 | `DailybotHQ/herdr-peers`，标签 `v1.1.0`，协议 1 |
| 注册表键 | `.dwp/config.json` 中的 `herdr` |
| 传输方式 | 交互式：Herdr 窗格中的一个对等方 |
| 提供 | `subagents`、`cancel_children` |
| 要求 | 计划契约中的 `agent_delegation` 授权 |

**自 `v1.0.0` 起稳定。** 公共接口遵循语义化版本：CLI 动词及其文档化的参数、退出码 `0`–`7`、文档化的 `HERDR_PEERS_*`、`DWP_PLAN` 和 `DWP_TASK` 变量、协议 1，以及 JSON 契约 `herdr-peers/lanes-v1`、`herdr-peers/lead-v1` 和委派记录。对其中任何一项的破坏性变更都会提升主版本号，线路格式的变更还会同时提升协议编号。`v1.0.0` 相对 `v0.3.3` 没有任何行为变化，0.x 版本不再受支持。

## 安装

安装 herdr-peers 及其所依赖的 Herdr 官方技能。凡是其代理需要作答的机器，也都需要安装该技能。

```bash
npx --yes skills add https://github.com/DailybotHQ/herdr-peers/tree/v1.1.0 --skill herdr-peers -g -y
npx --yes skills add https://github.com/herdrdev/herdr/tree/v0.9.3 --skill herdr -g -y
```

要求：Herdr 0.9.1 或更新版本、`bash`，以及 `python3` 3.9 或更新版本（仅使用标准库）。接入流程会提供该附加组件，并把你的回答记录在附加组件注册表中；未经同意，它绝不会被启用。

## 它为计划添加了什么

- **委派给对等方。** 在契约授予 `agent_delegation` 的 v7 计划中，`execute` 可以把一项 `parallel_safe` 任务或一个只读问题，交给另一个窗格中的代理，无论该代理在本机还是在另一台机器上。
- **一条获授权的回复。** 请求带有一个戳记，只授权恰好一条答复。对等方通过辅助程序回复一次，回复本身也带有自己的戳记。
- **先记录，后依赖。** 每次委派都会在回复被使用之前写入计划的 `analysis_results/delegations.ndjson`，并对应 v7 的 `delegation` 日志事件。
- **结果在核验前仍是声明。** 对等方的答复在计划自身的门控运行器观察到它之前，都属于 `asserted` 证据。它绝不会独自关闭一项任务。

## 安全模型

| 规则 | 含义 |
|---|---|
| 先有授权 | 仅当计划契约授予 `agent_delegation` 时才会进行委派。 |
| 深度上限 1 | 带有 `depth=1` 或 `reply-to=` 戳记的消息绝不会被回答，被委派者也绝不会再委派。 |
| 扇出上限 | 默认情况下，每个调用方最多四个对等方。 |
| 是数据，不是指令 | 回复绝不会授予接收方原本没有的权限。 |
| 每条路径一个写入者 | 会写入文件的对等方在自己的 git worktree 中工作。 |

herdr-peers 不对发送方进行身份验证：戳记中的 `from=` 字段只是一项声明。缓解措施是 `HERDR_PEERS_SCOPE` 允许列表，它限定了对等方所接受的工作区和机器。

## 容器与主机

借助基于 devcontainer-kit `v1.1.1` 的 [devcontainer](/kit/devcontainer) 附加组件，每个 dck 容器都自带 herdr-peers，并在 `dck up` 时加入网格：其中的代理可以向主机上、其他容器中以及主机的其他 loopback 容器中的代理提问，并收到回复。`dck setup` 会在主机上安装经过校验的 herdr-peers，因此主机上的代理也能回复。主机监听器以及允许其他容器接入的额外密钥由你在工具包的主机配置文件中决定；本附加组件从不设置它们。自 herdr-peers (`v0.2.3`) 起，每台机器都保留自己的状态（`$XDG_STATE_HOME/herdr-peers/<server>/`），因此主机与容器共享的检出不再混淆彼此的记录；自 devcontainer-kit (`v0.3.3`) 起，容器会自行导出 `HERDR_PEERS_SELF`，因此容器内的 Codex 代理无需手动步骤即可访问其他机器。

## Herdr 还是 agentkit

两个附加组件实现同一个委派接口——`launch`、`observe`、`collect`、`cancel`——但使用不同的传输方式。

| 情形 | 使用 |
|---|---|
| 一项有边界、声明了输出的 `parallel_safe` 任务 | [agentkit](/kit/agentkit)（在 worktree 中以无头方式运行 `ak run`） |
| 任务需要交互、运行时间长，或位于另一台机器上 | Herdr（窗格中的一个对等方） |

如果主导者要同时运行多条通道——位于主机、容器和其他机器上的窗格，各自使用自己的账户——`herdr-peers lanes` 会列出每条通道及其状态，`herdr-peers status <pane>` 会对受阻通道所停留的界面进行分类，而每条委派记录都会写明承担该工作的账户和厂商。参见[运行多个代理](/methodology/06-orchestration)。

**Codex 通道要指明自己的窗格。** Codex 通过同一账户所有会话共享的后台服务器运行通道的命令，因此它继承的窗格 id 可能属于另一个通道。Codex 通道在每个 herdr-peers 命令（`ask`, `reply`, `notify`, `check`, `wait`, `lanes`, `cancel`）上用 `--pane <pane>` 传入主导者任务说明中给出的自身窗格。

## 通知与主导权

herdr-peers (`v0.3.2`) 加入了让代理集群在主导者离开后仍能延续的能力（[集群自主](/zh/methodology/07-swarm-autonomy)）：

- **通知。** `herdr-peers notify <addr|lead> "<text>" --pane <pane>` 发送一条带 `reply=no` 戳记的单向消息。接收方的 `check` 把它归类为通知，作为数据记录下来，从不回复。通知不占用扇出名额，并且可以在一次询问尚未结束时发送；它们用于交接公告、主导者变更和发布广播。
- **每份计划一条主导者记录。** `herdr-peers lead claim --plan <P> --succession <A,B> --lanes <A,B>` 让一个代理成为某份计划的主导者；`lead show` 打印该记录（schema `herdr-peers/lead-v1`：计划、主导者、epoch、继任列表、通道、更新时间）。`lead handover <addr> --plan <P>` 移交主导权，`lead takeover --plan <P>` 在主导者离开时让第一个可达的副手接管，`lead release --plan <P>` 结束主导。每次变更都会提升 epoch 并通知每条通道。在启动计划的通道之前先认领该计划：`lead` 只有在记录存在后才能解析。从 `v0.3.2` 起，记录会在本地保存认领它的仓库，并拒绝另一个仓库对同一计划 id 的认领；请将那份计划写作 `--plan <repo>/<id>`。
- **隔离（fencing）。** 通道只接受以下来源的主导者通知：为它下达任务说明的代理（首次认领）、处于下一个 epoch 的当前主导者（移交），或处于下一个 epoch 的第一个可达继任条目（接管）。其他任何通知都会被记录并忽略；重新出现的主导者若看到更高的 epoch，就会让位。
- **`lead` 地址。** `ask lead …` 和 `notify lead …` 解析为 `--plan`（否则为 `$DWP_PLAN`）的当前主导者，因此任何通道任务说明都无需写死主导者的窗格。
- **`usage_limit` 界面。** `status` 和 `lanes` 会把 CLI 的用量限额消息识别为界面类别 `usage_limit`，其下一步是交接。绝不对它发送按键。`lanes --json` 会加上计划、其主导者、epoch 以及每条通道最近一次报告的容量。

通道之间也可以互相询问信息并进行协调——一个接口、一个参数名、一个分支状态——但只有主导者分配工作。深度为一和扇出上限依然有效。在 `v0.2.x` 中没有通知，也没有主导者记录：通道从任务说明中获得主导者地址并向其询问，主导者变更由开发者转达。

## 辩论

herdr-peers 1.1.0 新增原生的 **debate** 子技能（`debate.md`）：由一个主导智能体组织 Herdr 窗格中的对等智能体组成评审团，经过多轮讨论，最后得出一个用户可以信赖的结果，并附上证据和异议。只有在用户要求辩论、评审团、红队、由多个智能体或从多个角度开展的研究，或对某个结果再组织一次评审时才使用；单个智能体的意见只需一次 ask。

- **先定目的。** 主导者先选择目的——**决策**、**调研**技术现状、**压力测试**、**验证**或**生成**——每种目的都有各自的形式、计数方式和交付物。目的可以串联（调研 → 决策，决策 → 验证），辩论规模分为快速、标准和深入三档。
- **主导者的约定。** 主导者从不投票；用户的原话逐字照录；简报只经由一个渠道送达评审团；每个窗格把陈述写入磁盘，并用一行回复；任何窗格都不执行外部操作。
- **辩论形式。** 角度调研、经典轮次、草案包、逐条主张交叉质询、先红队后辩护、先强化再评判、全新上下文盲审挑战、复现评审团和发散提案。决策类辩论总是在限定的结论范围内收尾。
- **`herdr-peers debate` 命令。** `tally` 统计排序选票和逐项结论（Borda、Copeland、两两对决、Condorcet 胜者与败者）；`claims` 把各条工作线的主张台账合并为已确立、有争议、已驳倒等状态，这些状态只是多数共识，而非验证；`anon` 以匿名文件名复制陈述，映射关系保存在私有密钥中；`filings` 列出已提交、缺失和过短的陈述，只需重新询问缺失的窗格。
- **组建评审团。** `panel` 只提议评审团，不执行任何操作。席位在各模型提供商之间轮流分配，同一提供商内额度最多的席位优先，来源包括空闲窗格，以及安装了 agentkit（`ak`）时 `ak pick` 提议的账号。没有 `ak` 时，它会推荐 coding-agents-kit（可选，`v1.0.1` 或更高版本）。
- **模板。** `templates/debate/` 下有十六个模板，涵盖用户说明，调研、压力测试和各轮简报，选票与主张文件，主导者的交接包，以及决策、技术现状、压力测试和复现记录。
- **向受阻对等方投递。** `reply` 和 `notify` 会在最长 `--wait-blocked` 秒内，重试向卡在提问处的对等方投递；回复仍然只有一次。

此版本只做增量：协议 1 以及所有命令、参数、退出码和 JSON 契约均保持不变。

## 备注

可选且绝非必需。一个仓库在不带任何可选附加组件时即完全符合规范，也没有任何流程依赖这个附加组件。双窗格、跨机器的往返由针对模拟 Herdr 的测试覆盖；请为首次运行安排有人监督。
