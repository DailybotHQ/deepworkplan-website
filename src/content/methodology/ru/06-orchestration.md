# Запуск множества агентов

Один агент на одном плане — вариант по умолчанию, и он покрывает бо́льшую часть работы. Некоторая работа шире одной сессии: изменение, затрагивающее несколько репозиториев, релиз, который должен выйти в определённом порядке, или бэклог, на который одному агенту понадобились бы дни. DWP масштабируется на такую работу, не меняя своего контракта. План остаётся источником истины, каждая задача по-прежнему закрывается на собственном gate, а дополнительные агенты — это **линии** (lanes), которые координирует **ведущий агент** (lead).

Эта глава описывает модель. Она использует три необязательных аддона — [Herdr](/ru/kit/herdr) для панелей и peer-агентов, [agentkit](/ru/kit/agentkit) для учётных записей и [devcontainer](/ru/kit/devcontainer) для контейнеров, — и ни один из них не нужен для плана с одним агентом.

## Ведущий агент и его линии

**Ведущий агент** владеет родительским планом. Он определяет линии, передаёт каждой её объём работы, собирает вехи и даёт сигнал, который позволяет линии слить изменения или выпустить релиз. Он не пишет код другой линии.

**Линия** — это один агент с одним объёмом работы, обычно одним репозиторием. Она читает `AGENTS.md` этого репозитория, запускает его gate и хранит собственный план в репозитории. В [хабе-оркестраторе](/ru/methodology/05-archetypes) родительский план лежит в `.dwp/plans/` хаба вместе с таблицей отслеживания дочерних планов, а план каждой линии лежит в её собственном репозитории и использует идентификаторы планов и gate этого репозитория.

| Роль | Владеет | Никогда не делает |
| --- | --- | --- |
| Ведущий агент | Родительским планом, списком линий, порядком релизов, GO | Не редактирует репозиторий линии |
| Линия | Одним репозиторием: его веткой, планом, gate и pull request | Не сливает и не выпускает релиз до GO ведущего агента |

## Где работают линии

Линия — это агент в панели терминала, и панель может находиться в нескольких местах. [Herdr](https://herdr.dev) размещает каждого агента в панели и дотягивается до других машин по SSH, поэтому ведущий агент видит каждую линию в одной боковой панели.

- **На хосте.** Одна панель на линию, рядом с ведущим агентом. Самая быстрая настройка — для репозиториев, в которых разработчик уже работает.
- **В контейнере.** Контейнер [devcontainer-kit](/ru/kit/devcontainer) присоединяется к сети Herdr при `dck up`: его агенты дотягиваются до хоста и других контейнеров, а хост дотягивается до них. Контейнер — это песочница, поэтому его агенты могут работать в режиме автономии.
- **На другой машине.** Любая машина, до которой Herdr дотягивается по SSH, принимает линии так же, если на ней тоже установлен herdr-peers.

Место меняет изоляцию, а не протокол: линия в контейнере и линия на хосте координируются с ведущим агентом одинаково.

## Учётные записи и поставщики по запасу квоты

Множество агентов быстро расходует квоту. Каждая линия работает на собственной учётной записи — один CLI и один профиль в [coding-agents-kit](/ru/kit/agentkit), — поэтому линии не исчерпывают одно и то же окно, а учётная запись, упёршаяся в лимит, останавливает одну линию, а не все.

- **`ak usage`** показывает остаток квоты на каждой учётной записи и профиле, один раз на пакет.
- **`ak pick <kind> --count N`** возвращает N учётных записей с наибольшим запасом, начиная с лучшей; `--exclude` исключает занятую учётную запись, `--model` учитывает окно одной модели, а `--need` отказывается стартовать без достаточного запаса.
- **`ak <kind> @<profile>`** запускает агента линии на этой учётной записи, в его панели.

Поставщиков сочетают так же. Линия Claude может писать, пока линия Codex проводит ревью, каждая на учётной записи, которую `ak pick` выбрал для её типа. Линия в контейнере может использовать учётные записи хоста: когда в профиле хоста devcontainer-kit разработчика включён `host_profiles`, контейнер получает профили хоста для CLI, которые устанавливает репозиторий, — Claude через долгоживущий токен на профиль, Codex через его файл аутентификации — и не нуждается в собственном входе. Используйте только собственные учётные записи и соблюдайте условия каждого поставщика: распределяйте работу между ними, но никогда не чередуйте учётные записи, чтобы обойти лимит.

## Запуск и разблокировка линий без человека

Ведущий агент может запускать линии и поддерживать их движение, когда за клавиатурой никого нет. Для этого он использует собственные команды Herdr; никакой код kit не отправляет нажатия клавиш. У процедуры фиксированный порядок: избежать запроса, обнаружить остановку, разблокировать только известное, остальное эскалировать.

1. **Сначала избегайте.** `ak pick <kind>` называет учётную запись с наибольшим запасом, а `herdr pane run <pane> 'ak <kind> @<profile> --trust-cwd'` запускает линию в её собственной папке. `--trust-cwd` (или `AGENTKIT_TRUST_CWD=1`) заранее делает эту папку доверенной, а автономия kit по умолчанию делает остальное, поэтому Claude и Codex пропускают экраны доверия к папке без нажатий клавиш.
2. **Обнаруживайте.** `herdr agent list` показывает каждую линию как работающую, простаивающую, заблокированную или завершённую. Для линии, которая заблокирована или простаивает без вывода, выполняется `herdr pane read <pane>`, чтобы определить, на каком экране она стоит.
3. **Разблокируйте только известные экраны первого запуска.** С помощью `herdr pane send-keys` ведущий агент отвечает на два экрана и ни на что больше: доверие к собственной папке линии и одноразовое, для каждого профиля, подтверждение режима bypass-permissions в Claude для профиля, который разработчик запускает в автономии. Он делает это только тогда, когда разработчик разрешил работу без присмотра, — постоянным указанием или предварительной авторизацией плана. Он читает экран перед отправкой клавиш, отправляет минимум клавиш, отвечающих на него, и читает снова.
4. **Эскалируйте всё остальное.** Запросы входа и учётных данных, запросы разрешений на отдельные действия, подтверждения разрушительных действий, запросы оплаты или тарифа, неизвестные экраны и панели, которые ведущий агент не создавал, уходят разработчику как заблокированная веха, никогда как нажатия клавиш.
5. **Отказ побеждает.** При `AGENTKIT_PERMISSIONS=ask` подтверждение режима bypass-permissions никогда не принимается.
6. **Перезапускайте.** Если агент завершает работу, ведущий агент запускает его снова на той же учётной записи или выбирает другую. Потерянный вход — это запрос учётных данных: его эскалируют.

Каждое вмешательство — что показывал экран, какие клавиши отправлены, что произошло дальше — записывается в родительский план.

## Координация через herdr-peers

Линии и ведущий агент общаются через [herdr-peers](/ru/kit/herdr): **ask** несёт отметку, которая авторизует ровно один **reply**, и каждый обмен записывается. Ведущий агент держит протокол небольшим:

- **Вехи наверх.** Каждая линия отчитывается в фиксированных точках — план готов, pull request открыт, заблокировано, завершено — и между ними продолжает работать, не дожидаясь ответа.
- **Вопросы как ask.** Линия, которой нужно решение, спрашивает ведущего агента; ведущий агент отвечает одним reply.
- **Глубина один.** На reply никогда не отвечают, и линия не делегирует дальше. Ветвление на одного вызывающего ограничено, по умолчанию четырьмя peer-агентами.
- **Данные, а не инструкции.** Reply не даёт ничего, чего у получателя ещё не было. Утверждение линии, что её gate пройден, проверяется запуском этого gate.

## Одна ветка, один релиз на репозиторий

Правило, которое сохраняет возможность ревью множества линий, простое: **одна линия на репозиторий, на его базовом checkout, с одной веткой, одним pull request и одним релизом** для всего изменения. Линия не разбивает свою работу на несколько веток или worktree. Worktree нужны только тогда, когда двум записывающим приходится делить один репозиторий: каждый получает собственный, чтобы у каждого пути был один записывающий.

Pull request остаётся открытым, зелёным и помеченным меткой для ревью до GO ведущего агента. Тогда линия сливает изменения, ставит тег и сообщает тег обратно.

## Порядок релизов

Репозитории зависят друг от друга, поэтому их выпускают в порядке зависимостей: сначала инструменты, затем то, что их закрепляет, затем документация, описывающая результат, а затем потребители, которые его внедряют. Ведущий агент держит порядок и отправляет GO по одному репозиторию за раз. Линия, закрепляющая релиз другого репозитория, ждёт его тега, прежде чем записать закрепление, поэтому ни одно закрепление никогда не указывает на релиз, которого не существует.

## Контрольные точки

Родительский план закрывается на доказательствах, а не на отчётах:

1. **Для каждой линии.** Gate каждой линии проходит на её собственной ветке, а ревью её pull request чистое.
2. **Для каждого релиза.** Каждый тег существует и закрепляет то, что нужно следующему репозиторию.
3. **Интеграция.** После последнего релиза контрольная точка запускает потребителей на выпущенных версиях и записывает вердикт в `analysis_results/` родительского плана.
4. **Финальное ревью.** Проверка безопасности охватывает всё, что пересекло границу, — прежде всего учётные записи, токены и файлы, предоставленные контейнерам, — прежде чем родительский план будет завершён.

## Безопасность

- Никогда не помещайте ключ, токен или секрет в ask, prompt или лог; ссылайтесь на переменные по имени.
- Общие ресурсы получают блокировку: линия берёт её перед тяжёлым шагом, например сборкой контейнера, и освобождает после.
- Отказ от разрешений, если он установлен, побеждает для каждой линии и каждого агента, которого запускает линия.
- Линия, которая не может продолжить, сообщает об этом как о заблокированной вехе и останавливается; решает ведущий агент.
