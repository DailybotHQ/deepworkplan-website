# 中核ループ

DWP は、計画を目標から完了したレビュー可能な作業へと進める、小さな操作の集合を定義します。すなわち **create → execute → refine → resume → status** であり、結果を確認する適合チェックとして **verify** が加わります。これらが合わさって、エージェントが計画の生涯を通じて従うループを形づくります。エージェントは一度に一つのタスクを実行し、次へ進む前に各ステップを検証します。

このループは、仕様駆動開発の運用上のかたちです。計画はエージェントが照らして実行する仕様であり、各タスクは明示的な受け入れ基準を備え、検証のステップは完了の主張をその証拠へと変えるゲートです。計画とその進捗ログがリポジトリの中に存在するため、ループはセッションとエージェントをまたいで再開可能です。

## 操作

<CoreLoop lang="ja" class="not-prose my-10" />

この方法論スキルは、開発者の意図を9つの特化型サブスキルに委譲します。6つの中核実行操作、2つのライフサイクル操作、そして作成エンジンです：

- **create** — 目標から新しい計画を生成します。エージェントは目標を分析し、逐次的なタスクへと分解し、計画ファイルを作成します。ガイド付きモードでは、エージェントは [Lite 計画](/ja/spec/lite-plans)（README.md 内のコンパクトでインラインの提案）を直接マテリアライズし、開発者はそれを維持するか、タスクファイル形式の Full 計画へ昇格させるか、編集するか、中止するかを選択できます。trust モードでは、選択された表現形式（Lite または Full）をレビューなしで直接マテリアライズします。要件分析と計画品質チェックはいずれのモードでも実行されます。
- **execute** — 計画をタスクごとに逐次実行します。エージェントは各タスクの完了後に進捗ログを更新し、検証ゲートを実行し、コミットします。trust モードでは、タスク間での確認を求めずに無人実行を継続します。
- **refine** — 既存の計画を変更します（タスクの追加、編集、分割、並べ替え、または Lite 計画から Full 計画への昇格）。完了済みの検証証跡を厳格に保持し、未確認の基準緩和を禁止します。
- **resume** — 中断された計画を続行します。エージェントは追記専用ジャーナルとタスクファイルを読み込んで状態を再構築し、完了した作業を繰り返すことなく、最初の未完了タスクから続行します。
- **status** — 実行せずに進捗を報告します（厳格な読み取り専用）。エージェントは完了済み、進行中、保留中のタスクを要約し、何も変更しません。
- **verify** — 何も変更せずに適合性を確認します（厳格な読み取り専用）。エージェントはリポジトリが AI-first 標準を満たしているか、また計画タスクが明示的な受け入れ基準と検証ゲートを備えているかを報告します。
- **onboard** — 対象リポジトリを調査し、定型文のコピーではなく推論に基づいて、リポジトリに適合した `AGENTS.md`、標準的な `docs/` 階層、モジュール文書、および互換性シンボリックリンクを備えた `.agents/` キットを構築します。
- **upgrade** — アップストリームのリリースを確認し、ダウンロード前に開発者の明示的な同意を求め、固定された安定版タグをインストールし、既存の `.dwp/` 計画に触れることなくローカル適応を調整します。
- **author** — 実際の反復ワークフローに合わせてリポジトリ固有のスキル、エージェント、スラッシュコマンドを作成・進化させ、`.agents/docs/` カタログの整合性を維持します。

## `.dwp/` 出力ディレクトリ

すべての DWP 成果物は、リポジトリのルートにある gitignore された `.dwp/` ディレクトリの配下に存在します。作業領域をバージョン管理の外に置くことで、計画の作業状態がプロジェクトの履歴を汚すことは決してありません。リポジトリレベルのアドオン設定は `.dwp/config.json`（`dwp-config/v1`）に記録され、計画はフラットな番号付きディレクトリに配置されます：

```
.dwp/
├── config.json
└── plans/
    └── PLAN_001_<slug>/
        ├── manifest.json
        ├── contract.json
        ├── journal.ndjson
        ├── state.json
        ├── README.md
        ├── PROGRESS.md
        ├── 1.task_<slug>.md
        ├── 2.task_<slug>.md
        └── analysis_results/
```

## 十の節からなるタスク構造

<TaskAnatomy lang="ja" class="not-prose my-10" />

すべてのタスクファイルは、インストールされたスキルで定義された順序に従い、上記に示された十の規範的セクションで構成されます。

1. **Goal（目標）** — タスクが何を達成するかを述べる一段落。
2. **Context（コンテキスト）** — 背景、リンク、そしてこのタスクが存在する理由。
3. **Touched Surface（変更対象面）** — タスクが変更するものと、検証されなければならないものとの契約。
4. **Steps（手順）** — 実行すべき、順序づけられた具体的な行動。
5. **Acceptance criteria（受け入れ基準）** — 完了を定義する条件のチェックリスト。
6. **Validation（検証）** — 作業を検証するために実行するコマンドやテスト。
7. **Files（ファイル）** — 作成または変更されると見込まれるパス。
8. **Dependencies（依存関係）** — 他のタスクや外部の前提条件。
9. **Risks（リスク）** — 何がうまくいかない可能性があるか、そしてその緩和策。
10. **Completion & Log（完了とログ）** — 状態マーカーと時系列の記録。

## 検証、完了、再開

検証はタスクの一部であり、後付けではありません。各タスクは完了を証明するコマンドやテストを指定し、エージェントは完了を記す前にそれらを実行します。ここではテストが第一級です。新しい機能を追加したり挙動を変更したりするタスクは、その挙動に対する自動テストを追加または更新し、ビルドが成功することを確認するだけでなく、リポジトリの完全なコード品質チェック（テストに加えてリントと型チェック）を実行しなければなりません。既存のテストはグリーンを保ち、スキップするのではなく意図された挙動へと更新されます。セキュリティも同じように第一級です——認証、入力処理、シークレット、ネットワークの接触面、または依存関係に触れるあらゆるタスクは、その変更のセキュリティ上の期待を受け入れ基準に携え、すべてのコミットをシークレットのない状態に保ち、すべての計画は Final Review で締めくくられます — 変更セット全体を対象とするセキュリティパス、最終状態に対する完全な検証、そしてスキルに関する決定の突き合わせです。完了は、Completion & Log の節に明示的な状態マーカー（`[ ]` 未着手、`[~]` 進行中、`[x]` 完了、`[!]` 阻害）で記録されます。再開はこれらのマーカーと進捗ログに依拠します。エージェントは計画がどこで止まったかを正確に再構築し、完了した作業をやり直すことなく、最初の未完了タスクから続行できます。

## v6 と v7：方法論は同じ、構造はより厳格に

現在の DWP 標準は 7.0.0 で、7.x スキル系列が実装しています。このパックはすべての新しい計画を既定で v7 として作成します。明示的に `v6` を指定すれば、引き続き v6 計画が作成されます。既存の v1、v2、v5、v6 計画は記録された世代を維持し、暗黙に移行されることはありません。v5 計画を v6 に移行するには明示的な依頼が必要です。

v6 は同じ計画 → タスク → 検証ゲート → 完了の方法論、スラッシュコマンド、`.dwp/plans/` の配置を維持します。契約、ジャーナル、タスクごとのコンテキストマニフェスト、スケジューラを加え、空の許可リストを拒否することで構造を厳格化します。v7 はその記録層を維持し、任意の `parallel_safe` タスクマーカー、別のエージェントに委ねた範囲の限られた作業を記録する `delegation` ジャーナルイベント、`.dwp/config.json` アドオンレジストリを追加します。委任アドオンが一つも有効でなければ、すべての計画は現在のセッション内で順次実行されます。アーキテクチャ判断は GO です。エージェント成果の経験的な非劣性は測定されていません。
