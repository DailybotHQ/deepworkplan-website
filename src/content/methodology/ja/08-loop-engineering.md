# Loop engineering

**仕様ファースト、ループで完結：リポジトリがハーネスとなり、計画は自ら完了まで走り続けます。** この章では、最初の実行ターン後も計画を進め続ける任意の仕組みを説明します。計画は引き続き永続的な仕様であり、ループが与えるのは継続性であって、新たな権限ではありません。

規範となる本文は [loop engineering 仕様](/ja/spec/loop-engineering)にあります。この章はその解説的な手引きであり、ライフサイクルを順に追って各要素のつながりを示しますが、すべての MUST を繰り返すことはしません。

## なぜループなのか

DWP の最初の二つの柱には一つの空白が残ります。仕様ファーストの計画は、エピソードが*何を*届け、どう検証されるかを示します。ハーネスとしてのリポジトリは、コンテキスト、ツール、gates が*どこに*あるかを示します。しかし、実行中の agent がターンを終えたとき、使用量の上限に達したとき、またはペインを閉じたときに、*作業がどう完了するか*はどちらも示しません。ループがなければ、承認済みで仕様も整った計画であっても、誰かが「continue」と入力するのを待つことになります。

v8 の規則がこの空白を埋めます。承認済み計画は、その計画に記録された権限の範囲内で、人間の定型的な介入なしに完了まで実行されます。人間は待たれるのではなく通知を受けます。例外は、ログインや認証情報が必要な場合と、計画自身の C1–C7 gates のいずれかが事前に許可されていない人間の入力を求める場合です。これらの例外では、入力が届くまで実行はその gate で止まります。

したがってループは継続の仕組みであって承認の仕組みではなく、しかも任意です。Herdr 統合（herdr-peers `autopilot --loop`）は、もともと単一セッションで動く手法を増幅するものです。

## ライフサイクルの概要

一つの承認済み計画は次の段階を進みます。各段階は以下で詳しく説明します。

| 段階 | 何が起きるか | 誰が行うか |
|---|---|---|
| 承認 | 計画が承認される。契約がその権限を記録し、v8 では任意の `autonomy` ブロックも記録する | 人間 |
| 登録 | `execute` が計画の lead レコードを取得し（`resume` は再取得）、計画が後継者を指定していれば後継の順序も記録する | lead agent（パック経由） |
| 実行 | lead が受け入れ基準と gates に照らしてタスクを一つずつ進める | lead とその lanes |
| アイドル | 計画が未完了のまま lead のペインがアイドル状態になる | — |
| 促し | daemon が固定の続行プロンプトを一つ送る | daemon |
| ブロック | lead が構造化ブロッカーを記録して停止する。daemon は何も送らない | lead |
| 停滞 | 進捗のないプロンプトが 3 回続くと、計画は `plan_stalled` として記録される | daemon が記録する |
| フェイルオーバー | 一覧の後継者が引き継ぐ。許可があれば lane が任命され、`--revive` があれば新しい agent が起動される | 後継者、lane、または revive された agent（helper 経由） |
| 完了 | 計画の完了処理がキュー項目を完了にし、次にキューにある計画が開始できる | lead。daemon が次の lead に促す |
| 通知 | 停滞、ブロッカー、lead の喪失、完了、キューのイベントが `--notify` コマンドに送られる | daemon がコマンドを実行する |

## 承認し、権限を記録する

承認はループが関わる前に行われ、ループのどの部分も計画を承認したり、広げたり、修正の代わりになったりすることはできません。

v8 では、計画契約（`plan-contract/v8`）が任意の閉じた `autonomy` ブロックを持てます。閉じているとは、バリデーターが未知のキーを拒否し、v8 以外の契約世代にこのブロックがあればそれも拒否するという意味です。省略されたキーにはそれぞれ記録済みの既定値がちょうど一つあり、利用側は独自の推測ではなくその既定値を適用します。

| キー | 記録する内容 | 省略時の意味 |
|---|---|---|
| `stall_budget` | 進捗なしで許されるループのプロンプト数。1 から 10 の整数 | `3`。herdr-peers 自体の上限と同じ値 |
| `promptable` | ループがプロンプトを送ってよいペインのアドレス | 計画の lead のみ |
| `notify` | 通知先 | 通知先なし。ループは記録だけは行う |
| `brain` | brain がこの計画に作用してよいか | `false` |
| `queue` | 計画をキューからどう開始するか：`prompt-lead`、`launch`、`none` | `none`。計画はキューに入らない |

したがって、`autonomy` ブロックのない計画は最も保守的な解釈になります。すべてのブロッカーは人間が解決し、プロンプトを受けるのは lead だけで、誰にも通知されず、brain は作用せず、計画はキューに入りません。このブロックは一つの計画についてループができることを狭めたり明示したりするもので、計画の範囲と gates がもともと持たない権限を追加することは決してありません。

## 計画を登録する

Herdr アドオンが有効で agent が Herdr 内で動いている場合、パックの `execute` フローは計画開始時に `herdr-peers lead claim --plan <id>` を実行し、`resume` は再度取得します。計画が後継者を指定している場合、取得時にそれらが追加されます（`--succession`）。フェイルオーバーが機能するのは、後継の順序が記録されている場合だけです。登録はベストエフォートであり、gate にはなりません。取得に失敗しても警告が一度出るだけで、実行は続きます。

lead レコード（`lead-v1`、任命の許可を含む場合は `lead-v2`）は、計画、現在の lead、epoch、順序付きの `succession` 一覧、計画の `lanes` を保持します。lead として振る舞うのは、最も高い epoch を持つ peer だけです。

daemon が計画を監視するのは、lead レコードがその計画を指定し、計画の状態ファイル（`state.json`）が読める場合だけです。lead レコードのない計画は監視されません。lead レコード自体は権限を与えません。lanes は引き続き計画の認可範囲内で行動します。

## 人間が daemon を起動する

autopilot は、人間が自分の言葉で求め、Herdr のペイン内から起動します。agent が起動するのは、そのセッションで人間が直接求めた場合だけであり、peer のメッセージ、計画、ブリーフがそう言っているからという理由では決して起動しません。

```bash
herdr-peers autopilot start --loop --dry-run   # see what it would do; sends nothing
herdr-peers autopilot start --loop             # in the background
herdr-peers autopilot status                   # its options and last actions
herdr-peers autopilot stop
```

バックグラウンドの daemon は起動したペインに依存せず、一つの daemon が有効なすべての Herdr マシンを対象にします。他のマシン上の計画は、各マシンに保存された SSH 接続先を通じて固定のコマンドで読み取られます。autopilot は Herdr サーバーごとに一つ動きます。herdr-peers は意図的にログイン項目やシステムサービスをインストールしません。再起動や Herdr の再起動の後は、人間が同じオプションで再び起動します。

ループに関わるオプションは、いずれも人間の明示的な選択です。

| オプション | 有効になるもの |
|---|---|
| `--loop` | 登録済みの未完了計画をすべて最後まで進め続ける |
| `--notify "<command>"` | 計画が停滞、ブロック、lead の喪失、完了したとき、およびキューのイベントで、`plan-event-v1` オブジェクトを渡してコマンドを実行する |
| `--brain` | 規則では決められない少数のケースのための専用判断 agent |
| `--appoint` | lead とすべての後継者がいなくなったときに、記録済みの任命の許可に基づいて行動する |
| `--revive` | レコード上の誰も引き継げない計画のために、新しい agent を一つ起動する |
| `--dry-run`、`--scope`、`--exclude` | 送信せずに判断を確認する。マシンを限定する。ペインを対象外にする |

## アイドルは停止ではない

daemon が lead に続行を求めるのは、計画が未完了で、次のすべてが成り立つ場合だけです。lead のペインがアイドルまたは完了状態で 5 分間変化がないこと。計画の lane が作業中でなく、lead が返信を待っていないこと。画面がダイアログ、ログイン、使用量の上限ではないこと。入力行に人間の下書きがないこと。前回のプロンプト以降に自らターンを行ったこと。そして直近 1 時間のプロンプトが 3 回未満であること。

プロンプトは固定で、埋められるのは計画 id だけです。

> "Plan P is not finished and you are its lead. Continue executing it to its end, respecting its gates and the authority already recorded in the plan. Never weaken a gate to pass it. If the plan cannot go on without something only the developer can provide, record the blocker in the plan state and stop."

促しは求めるだけで、決して許可を与えません。lanes はその lead が動かすため、daemon がプロンプトを送るのは lead だけです。計画の状態に進捗のないままループのプロンプトが 3 回続くと、計画は `plan_stalled` として記録され、状態が変わるまで放置されます。未完了の計画を複数持つ lead が受け取るプロンプトは、1 回の巡回につき一つです。

## 構造化ブロッカー

v8 の計画は、続行できない理由をデータとして記録します。そのため、ループ、フリートマップ、再開する agent は、文章を解釈する代わりに同じフィールドを読みます。ブロッカーはレジャーの helper（`ledger.py block`）で提起し、`ledger.py unblock` で解決します。これは `journal-event/v8` の `blocker` イベントです。ブロッカーイベントの直接追記は拒否されます。

| フィールド | 意味 |
|---|---|
| `task` | ブロックされたタスク。証跡によってすでに閉じたタスクはブロックできない |
| `reason` | タスクが続行できない理由（最大 1000 文字） |
| `needs` | 何があればブロックが解けるかを示す 1 行（最大 500 文字） |
| `class` | 必須：C1–C7 のいずれか |
| `resolver` | 任意：`lead` または `human`。省略時は `human` とみなす |

`resolver: "lead"` は、認証情報、ログイン、同意、支払い、main への push、リリース、削除なしに、計画に記録された権限の範囲内でブロッカーを解決できることを意味します。C1、C2、C5、C6 では拒否されます。アクティブなブロッカーは計画ごとに最大一つで、未解決の間はそのタスクを完了できません。

読み手は計画の `state.json`（`plan-snapshot/v8`）でブロッカーを確認します。アクティブなブロッカーか `null` があり、`blocked` は導出されたタスク状態です。`PROGRESS.md` は固定の 4 行のヘッダーで始まり、遷移のたびに更新されます。

```text
Goal: <one line>
Current task: <task id> - <title> (<status>)
Next action: <one line>
Needs: none | <class> (<resolver>): <needs>
```

ループはブロックされた計画を控えめに扱います。何も送らず、`plan_blocked` を一度だけ記録します。daemon もその brain も、計画が `resolver: "lead"` と記していないブロッカーの解決を lead に求めることはできません。それ以外はすべて人間を待ちます。以前の世代（v6 と v7）の計画はブロッカーイベントを記録せず、それらが報告するブロッカーはすべて人間が扱うものです。

## daemon が決してしないこと

daemon は決して次のことをしません。

- ログイン、サインイン、API キー、デバイスコードの入力画面や、Claude の bypass-permissions 確認に触れること。サインインは人間が行う。
- 拒否の行、自由記述の行、または agent の常設権限を広げる行を選ぶこと。
- 入力行に人間の下書きがあるペインや、対象範囲外のペインにプロンプトを送ること。
- ブロックされた計画や、状態を読み取れない計画にプロンプトを送ること。
- lead レコードを書き込んだり編集したり、プロトコルメッセージを送ったり、レコードにないペインを任命したりすること。
- 計画キューに書き込むこと。

すべての行が拒否か権限の拡大である権限ダイアログは、ブロックされたまま放置されるのではなく拒否され、その後 agent には、計画の gates の範囲内で別の方法で続行するか、ブロッカーを記録するよう一度だけ伝えられます。agent 自身の質問ですべての行が拒否である場合は、作業についての判断であるため人間に委ねられます。

## リーダーシップ：epoch、後継、引き継ぎ

リーダーシップは epoch によってフェンスされます。lead を移すあらゆる変更（引き渡し、引き継ぎ、解放、任命）で epoch が増え、lead として振る舞うのは最も高い epoch を持つ者だけです。戻ってきた以前の lead はより高い epoch を目にし、その lead 操作は拒否され、次の lead 通知によって退きます。

lead がいなくなったとき（そのペインが 2 回続けて一覧に現れないとき）、daemon はレコードの `succession` で到達可能な最初のアドレスに、`herdr-peers lead takeover --plan P` を実行するよう epoch ごとに一度依頼します。理由は渡さないため、lead が本当にいなくなったかどうかは helper 自身の確認が判断します。使用量の上限に達した lead はいなくなったわけではなく、daemon は 30 分ごとに再試行します。後継の順序の誰にも依頼できない場合、daemon は `plan_no_lead` を記録します。

後継者は計画、その受け入れ基準、その gates を引き継ぎます。後継によって変わるのは誰が実行するかであり、何が許可されているかは決して変わりません。

## 任命と revive

lead と後継者がすべていなくなった計画には、さらに二つの道があります。いずれも人間の明示的な行為を必要とし、引き継ぎは agent 自身が行い、helper が確認します。

**任命（protocol 2）。** 人間による二つの行為が必要です。lead レコードに記録された許可（`lead claim --allow-appointment`。lead はその人間の指示があった場合にのみ実行する）と、`--appoint` 付きで起動された daemon です。daemon が自らこの許可を与えることはできません。少なくとも 15 分離れた 2 回の観察で lead とすべての後継者がいなくなっており、進捗もない場合、daemon は計画の最初の稼働中の lane に `lead takeover --plan P --as-lane` を実行するよう依頼します。その helper は許可を再確認し、それが計画のリポジトリで作業している lane であることを確かめ、lead、すべての後継者、それ以前のすべての lane を 1 分間隔で 2 回調べます。生存の兆候が一つでもあれば拒否します。任命は計画ごとに最大 2 回までです。

**Revive（herdr-peers 2.2.0）。** `--loop --revive` で daemon を起動すること自体が許可になります。計画の lead、後継の順序と lanes のすべてのメンバーがいなくなり、誰も引き継げない場合、daemon は計画のチェックアウトで新しい agent を一つ起動し、1 回限りのチケットを書き、`lead takeover --plan P --reason revive` を実行するよう指示できます。helper は、そのチケットがあり、かつ自身の確認ですべてのメンバーがいなくなっていると判断した場合にのみ引き継ぎを受け入れます。revive されたレコードが採用されるのは daemon のマシン上だけです。lead がまだ生きている停滞した計画が、その lead から取り上げられることは決してありません。lead に引き渡しを一度依頼するだけです。revive の上限は、計画ごとに 6 時間に 1 回、計画ごとに合計 2 回、フリート全体で 1 時間に 2 回です。

**不可逆な手順の前に検証する。** 任命された lead や revive された lead も、他の lead と同じく、merge、tag、release の前に `herdr-peers lead verify --plan <id>` を実行します。別のマシンでその計画がより高い epoch を示している場合は拒否し、計画のマシンに到達できない場合は非ゼロで終了します。

## 任意の brain

daemon の規則でほぼすべてが決まります。規則で決められない少数のケースのために、`--brain` は daemon 自身が ask モードで起動する専用の判断 agent を一つ保持し、閉じたアクション一覧の範囲内でのみそれに従います。coding-agents-kit 1.3.0 以降が必要で、ない場合、`--brain` 付きで起動した daemon は、求められた brain なしで動くのではなく起動を拒否します。

| ケース | 許可されるアクション |
|---|---|
| 計画が停滞している | もう一度だけ促す（計画ごとに一度）、人間に伝える、または何もしない |
| 計画が `resolver: "lead"` で、lead が扱えるクラス（C3、C4、C7）であり、機微な対象を含まずにブロックされている | 記録済み権限の範囲内で解決するよう lead に固定の依頼を一度送る、人間に伝える、または何もしない |
| agent が daemon の認識しない画面で待っている | 人間に伝える、または何もしない |

3 分以内に有効な回答がなければ、既定では何もしません。brain のテキストが入力、キー送信、実行されることは決してありません。brain は lead の任命、agent の起動、merge、release、サインイン、権限の変更のいずれもできません。唯一の実行者は daemon です。v8 では、計画の `autonomy.brain` が、そもそも brain がその計画に作用してよいかどうかを記録します。

## 計画キュー

リポジトリは、承認済み計画のキューを `.dwp/queue.json`（スキーマ `dwp-queue-v1`）に保持できます。書き込むのはパック（`shared/queue.py`）か人間で、daemon は読み取るだけであり、その読み取りは範囲が制限され、全体が検証されます。開発者がキューへの追加を求めた場合（または v8 契約が `none` 以外の `autonomy.queue` を記録している場合）、create は承認時に計画を追加します。並べ替えは人間または lead が行います。execute は、計画がその lead のもとで開始されると項目を `started` にし、計画の完了処理後に `done` にします。キューが保持できる項目は最大 64 個です。依存関係はキュー内部に限られ、`after` はすでにキューにある計画を指定します。キューが `parallel: true` を持たない限り、リポジトリごとに一度に動く計画は一つです。

`--loop` では、リポジトリの現在の計画が終わると、次の準備ができた項目が、キューが指名する lead への固定のプロンプト一つで開始されます。「Plan P is next in the queue of the repository at "R" and approved. In that repository, run the plan tool's execute flow for it (its start gate checks the approval again) and execute it to its end, respecting its gates.」項目の準備ができているのは、その `after` の計画が完了し、そのリポジトリで他の計画が動いておらず、lead を指名しており、その承認が現行の契約に対する計画の最新の承認または修正イベントのままである場合だけです。`launch` 項目はループによって開始されません。未承認の項目や lead のない項目と同様に、`queue_blocked` として報告されます。破損したキューは空として読まれ、計画のライフサイクルを壊すことはありません。

## イベント、通知、フリートマップ

daemon は計画イベントを、`--notify` コマンドの標準入力に渡す一つの `plan-event-v1` JSON オブジェクトとして報告します。内容はイベント、計画、マシン、lead、リポジトリ、ブロッカーのクラスです。イベントには、計画と状況ごとに一度の `plan_stalled`、`plan_blocked`、`plan_no_lead`、`plan_lead_moved`、`plan_completed` のほか、`plan_queued_started`、`queue_blocked`、任命と revive のイベント、brain からの `needs_human` があります。失敗は記録されますが、巡回を止めることはありません。

パックの Herdr アドオンには Dailybot notifier（`scripts/notify-dailybot.py`）が付属し、インストール済みの Dailybot CLI を通じて、完了、停滞、ブロック、lead 不在、lead 移動のイベントを、人が読めるチーム向けの更新一つに変換します。CLI がない場合、ログインしていない場合、送信に失敗した場合は静かに終了します。通知は進捗や必要事項を伝えるもので、操作を許可したり計画レコードを置き換えたりすることは決してありません。

ループを観察するには、`herdr-peers plans` が一台のマシンの計画（`plans-v1`）を表示し、`herdr-peers fleet` が統合されたマップ（`fleet-v1`）を表示します。内容はマシン、agent、計画、そして各 agent の lead、後継者、lane としての役割です。`herdr-peers fleet ui` はマップをライブで表示し、計画、リポジトリ、マシン、キューごとにまとめ、対応が必要なもの、アクティブなもの、待機中のもの、完了したもののビューを提供します。UI は読み取り専用で、計画状態を書き込まず、どの agent にもプロンプトを送りません。

## 具体例：一晩で進む一つの計画

以下の手順は説明のための例であり、各手順は上で述べた規則に従っています。

1. 夜、開発者は `notify` 以外を既定値のままにした `autonomy` ブロックを持つ計画を承認します。agent は `execute` を実行し、後継者を一人指定して lead レコードを取得します。
2. 開発者は `herdr-peers autopilot start --loop --notify "<notifier>"` を起動し、オフラインになります。
3. lead は三つのタスクを終えてターンを終了します。5 分後、作業中の lane も返信待ちもないため、daemon は固定の続行プロンプトを送り、lead は次のタスクから再開します。
4. あるタスクに、計画が持っていないシークレットが必要になります。lead は resolver を省略した（`human` とみなされる）C1 ブロッカーを提起して停止します。daemon は計画に何も送らず、`plan_blocked` を記録し、notifier はブロッカーのクラスを示すチーム向けの更新を一つ投稿します。
5. 朝、開発者が入力を提供し、lead は `ledger.py unblock` でブロッカーを解決し、実行が続きます。その後 lead のペインが閉じます。2 回続けて一覧に現れなかった後、daemon は後継者に `lead takeover` の実行を依頼し、epoch が進み、後継者は同じ gates のもとで続行します。
6. 計画の最終 merge の前に、新しい lead は `lead verify` を実行します。計画が完了し、`plan_completed` が notifier に届きます。リポジトリにキューがあれば、次の承認済み計画の lead が固定のキュー用プロンプトを受け取ります。

この間、daemon が何かを承認したり、認証情報を入力したり、作業の内容を決めたりしたことは一度もありません。

## 権限の境界

ループは、計画の権限が止まるところでちょうど止まります。その線を示すのが agent プロトコルのエスカレーションクラスです。C1 権限（計画の認可外の操作、同意チェックポイントでの操作、シークレットに関わる操作）、C2 同意画面（権限、ログイン、認証情報、支払いの画面。agent がキー操作することは決してない）、C3 解消できない曖昧さ、C4 弱めなければ通らない gate、C5 損害、C6 規約、C7 能力の枯渇です。これらのいずれかが事前の許可なしに生じた場合、実行はその gate で止まり、必要事項が記録・報告されます。

ログインと認証情報は常に人間の操作です。人間が daemon を起動し、任命や revive を明示的に許可し、記録された権限では満たせない必要事項を解決します。それ以外については、人間は各手順に付き添うよう求められるのではなく、通知を受けます。

## アドオンなしで使う

これらはいずれも必須ではありません。Herdr がない場合やアドオンが無効な場合、パックはループが存在しないかのように動作します。計画はセッション内で実行され、`resume` で最初の未完了タスクから再開されるか、人間が調整する引き継ぎによって別の agent に渡されます。計画契約、構造化ブロッカー、`PROGRESS.md` のヘッダーは同じように機能するため、人間や別の agent は、ループが読んだはずの状態と同じものを読みます。
