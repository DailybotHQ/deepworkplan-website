# Plan and task templates

A Deep Work Plan is a directory of markdown files. The shape of that directory — and of each file inside it — is what makes a plan reviewable by both humans and agents.

## Plan structure

<PlanTree lang="en" class="not-prose my-10" />

A plan is a directory under `.dwp/plans/` named `PLAN_001_<slug>/`. It contains:

- `manifest.json` — plan metadata, status, and contract pointer.
- `contract.json` — immutable, content-addressed outcome contract (acceptance criteria, scope, invariants).
- `journal.ndjson` — append-only execution log of ledger events.
- `state.json` — derived state cache computed from contract and journal.
- `README.md` — plan overview: goal, source material, task table, and status.
- `PROGRESS.md` — human-readable running log of execution.
- `1.task_<slug>.md`, `2.task_<slug>.md` — individual task markdown files.
- `analysis_results/` — directory for task artifacts, analysis reports, and gate evidence.

The current 7.x pack creates new v7 plans by default with slugs of 2–5 words, as v6 plans have. The retained v5 flow uses 2–4 words because its frozen schemas count the numeric ID as a word. New plans receive monotonically increasing numeric IDs of at least three digits (for example, `PLAN_001_add_payment_webhooks/`). Existing unnumbered `PLAN_<slug>/` folders remain readable and are never renamed; existing plans are never migrated implicitly. When numbered plans exist, `latest` resolves to the plan with the highest numeric ID.

## Task file structure

Each task file is named `<n>.task_<slug>.md` and follows the ten normative sections defined by the installed skill (see [The core loop](/methodology/02-core-loop) for the task anatomy). Each task re-anchors to the plan's goal before it acts, which keeps an agent from drifting over a long, multi-hour horizon.

## The Final Review

Every plan must end with exactly one mandatory task: the **Final Review**. It closes the plan in five ordered parts — nothing in the security pass or gates is relaxed:

1. **Security pass** — audit everything the plan changed for secrets, injection risks, and new attack surface, and keep `docs/SECURITY.md` current; run the required local review if `.agents/skills/ai-diff-reviewer/` and an extension file are present. Every plan leaves its own changes audited, and a critical finding blocks completion.
2. **Final-state validation** — the repository's complete applicable test, lint, and type-check suites run and pass on the final state. Any fix made during review invalidates affected results and triggers a rerun.
3. **Skills reconciliation** — verify every task recorded its task-local skills disposition and reconcile any warranted authoring in `analysis_results/SKILLS_CANDIDATES.md`.
4. **Documentation reconciliation** — sweep every behavior-changing task's touched surface against the docs that register it (`docs/TESTING_GUIDE.md`, architecture docs, and `AGENTS.md`).
5. **Completion and closure** — verify the terminal projection against actual artifacts, record `analysis_results/FINALIZATION.json`, and close.

## README and PROGRESS conventions

The plan `README.md` must contain a title (`# Deep Work Plan: <name>`), a prose goal statement, an optional source-material section, a task table (number, task name, status checkbox), and a plan-status line in the form `<n>/<total> tasks complete`.

`PROGRESS.md` is an append-only execution log. Each entry records an ISO 8601 timestamp, the task number and name, what was done, and any deviations or skip reasons. Because it only ever grows, it is a reliable history of how the plan actually unfolded.

## Headings and cross-references

All headings use sentence case, and documents avoid marketing language and exclamation marks. These conventions keep plans consistent across agents and over time.
