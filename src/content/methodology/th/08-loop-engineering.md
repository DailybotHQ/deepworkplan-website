# Loop engineering

**สเปกมาก่อน ปิดลูปในตัว: repository คือ harness และแผนจะเดินหน้าเองจนเสร็จ** บทนี้อธิบายกลไกเสริมที่ช่วยให้แผนเดินหน้าต่อหลังรอบการทำงานแรก แผนยังคงเป็นข้อกำหนดที่ถาวร ลูปให้ความต่อเนื่อง ไม่ได้ให้อำนาจใหม่

ข้อความเชิงบรรทัดฐานอยู่ใน[ข้อกำหนด loop engineering](/th/spec/loop-engineering) บทนี้เป็นส่วนเล่าเรื่องคู่กัน: ไล่วงจรชีวิตตามลำดับและแสดงว่าส่วนต่าง ๆ ประกอบเข้ากันอย่างไร โดยไม่กล่าวซ้ำทุก MUST

## ทำไมต้องมีลูป

สองเสาหลักแรกของ DWP ยังเหลือช่องว่างหนึ่งจุด การวางแผนแบบสเปกมาก่อนบอกว่าตอนการทำงานหนึ่งต้องส่งมอบ *อะไร* และตรวจสอบอย่างไร repository ในฐานะ harness บอกว่าบริบท เครื่องมือ และ gates อยู่ *ที่ไหน* แต่ไม่มีข้อใดบอกว่างาน *จบอย่างไร* เมื่อ agent ที่ดำเนินงานจบรอบของตน ถึงขีดจำกัดการใช้งาน หรือปิด pane ของตน หากไม่มีลูป แผนที่อนุมัติแล้วและระบุไว้อย่างดีก็ยังต้องรอให้ใครสักคนพิมพ์ "continue"

กฎของ v8 ปิดช่องว่างนั้น แผนที่อนุมัติแล้วจะทำงานจนเสร็จโดยไม่ต้องมีการแทรกแซงจากมนุษย์เป็นประจำ ภายในอำนาจที่บันทึกไว้ในแผนนั้น มนุษย์จะได้รับแจ้ง ไม่ต้องรอมนุษย์ ยกเว้นเมื่อต้องเข้าสู่ระบบหรือใช้ข้อมูลรับรอง หรือเมื่อ gate C1–C7 ของแผนเองข้อใดข้อหนึ่งต้องการข้อมูลจากมนุษย์ที่ไม่ได้อนุญาตไว้ล่วงหน้า ในกรณียกเว้นเหล่านี้ การดำเนินงานจะหยุดที่ gate จนกว่าข้อมูลนั้นจะมาถึง

ดังนั้นลูปจึงเป็นกลไกการทำต่อ ไม่ใช่กลไกการอนุมัติ และเป็นตัวเลือก: การผสานกับ Herdr (herdr-peers `autopilot --loop`) ขยายวิธีการที่ทำงานได้อยู่แล้วในเซสชันเดียว

## วงจรชีวิตโดยสังเขป

แผนที่อนุมัติแล้วหนึ่งแผนผ่านขั้นตอนเหล่านี้ แต่ละขั้นอธิบายโดยละเอียดด้านล่าง

| ขั้นตอน | สิ่งที่เกิดขึ้น | ผู้ดำเนินการ |
|---|---|---|
| อนุมัติ | แผนได้รับอนุมัติ สัญญาของแผนบันทึกอำนาจของแผน และภายใต้ v8 อาจมีบล็อก `autonomy` แบบเลือกได้ | มนุษย์ |
| ลงทะเบียน | `execute` อ้างสิทธิ์บันทึก lead ของแผน (`resume` อ้างสิทธิ์อีกครั้ง) พร้อมลำดับการสืบทอดเมื่อแผนระบุผู้สืบทอดไว้ | lead agent ผ่าน pack |
| ดำเนินงาน | lead ทำงานทีละ task ตามเกณฑ์การยอมรับและ gates | lead และ lane ของตน |
| ว่าง | pane ของ lead ว่างอยู่ขณะที่แผนยังเปิดอยู่ | — |
| เตือน | daemon ส่งข้อความให้ทำต่อแบบคงที่หนึ่งข้อความ | daemon |
| ติดขัด | lead บันทึกสิ่งกีดขวางแบบมีโครงสร้างแล้วหยุด daemon ไม่ส่งอะไรเลย | lead |
| หยุดชะงัก | หลังเตือน 3 ครั้งโดยไม่มีความคืบหน้า แผนจะถูกบันทึกเป็น `plan_stalled` | daemon เป็นผู้บันทึก |
| สลับเมื่อล้มเหลว | ผู้สืบทอดในรายการรับช่วงต่อ หากมีการอนุญาต จะแต่งตั้ง lane หนึ่ง หากใช้ `--revive` จะเปิด agent ใหม่ | ผู้สืบทอด lane หรือ agent ที่ revive ผ่าน helper |
| เสร็จสิ้น | การปิดแผนทำเครื่องหมายรายการในคิวว่าเสร็จ แผนถัดไปในคิวอาจเริ่มได้ | lead และ daemon ส่งข้อความถึง lead คนถัดไป |
| แจ้งเตือน | การหยุดชะงัก สิ่งกีดขวาง lead ที่หายไป การเสร็จสิ้น และเหตุการณ์ของคิว ถูกส่งไปยังคำสั่ง `--notify` | daemon เป็นผู้รันคำสั่ง |

## อนุมัติและบันทึกอำนาจ

การอนุมัติเกิดขึ้นก่อนที่ลูปจะเกี่ยวข้อง และไม่มีสิ่งใดในลูปที่อนุมัติแผน ขยายแผน หรือใช้แทนการแก้ไขแผนได้

ภายใต้ v8 สัญญาของแผน (`plan-contract/v8`) อาจมีบล็อก `autonomy` แบบปิดที่เป็นตัวเลือก แบบปิดหมายความว่าตัวตรวจสอบจะปฏิเสธคีย์ที่ไม่รู้จัก และปฏิเสธบล็อกนี้บนสัญญารุ่นอื่นนอกจาก v8 คีย์ที่ไม่ได้ระบุทุกคีย์มีค่าเริ่มต้นที่บันทึกไว้เพียงค่าเดียว และผู้ใช้ข้อมูลจะใช้ค่าเริ่มต้นนั้นแทนการเดาเอง

| คีย์ | สิ่งที่บันทึก | หากไม่ระบุ |
|---|---|---|
| `stall_budget` | จำนวนข้อความเตือนของลูปที่อนุญาตโดยไม่มีความคืบหน้า เป็นจำนวนเต็ม 1 ถึง 10 | `3` ค่าเดียวกับเพดานของ herdr-peers เอง |
| `promptable` | ที่อยู่ pane ที่ลูปส่งข้อความเตือนได้ | เฉพาะ lead ของแผน |
| `notify` | เป้าหมายการแจ้งเตือน | ไม่มีเป้าหมาย ลูปยังคงบันทึก |
| `brain` | brain ทำการกับแผนนี้ได้หรือไม่ | `false` |
| `queue` | แผนเริ่มจากคิวอย่างไร: `prompt-lead`, `launch` หรือ `none` | `none` แผนไม่ได้อยู่ในคิว |

ดังนั้นแผนที่ไม่มีบล็อก `autonomy` จะถูกตีความแบบระมัดระวังที่สุด: มนุษย์แก้สิ่งกีดขวางทุกข้อ ส่งข้อความเตือนได้เฉพาะ lead ไม่มีใครได้รับแจ้ง ไม่มี brain ทำการ และแผนไม่ได้อยู่ในคิว บล็อกนี้จำกัดหรือระบุสิ่งที่ลูปทำได้สำหรับแผนหนึ่งแผน และไม่เคยเพิ่มอำนาจที่ขอบเขตและ gates ของแผนไม่ได้มีอยู่แล้ว

## ลงทะเบียนแผน

เมื่อเปิดใช้ส่วนเสริม Herdr และ agent ทำงานอยู่ใน Herdr โฟลว์ `execute` ของ pack จะรัน `herdr-peers lead claim --plan <id>` เมื่อเริ่มแผน และ `resume` จะอ้างสิทธิ์อีกครั้ง เมื่อแผนระบุผู้สืบทอดไว้ การอ้างสิทธิ์จะเพิ่มผู้สืบทอดเหล่านั้น (`--succession`) การสลับไปยังผู้สืบทอดเมื่อเกิดความล้มเหลวทำได้เฉพาะเมื่อมีลำดับการสืบทอดที่บันทึกไว้ การลงทะเบียนเป็นแบบพยายามอย่างดีที่สุดและไม่เคยเป็น gate: หากอ้างสิทธิ์ล้มเหลวจะเตือนหนึ่งครั้งและดำเนินงานต่อ

บันทึก lead (`lead-v1` หรือ `lead-v2` เมื่อมีการอนุญาตการแต่งตั้ง) เก็บแผน lead ปัจจุบัน epoch รายการ `succession` ตามลำดับ และ `lanes` ของแผน เฉพาะ peer ที่ถือ epoch สูงสุดเท่านั้นที่ทำหน้าที่เป็น lead

daemon เฝ้าดูแผนเฉพาะเมื่อมีบันทึก lead ระบุแผนนั้นและอ่านไฟล์สถานะของแผน (`state.json`) ได้ แผนที่ไม่มีบันทึก lead จะไม่ถูกเฝ้าดู บันทึก lead ไม่ได้ให้อำนาจในตัวเอง: lane ยังคงทำงานภายในการอนุญาตของแผน

## มนุษย์เริ่ม daemon

มนุษย์เริ่ม autopilot ด้วยคำพูดของตนเอง จากภายใน pane ของ Herdr agent จะเริ่มได้ก็ต่อเมื่อมนุษย์ของตนขอโดยตรงในเซสชันนั้น ไม่ใช่เพราะข้อความของ peer แผน หรือ brief บอกให้ทำ

```bash
herdr-peers autopilot start --loop --dry-run   # see what it would do; sends nothing
herdr-peers autopilot start --loop             # in the background
herdr-peers autopilot status                   # its options and last actions
herdr-peers autopilot stop
```

daemon เบื้องหลังไม่ขึ้นกับ pane ที่เริ่มมัน และ daemon หนึ่งตัวครอบคลุมทุกเครื่อง Herdr ที่เปิดใช้งาน แผนบนเครื่องอื่นอ่านผ่านเป้าหมาย SSH ที่บันทึกไว้ของแต่ละเครื่องด้วยคำสั่งคงที่ autopilot หนึ่งตัวทำงานต่อหนึ่งเซิร์ฟเวอร์ Herdr herdr-peers ตั้งใจไม่ติดตั้งรายการเข้าสู่ระบบหรือบริการของระบบ: หลังรีบูตหรือรีสตาร์ต Herdr มนุษย์จะเริ่มใหม่ด้วยตัวเลือกเดิม

ตัวเลือกที่มีผลต่อลูปแต่ละข้อเป็นการเลือกอย่างชัดแจ้งของมนุษย์:

| ตัวเลือก | สิ่งที่เปิดใช้ |
|---|---|
| `--loop` | ให้ทุกแผนที่เปิดอยู่และลงทะเบียนแล้วทำงานต่อจนจบ |
| `--notify "<command>"` | รันคำสั่งพร้อมออบเจ็กต์ `plan-event-v1` เมื่อแผนหยุดชะงัก ถูกบล็อก สูญเสีย lead หรือเสร็จสิ้น และสำหรับเหตุการณ์ของคิว |
| `--brain` | agent ตัดสินใจโดยเฉพาะสำหรับกรณีไม่กี่กรณีที่กฎตัดสินไม่ได้ |
| `--appoint` | ดำเนินการตามการอนุญาตการแต่งตั้งที่บันทึกไว้เมื่อ lead และผู้สืบทอดทุกคนหายไป |
| `--revive` | เปิด agent ใหม่หนึ่งตัวสำหรับแผนที่ไม่มีใครในบันทึกรับช่วงต่อได้ |
| `--dry-run`, `--scope`, `--exclude` | ดูการตัดสินใจโดยไม่ส่ง จำกัดเครื่อง กัน pane หนึ่งไว้นอกการเข้าถึง |

## ว่างไม่ได้แปลว่าหยุด

daemon ขอให้ lead ทำต่อเฉพาะเมื่อแผนยังเปิดอยู่และครบทุกเงื่อนไขต่อไปนี้: pane ของ lead ว่างหรือเสร็จแล้วและไม่เปลี่ยนแปลงมา 5 นาที ไม่มี lane ใดของแผนกำลังทำงานและ lead ไม่ได้รอคำตอบ หน้าจอไม่ใช่กล่องโต้ตอบ การเข้าสู่ระบบ หรือขีดจำกัดการใช้งาน บรรทัดป้อนข้อมูลไม่มีร่างของมนุษย์ ได้ทำรอบของตนเองแล้วนับจากข้อความเตือนครั้งก่อน และได้รับข้อความเตือนน้อยกว่า 3 ครั้งในชั่วโมงที่ผ่านมา

ข้อความเตือนเป็นข้อความคงที่ เติมเฉพาะ id ของแผน:

> "Plan P is not finished and you are its lead. Continue executing it to its end, respecting its gates and the authority already recorded in the plan. Never weaken a gate to pass it. If the plan cannot go on without something only the developer can provide, record the blocker in the plan state and stop."

การเตือนเป็นการขอ ไม่เคยเป็นการอนุญาต daemon ส่งข้อความเตือนถึง lead เท่านั้น เพราะ lane ถูกขับเคลื่อนโดย lead ของตน หลังข้อความเตือนของลูป 3 ครั้งโดยไม่มีความคืบหน้าในสถานะของแผน แผนจะถูกบันทึกเป็น `plan_stalled` และปล่อยไว้จนกว่าสถานะจะเปลี่ยน lead ที่มีหลายแผนเปิดอยู่จะได้รับข้อความเตือนหนึ่งครั้งต่อรอบ

## สิ่งกีดขวางแบบมีโครงสร้าง

แผน v8 บันทึกเหตุผลที่ทำต่อไม่ได้เป็นข้อมูล เพื่อให้ลูป แผนที่ fleet และ agent ที่กลับมาทำต่ออ่านฟิลด์เดียวกันแทนการตีความข้อความร้อยแก้ว สิ่งกีดขวางถูกยกขึ้นด้วย helper ของ ledger (`ledger.py block`) และแก้ด้วย `ledger.py unblock` เป็นเหตุการณ์ `blocker` ของ `journal-event/v8` การต่อท้ายเหตุการณ์สิ่งกีดขวางแบบดิบจะถูกปฏิเสธ

| ฟิลด์ | ความหมาย |
|---|---|
| `task` | task ที่ถูกบล็อก task ที่หลักฐานปิดไปแล้วไม่สามารถถูกบล็อกได้ |
| `reason` | เหตุใด task จึงทำต่อไม่ได้ (ไม่เกิน 1000 อักขระ) |
| `needs` | หนึ่งบรรทัดบอกว่าอะไรจะปลดบล็อก (ไม่เกิน 500 อักขระ) |
| `class` | จำเป็น: หนึ่งใน C1–C7 |
| `resolver` | ไม่บังคับ: `lead` หรือ `human` หากไม่ระบุจะอ่านเป็น `human` |

`resolver: "lead"` หมายความว่าสิ่งกีดขวางแก้ได้ภายในอำนาจที่บันทึกไว้ของแผน โดยไม่ต้องใช้ข้อมูลรับรอง การเข้าสู่ระบบ ความยินยอม การชำระเงิน การ push ไปยัง main การ release หรือการลบ ค่านี้ถูกปฏิเสธสำหรับ C1, C2, C5 และ C6 แต่ละแผนมีสิ่งกีดขวางที่ใช้งานอยู่ได้ไม่เกินหนึ่งข้อ และขณะที่ยังไม่ได้แก้ task นั้นจะเสร็จไม่ได้

ผู้อ่านพบสิ่งกีดขวางใน `state.json` ของแผน ซึ่งเป็น `plan-snapshot/v8`: สิ่งกีดขวางที่ใช้งานอยู่หรือ `null` โดยมี `blocked` เป็นสถานะ task ที่อนุมานได้ `PROGRESS.md` เริ่มต้นด้วยบรรทัดส่วนหัวคงที่สี่บรรทัด ซึ่งรีเฟรชทุกครั้งที่มีการเปลี่ยนสถานะ:

```text
Goal: <one line>
Current task: <task id> - <title> (<status>)
Next action: <one line>
Needs: none | <class> (<resolver>): <needs>
```

ลูปปฏิบัติต่อแผนที่ถูกบล็อกอย่างยับยั้งชั่งใจ ไม่ส่งอะไรถึงแผนนั้นและบันทึก `plan_blocked` หนึ่งครั้ง ทั้ง daemon และ brain ของมันไม่อาจขอให้ lead แก้สิ่งกีดขวางที่แผนไม่ได้ทำเครื่องหมาย `resolver: "lead"` ไว้ ทุกอย่างที่เหลือรอมนุษย์ แผนของรุ่นก่อนหน้า (v6 และ v7) ไม่บันทึกเหตุการณ์สิ่งกีดขวาง และสิ่งกีดขวางทุกข้อที่แผนเหล่านั้นรายงานเป็นของมนุษย์

## สิ่งที่ daemon ไม่เคยทำ

daemon ไม่เคย:

- แตะหน้าขอเข้าสู่ระบบ ลงชื่อเข้าใช้ API-key หรือ device-code หรือการยืนยัน bypass-permissions ของ Claude มนุษย์เป็นผู้ลงชื่อเข้าใช้
- เลือกแถวปฏิเสธ แถวข้อความอิสระ หรือแถวที่ขยายสิทธิ์ถาวรของ agent
- ส่งข้อความเตือนถึง pane ที่บรรทัดป้อนข้อมูลมีร่างของมนุษย์ หรือ pane ที่อยู่นอกขอบเขตของมัน
- ส่งข้อความเตือนถึงแผนที่ถูกบล็อก หรือแผนที่มันอ่านสถานะไม่ได้
- เขียนหรือแก้ไขบันทึก lead ส่งข้อความโปรโตคอล หรือแต่งตั้ง pane ที่ไม่อยู่ในบันทึก
- เขียนคิวของแผน

กล่องโต้ตอบสิทธิ์ที่ทุกแถวปฏิเสธหรือขยายสิทธิ์จะถูกปฏิเสธ ไม่ปล่อยค้างไว้ จากนั้นจะบอก agent หนึ่งครั้งให้ทำต่อด้วยวิธีอื่นภายใน gates ของแผน หรือบันทึกสิ่งกีดขวาง คำถามของ agent เองที่ทุกแถวเป็นการปฏิเสธจะปล่อยไว้ให้มนุษย์ เพราะเป็นการตัดสินใจเกี่ยวกับงาน

## การนำ: epoch การสืบทอด และ takeover

การนำถูกล้อมรั้วด้วย epoch ทุกการเปลี่ยนแปลงที่ย้าย lead (การส่งมอบ takeover การปล่อย การแต่งตั้ง) จะเพิ่ม epoch และเฉพาะผู้ถือ epoch สูงสุดเท่านั้นที่ทำหน้าที่เป็น lead lead คนเดิมที่กลับมาจะพบ epoch ที่สูงกว่า คำสั่ง lead ของมันจะถูกปฏิเสธ และการแจ้ง lead ครั้งถัดไปจะทำให้มันลงจากตำแหน่ง

เมื่อ lead หายไป (pane ของมันไม่ปรากฏในรายการสองครั้งติดกัน) daemon จะขอให้ที่อยู่แรกที่ติดต่อได้ใน `succession` ของบันทึกรัน `herdr-peers lead takeover --plan P` หนึ่งครั้งต่อ epoch โดยไม่ส่งเหตุผล การตรวจของ helper เองจึงเป็นผู้ตัดสินว่า lead หายไปจริงหรือไม่ lead ที่ถึงขีดจำกัดการใช้งานไม่นับว่าหายไป: daemon จะลองใหม่ทุก 30 นาที หากไม่มีใครในลำดับการสืบทอดที่ขอได้ daemon จะบันทึก `plan_no_lead`

ผู้สืบทอดรับช่วงแผน เกณฑ์การยอมรับ และ gates ของแผน การสืบทอดเปลี่ยนว่าใครดำเนินงาน ไม่เคยเปลี่ยนว่าอะไรได้รับอนุญาต

## การแต่งตั้งและ revive

มีอีกสองเส้นทางสำหรับแผนที่ lead และผู้สืบทอดหายไปทั้งหมด แต่ละเส้นทางต้องมีการกระทำของมนุษย์อย่างชัดแจ้ง และปล่อยให้ agent ทำ takeover เอง โดยมี helper ตรวจสอบ

**การแต่งตั้ง (protocol 2)** ต้องมีการกระทำของมนุษย์สองอย่าง: การอนุญาตที่บันทึกไว้ในบันทึก lead (`lead claim --allow-appointment` ซึ่ง lead รันเฉพาะเมื่อมนุษย์ของตนสั่ง) และ daemon ที่เริ่มด้วย `--appoint` daemon ให้สิทธิ์นี้แก่ตัวเองไม่ได้ เมื่อ lead และผู้สืบทอดทุกคนหายไปในการสังเกตสองครั้งที่ห่างกันอย่างน้อย 15 นาทีโดยไม่มีความคืบหน้า daemon จะขอให้ lane แรกที่ยังทำงานอยู่ของแผนรัน `lead takeover --plan P --as-lane` helper นั้นตรวจการอนุญาตอีกครั้ง ยืนยันว่าเป็น lane ที่ทำงานใน repository ของแผน และตรวจ lead ผู้สืบทอดทุกคน และ lane ก่อนหน้าทุกตัวสองครั้ง ห่างกันหนึ่งนาที สัญญาณชีวิตใด ๆ จะทำให้ปฏิเสธ อนุญาตการแต่งตั้งได้ไม่เกินสองครั้งต่อแผน

**Revive (herdr-peers 2.2.0)** การเริ่ม daemon ด้วย `--loop --revive` คือการอนุญาตในตัว เมื่อ lead ของแผนและสมาชิกทุกคนในลำดับการสืบทอดและ lane หายไปและไม่มีใครรับช่วงต่อได้ daemon อาจเปิด agent ใหม่หนึ่งตัวใน checkout ของแผน เขียนตั๋วใช้ครั้งเดียว และ brief ให้รัน `lead takeover --plan P --reason revive` helper ยอมรับ takeover เฉพาะเมื่อมีตั๋วนั้น และเฉพาะหลังจากการตรวจของตนเองพบว่าสมาชิกทุกคนหายไป บันทึกที่ revive จะถูกรับใช้เฉพาะบนเครื่องของ daemon แผนที่หยุดชะงักซึ่ง lead ยังมีชีวิตอยู่จะไม่ถูกยึดไปจาก lead เลย: จะขอให้ lead ส่งมอบหนึ่งครั้ง revive จำกัดไว้ที่หนึ่งครั้งต่อแผนต่อ 6 ชั่วโมง รวมสองครั้งต่อแผน และสองครั้งต่อชั่วโมงทั่วทั้ง fleet

**ตรวจสอบก่อนขั้นตอนที่ย้อนกลับไม่ได้** lead ที่ได้รับแต่งตั้งหรือ revive เช่นเดียวกับ lead ทุกคน จะรัน `herdr-peers lead verify --plan <id>` ก่อน merge, tag หรือ release ทุกครั้ง คำสั่งนี้ปฏิเสธเมื่อเครื่องอื่นแสดงแผนที่ epoch สูงกว่า และออกด้วยรหัสที่ไม่ใช่ศูนย์เมื่อติดต่อเครื่องใดของแผนไม่ได้

## brain แบบเลือกได้

กฎของ daemon ตัดสินเกือบทุกอย่าง สำหรับกรณีไม่กี่กรณีที่กฎตัดสินไม่ได้ `--brain` จะคง agent ตัดสินใจโดยเฉพาะหนึ่งตัวที่ daemon เปิดเองในโหมด ask และเชื่อฟังเฉพาะภายในรายการการกระทำแบบปิด ต้องใช้ coding-agents-kit 1.3.0 ขึ้นไป หากไม่มี daemon ที่เริ่มด้วย `--brain` จะไม่ยอมเริ่มทำงาน แทนที่จะทำงานโดยไม่มี brain ที่ถูกขอไว้

| กรณี | การกระทำที่อนุญาต |
|---|---|
| แผนหยุดชะงัก | เตือนอีกหนึ่งครั้ง (ครั้งเดียวต่อแผน) แจ้งมนุษย์ หรือปล่อยไว้ |
| แผนถูกบล็อกด้วย `resolver: "lead"` อยู่ในประเภทที่ lead จัดการได้ (C3, C4, C7) และไม่มีเรื่องอ่อนไหว | ส่งคำขอคงที่หนึ่งครั้งให้ lead แก้ภายในอำนาจที่บันทึกไว้ แจ้งมนุษย์ หรือปล่อยไว้ |
| agent รออยู่ที่หน้าจอที่ daemon ไม่รู้จัก | แจ้งมนุษย์ หรือปล่อยไว้ |

เมื่อไม่มีคำตอบที่ถูกต้องภายใน 3 นาที ค่าเริ่มต้นคือปล่อยกรณีนั้นไว้ ข้อความของ brain ไม่เคยถูกพิมพ์ กดแป้น หรือรัน มันแต่งตั้ง lead เปิด agent merge, release ลงชื่อเข้าใช้ หรือเปลี่ยนสิทธิ์ไม่ได้ daemon ยังคงเป็นผู้กระทำเพียงรายเดียว ภายใต้ v8 `autonomy.brain` ของแผนบันทึกว่า brain ทำการกับแผนนั้นได้หรือไม่

## คิวของแผน

repository หนึ่งเก็บคิวของแผนที่อนุมัติแล้วไว้ใน `.dwp/queue.json` ได้ ด้วยสคีมา `dwp-queue-v1` pack (`shared/queue.py`) หรือมนุษย์เป็นผู้เขียน daemon อ่านอย่างเดียว อย่างมีขอบเขตและตรวจสอบทั้งเอกสาร create จะต่อท้ายแผนเมื่ออนุมัติหากนักพัฒนาขอให้เข้าคิว (หรือเมื่อสัญญา v8 บันทึก `autonomy.queue` ที่ไม่ใช่ `none`) มนุษย์หรือ lead จัดลำดับใหม่ execute ทำเครื่องหมายรายการเป็น `started` เมื่อแผนเริ่มภายใต้ lead ของตน และ `done` หลังปิดแผน คิวหนึ่งมีได้ไม่เกิน 64 รายการ dependency อยู่ภายในคิว: `after` ระบุแผนที่อยู่ในคิวแล้ว repository หนึ่งรันได้ทีละหนึ่งแผน เว้นแต่คิวมี `parallel: true`

เมื่อใช้ `--loop` และแผนปัจจุบันของ repository เสร็จสิ้น รายการถัดไปที่พร้อมจะเริ่มด้วยข้อความคงที่หนึ่งข้อความถึง lead ที่คิวระบุ: "Plan P is next in the queue of the repository at "R" and approved. In that repository, run the plan tool's execute flow for it (its start gate checks the approval again) and execute it to its end, respecting its gates." รายการจะพร้อมเฉพาะเมื่อแผน `after` เสร็จแล้ว ไม่มีแผนอื่นของ repository นั้นกำลังทำงาน รายการระบุ lead และการอนุมัติยังคงเป็นเหตุการณ์อนุมัติหรือแก้ไขล่าสุดของแผนสำหรับสัญญาที่ใช้งานอยู่ ลูปไม่เริ่มรายการ `launch` เช่นเดียวกับรายการที่ยังไม่อนุมัติหรือไม่มี lead รายการนั้นจะถูกรายงานเป็น `queue_blocked` คิวที่เสียหายจะอ่านเป็นคิวว่างและไม่เคยทำให้วงจรชีวิตของแผนพัง

## เหตุการณ์ การแจ้งเตือน และแผนที่ fleet

daemon รายงานเหตุการณ์ของแผนเป็นออบเจ็กต์ JSON `plan-event-v1` หนึ่งรายการทาง standard input ของคำสั่ง `--notify`: เหตุการณ์ แผน เครื่อง lead repository และประเภทของสิ่งกีดขวาง เหตุการณ์ได้แก่ `plan_stalled`, `plan_blocked`, `plan_no_lead`, `plan_lead_moved` และ `plan_completed` หนึ่งครั้งต่อแผนและสถานการณ์ รวมถึง `plan_queued_started`, `queue_blocked` เหตุการณ์การแต่งตั้งและ revive และ `needs_human` จาก brain ความล้มเหลวจะถูกบันทึกและไม่เคยหยุดรอบการทำงาน

ส่วนเสริม Herdr ของ pack มาพร้อม notifier ของ Dailybot (`scripts/notify-dailybot.py`) ที่แปลงเหตุการณ์เสร็จสิ้น หยุดชะงัก ถูกบล็อก ไม่มี lead และ lead ย้าย เป็นอัปเดตสำหรับทีมที่มนุษย์อ่านได้หนึ่งรายการผ่าน Dailybot CLI ที่ติดตั้งไว้ notifier จะออกอย่างเงียบ ๆ เมื่อไม่มี CLI ยังไม่ได้เข้าสู่ระบบ หรือส่งไม่สำเร็จ การแจ้งเตือนรายงานความคืบหน้าหรือความต้องการ ไม่เคยอนุมัติการกระทำหรือแทนที่บันทึกของแผน

เพื่อสังเกตลูป `herdr-peers plans` พิมพ์แผนของเครื่องหนึ่ง (`plans-v1`) และ `herdr-peers fleet` พิมพ์แผนที่ที่รวมกันแล้ว (`fleet-v1`): เครื่อง agent แผน และบทบาทของแต่ละ agent ในฐานะ lead ผู้สืบทอด หรือ lane `herdr-peers fleet ui` แสดงแผนที่แบบสด จัดกลุ่มตามแผน repository เครื่อง หรือคิว พร้อมมุมมองสิ่งที่ต้องการความสนใจ สิ่งที่กำลังทำงาน รออยู่ หรือเสร็จแล้ว UI อ่านอย่างเดียว: ไม่เขียนสถานะแผนและไม่ส่งข้อความเตือนถึง agent ใด

## ตัวอย่าง: หนึ่งแผนตลอดคืน

ลำดับต่อไปนี้เป็นเพียงตัวอย่าง แต่ละขั้นทำตามกฎที่อธิบายไว้ข้างต้น

1. ตอนเย็น นักพัฒนาอนุมัติแผนที่มีบล็อก `autonomy` ซึ่งคงค่าเริ่มต้นไว้ทั้งหมดยกเว้น `notify` agent รัน `execute` ซึ่งอ้างสิทธิ์บันทึก lead พร้อมผู้สืบทอดหนึ่งคน
2. นักพัฒนาเริ่ม `herdr-peers autopilot start --loop --notify "<notifier>"` แล้วออฟไลน์
3. lead ทำ task เสร็จสามรายการและจบรอบของตน ห้านาทีต่อมา เมื่อไม่มี lane ใดทำงานและไม่มีคำตอบที่รออยู่ daemon ส่งข้อความเตือนคงที่ให้ทำต่อ และ lead กลับมาทำต่อที่ task ถัดไป
4. task หนึ่งต้องใช้ secret ที่แผนไม่มี lead ยกสิ่งกีดขวาง C1 โดยไม่ระบุ resolver (อ่านเป็น `human`) แล้วหยุด daemon ไม่ส่งอะไรถึงแผน บันทึก `plan_blocked` และ notifier โพสต์อัปเดตสำหรับทีมหนึ่งรายการที่ระบุประเภทของสิ่งกีดขวาง
5. ตอนเช้า นักพัฒนาให้ข้อมูลที่ต้องการ lead แก้สิ่งกีดขวางด้วย `ledger.py unblock` และการดำเนินงานดำเนินต่อ ต่อมา pane ของ lead ปิดลง หลังรายการสองครั้งที่ไม่มี pane นั้น daemon ขอให้ผู้สืบทอดรัน `lead takeover` epoch เลื่อนขึ้น และผู้สืบทอดทำต่อภายใต้ gates เดิม
6. ก่อน merge ครั้งสุดท้ายของแผน lead คนใหม่รัน `lead verify` แผนเสร็จสิ้น `plan_completed` ไปถึง notifier และหาก repository มีคิว lead ของแผนที่อนุมัติแล้วถัดไปจะได้รับข้อความคงที่ของคิว

ไม่มีจุดใดที่ daemon อนุมัติสิ่งใด พิมพ์ข้อมูลรับรอง หรือตัดสินว่างานควรเป็นอะไร

## ขอบเขตของอำนาจ

ลูปหยุดตรงจุดที่อำนาจของแผนหยุดพอดี ประเภทการยกระดับของโปรโตคอล agent เป็นตัวกำหนดเส้นนั้น: C1 อำนาจ (การกระทำนอกการอนุญาตของแผน ณ จุดตรวจความยินยอม หรือเกี่ยวข้องกับ secrets) C2 หน้าจอความยินยอม (หน้าจอสิทธิ์ การเข้าสู่ระบบ ข้อมูลรับรอง หรือการชำระเงิน ซึ่ง agent ไม่เคยกดแป้นผ่าน) C3 ความกำกวมที่ลดทอนไม่ได้ C4 gate ที่ผ่านไม่ได้หากไม่ทำให้อ่อนลง C5 ความเสียหาย C6 ข้อกำหนด และ C7 ความสามารถที่หมดลง เมื่อข้อใดข้อหนึ่งเกิดขึ้นโดยไม่มีการอนุญาตล่วงหน้า การดำเนินงานจะหยุดที่ gate และความต้องการนั้นจะถูกบันทึกและรายงาน

การเข้าสู่ระบบและข้อมูลรับรองยังคงเป็นการกระทำของมนุษย์เสมอ มนุษย์เริ่ม daemon ให้การอนุญาตการแต่งตั้งหรือ revive อย่างชัดแจ้ง และแก้ความต้องการที่อำนาจที่บันทึกไว้รองรับไม่ได้ สำหรับทุกอย่างที่เหลือ มนุษย์จะได้รับแจ้งแทนที่จะต้องคอยเฝ้าทุกขั้น

## ทำงานโดยไม่มีส่วนเสริม

สิ่งเหล่านี้ไม่มีข้อใดจำเป็น หากไม่มี Herdr หรือปิดใช้ส่วนเสริม pack จะทำงานเหมือนไม่มีลูปอยู่: แผนดำเนินงานในเซสชันเดียว กลับมาทำต่อด้วย `resume` จาก task แรกที่ยังเปิดอยู่ หรือส่งต่อให้ agent อื่นผ่านการส่งต่องานที่มนุษย์ประสาน สัญญาของแผน สิ่งกีดขวางแบบมีโครงสร้าง และส่วนหัวของ `PROGRESS.md` ทำงานแบบเดียวกัน ดังนั้นมนุษย์หรือ agent อื่นจะอ่านสถานะเดียวกับที่ลูปจะอ่าน
